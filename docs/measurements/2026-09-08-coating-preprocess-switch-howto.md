# 전처리 전환 확인 — 사내 PC 에서 무엇을 돌리고 무엇을 읽나

전처리 규칙이 바뀌었다(앵커 병합 + 끝 기준 ±10분 격리 + 선별 통일).
실데이터는 사내 PC 에만 있으므로 아래를 직접 돌리고, **§0 · §3 · §4 세 덩어리만**
잘라서 돌려주면 된다. 원본 데이터는 필요 없다.

## 1. 돌릴 것

```
cd backend
python -m app.coating.diagnose --preprocess data/coating/raw/merged.parquet --out preprocess.txt
```

`--out` 을 쓴다. **셸 리다이렉션(`> preprocess.txt`)은 쓰지 않는다** — PowerShell 은
외부 프로그램의 출력을 파일에 담기 전에 `[Console]::OutputEncoding`(사내 PC 기본
cp949)으로 한 번 해석한다. 프로그램이 UTF-8 로 내보내도 그 자리에서 한글이 깨지고,
깨진 글자가 그대로 저장돼 무엇으로 열어도 돌아오지 않는다. `--out` 은 파일을 직접
쓰므로(UTF-8 BOM) 셸이 무엇이든 상관없고, 메모장·엑셀도 바로 알아본다.

`--out` 없이 돌리면 화면으로 나온다. 콘솔이 한글을 제대로 보여주면 그래도 된다.

리포트까지 같이 보려면:

```
python -m app.coating.report --input data/coating/raw/merged.parquet --dump
```

`--dump` 를 주면 `12_event_ledger.csv` 가 함께 떨어진다. 엑셀에서 열어
`isolated` 로 필터하면 통과한 것만 볼 수 있다.

## 2. 읽는 법 — §4 (창이 반응을 담고 있나)

이전 판은 "최댓값이 마지막 칸에 섰는가" 하나만 봤다. 그 검사 하나로는
놓치는 실패 양식이 있다 - 순수지연이 창보다 길면 관측한 0~10분 구간
전부가 순수 노이즈이고, 그때 argmax 는 11칸에 균등분포한다. Monte Carlo
로 재보면 그 경우에도 "마지막 칸이 아니다" 가 표본 수와 무관하게 약
90.9% 확률로 나온다 - 표본을 늘려도 사라지지 않는 거짓 `✓` 였다. 그래서
지금은 판정이 셋으로 갈린다.

| 출력 | 뜻 | 다음 |
|---|---|---|
| `✓ 창 안쪽에서, 노이즈 위로 반응이 잡혔다` | 최댓값이 안쪽(마지막 칸이 아님)이고 자기 표준오차(SE)의 2배를 넘는다 | 10분 창이 반응을 담고 있다 — 그대로 진행 |
| `⚠ 가장자리에서 상승` | 최댓값이 마지막 칸에 섰다 — 창이 짧다 | `COATING_ISOLATION_POST_MINUTES` 와 `COATING_RESPONSE_POST_MINUTES` 를 **둘 다** 표시된 두 배 값으로 올리고 재실행 |
| `⚠ 노이즈 아래` | 최댓값이 안쪽이지만 자기 SE 의 2배를 못 넘는다 — 이 창 안에서는 반응이 검출되지 않았다 | 순수지연이 창보다 길거나 반응이 검출 한계 아래다(곡선만으로는 못 가른다). 창을 늘려 다시 본다. 그래도 안 보이면 §0 의 격리 통과 건수(표본 부족)를 의심한다 |
| `⚠ 다만 최댓값이 lag 0(또는 1)에 섰다` | 위 `✓` 를 받았어도 붙는 별도 경고 — 순수지연이 있는 계단 응답이 lag 0~1 에서 봉우리에 서는 것은 물리적으로 불가능하다 | zone 대응이 밀렸을 수 있다. `diagnose.py --dump <덤프폴더>` 로 커널 진단(밀림 탐지)을 본다 |
| `격리를 통과한 이벤트가 0건` | 표본이 없다 | §0 의 탈락 내역을 본다 |
| `정렬된 응답이 없다` | 표본이 모자라거나, 이 창의 모든 lag 에서 Wet 이 결측이다(조정한 zone 의 Wet 이 그 lot 에서 통째로 미측정일 수 있다) | 원본에 제어값 변경이 있는지 §0 의 "시작값 제외" 줄을, Wet 결측 여부는 유효 zone 목록을 본다 |

한 줄에 최댓값 lag·평균·SE·관측 끝 lag 이 전부 찍힌다(예:
`최댓값 lag = +6분 (관측 끝 +10분) — 평균 +0.5000 · SE 0.0100 (기준 2×SE)`) —
판정만 있고 근거가 없으면 사람이 확인할 수 없기 때문이다. "노이즈 아래"
경계는 코드 상수 `response._SIGMA_K = 2.0`(SE 의 2배)이고, "두 배로 올리고"
는 실측이다 - 코드가 현재 설정을 그 자리에서 두 배로 계산해 찍는 값이라,
설정이 바뀌면 이 문구도 같이 바뀐다(`app/coating/diagnose.py`
`_window_check_lines`).

뒤 격리(`COATING_ISOLATION_POST_MINUTES`)와 응답창(`COATING_RESPONSE_POST_MINUTES`)
두 값은 **항상 같이** 움직여야 한다. 뒤 격리보다 응답창이 길면, 응답으로 읽는
구간의 일부가 다른 조정에 오염돼 있어도 통과한다. 둘이 어긋나면 이제 §4 의
헤더와 리포트의 동특성 절 양쪽에서 `⚠` 로 스스로 경고한다(예외로 죽이지
않는다 - 실행은 계속되고 사람이 보고 판단한다).

## 3. 읽는 법 — §0 (격리 통과 건수)

| 통과 건수 | 뜻 | 다음 |
|---|---|---|
| 20건 이상 | 커널 추정 하한(`_MIN_EVENTS=20`, `report.py:29`)을 넘는다 — 코드가 막는 값 | 진행 |
| 5~19건 | L·τ 는 볼 수 있으나 커널은 이르다 — **"5" 는 코드 상수가 아니라 판단선**이다 | 격리 창을 ±5로 좁혀 재시도하고 §3 으로 손실을 확인 |
| 5건 미만 | 이 데이터로는 안 된다 — 위와 같은 판단선 | §3 의 "구에만" 건수를 근거로 사업부에 요구 |

코드가 실제로 강제하는 하한은 이 "5" 가 아니라 둘이다. 커널은
`_MIN_EVENTS=20`(`report.py:29`, 분기 `report.py:343`) 밑에서 안 돈다. L·τ 는
(이벤트×zone) 쌍이 `_MIN_PAIRS=3`(`response.py:46`, 분기 `response.py:273`) 밑으로
떨어지면 평균의 표준오차조차 못 내 계산 자체가 멈춘다. 위 표의 "5건" 은 이
쌍 하한 위에 여유를 둔 **판단선**일 뿐이다 — 이벤트 수와 쌍 수는 다르므로(zone
을 여럿 만지면 이벤트 하나가 쌍 여럿이 된다) 정확한 대응표가 아니고, 그래서
코드 상수가 아니다.

## 4. 읽는 법 — §3 (구/신 대조)

- **신에만 N건**: 뒤 창이 60→10 으로 풀려 살아난 것. 늘어나는 게 정상이다.
- **구에만 N건**: 연쇄 병합이 삼켰던 긴 구간. 이게 크면 현장에서 조정이 촘촘하게
  일어난다는 뜻이고, **그 자체가 사업부에 낼 요구서다** — "한 번 만지고 10분
  기다려 달라" 의 근거.
- **양쪽 통과 N건**: 두 규칙이 같이 인정한 것. 이게 0이면 전환의 영향이 크므로
  숫자를 그대로 돌려준다.

## 5. 무엇을 돌려주나

§0 깔때기 전체, §3 대조표 전체, §4 전체(헤더 아래 판정 줄들 - 이제 갈래에 따라
줄 수가 다르다). 세 덩어리를 그대로 복사해 붙이면 된다. 원본 CSV·parquet 은
보내지 않는다.

## 6. 숙제 — 여기서는 못 끝내는 것

가드 밴드 문서(`docs/understanding/2026-09-07-01-explanation-coating-noise-floor.html`)
의 노이즈 플로어 결론은 조용 구간 가드 ±60분을 전제로 나왔다. 이번 전환으로
그 가드가 ±10분(`coating_response_post_minutes`)으로 줄었다 - 좁은 가드는 σ 를
더 많은 표본으로 추정하지만, 진짜 조정 근처를 더 타이트하게만 뺀다는 뜻이라
σ 값 자체가 달라질 수 있다. **이 재확인은 실데이터가 있어야 하고, 여기서
합성으로는 결론을 낼 수 없다.** §4 를 돌릴 때 noise_floor 의 σ (리포트의
"노이즈 바닥" 줄)를 예전 문서의 값과 비교해 자릿수가 같은지 확인해 달라 -
달라졌으면 가드 밴드 문서를 새 σ 로 다시 써야 한다.
