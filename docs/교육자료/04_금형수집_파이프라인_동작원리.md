# 금형 데이터 수집 파이프라인 — 동작 원리

부서가 올린 엑셀을 읽어 대시보드에 띄우기까지, 코드가 실제로 무엇을 하는지 정리한 학습용 문서다.
설계 의도는 `docs/superpowers/specs/2026-07-28-금형-데이터-수집-파이프라인-design.md` 에 있고,
이 문서는 **"그래서 코드가 어떻게 도는가"** 를 다룬다.

- 대상: 1단계(MES + IQC). PQC 조인·자동 폴링·마스터 엑셀 출력은 아직 없다.
- 코드 위치: `backend/app/ingest/` (12개 모듈, 약 1,500줄)

## 1. 실행 방법

```powershell
# 폴더 만들기 (경로는 backend/ 기준 상대경로)
mkdir backend\data\uploads\MES
mkdir backend\data\uploads\IQC

# 엑셀 넣기
#   backend\data\uploads\MES\   ← MES 생산이벤트 파일 (마스터)
#   backend\data\uploads\IQC\   ← IQC 입고검사 파일

python dev.py
```

`http://localhost:5173/dashboard` → 좌측 상단 **데이터 수집** 패널 → `수집 실행`

### `.env` 는 건드릴 필요 없다

`Settings` 에 기본값이 있어서 `.env` 에 없으면 그대로 쓴다 (`backend/app/config.py`).

| 설정 | 기본값 | 의미 |
|---|---|---|
| `INGEST_ROOT` | `./data/uploads` | 업로드 루트 (backend/ 기준) |
| `INGEST_STAGE_DIRS` | `MES:mes,IQC:iqc,PQC:pqc,…` | 폴더명 ↔ 소스종류 매핑 |
| `MOLDS_DB_PATH` | `./molds.db` | 수집 DB. **채팅용 `app.db` 와 반드시 별도** |
| `INGEST_POLL_SECONDS` | `0` | 자동 폴링 끔 (1단계는 수동 트리거만) |

`molds.db` 를 분리한 이유: `app.db` 는 LangGraph 체크포인터가 채팅 턴마다 쓴다.
같은 파일에 수집 배치가 쓰면 SQLite 쓰기 락을 두고 경합해 `database is locked` 가 난다.

### LLM 이 필요하다

양식을 **처음 볼 때만** 에이전트가 구조를 해석한다. Ollama 나 사내 LLM 이 붙어 있어야 한다.
사이드바의 **LLM 연결 테스트**로 먼저 확인할 것.

## 2. 한눈에 보는 전체 흐름

```
엑셀 저장
   │
   ▼
① sha256 비교 ─── 같으면 ──→ skipped ("변경된 파일이 없어…")
   │ 다름
   ▼
② open_workbook (Excel 프로세스 기동, 파일당 1회)
   │
   ▼
③ 앵커 대조 ─── 일치 ──→ 캐시된 레이아웃          (LLM 0회)
   │ 불일치
   ▼
   ReAct 에이전트 → submit_layout                  (LLM 1회)
   │
   ▼
④ parse_rows (순수 파이썬) → list[Row]
   │
   ▼
⑤ assemble  MES=마스터, IQC 부착, 손실 집계
   │
   ▼
⑥ replace_all  트랜잭션 안에서 DB 전체 교체
   │
   ▼
⑦ query.py 가 DB 를 읽어 대시보드 객체로
```

**핵심 한 줄**: LLM 은 *"어디에 무엇이 있는지"* 만 판단하고, *"값이 얼마인지"* 는 코드가 정한다.
그래서 같은 파일을 몇 번 돌려도 숫자가 흔들리지 않는다.

## 3. 모듈 지도

```
backend/app/ingest/
  schemas.py    데이터 계약 (SheetLayout, Row, MoldRecord, RunSummary …)
  normalize.py  셀 값 정규화                        ★순수
  scanner.py    폴더 훑기 + 내용 해시
  layout.py     앵커 대조 → 캐시 재사용 판정          ★순수
  discover.py   ReAct 에이전트 + submit_layout 도구   ← LLM 은 여기서만
  parser.py     격자 + 레이아웃 → 행                 ★순수
  assemble.py   MES/IQC 행 → 금형 레코드             ★순수
  db.py         molds.db 스키마·연결·마이그레이션
  registry.py   처리 이력 / 레이아웃 캐시 / 배치 요약
  store.py      금형 데이터 전체 교체 (트랜잭션)
  pipeline.py   위를 엮어 배치 하나를 실행           ← 유일한 조립 지점
```

의존 방향이 한쪽으로만 흐른다:

```
normalize / layout / parser / assemble  →  schemas 만       (LLM✗ COM✗ DB✗ 파일✗)
scanner                                 →  표준 라이브러리
discover                                →  schemas, excel.tools, llm
store / registry                        →  schemas, sqlite3
pipeline                                →  전부                ← 조립은 여기서만
```

**★순수 함수 4개가 이 설계의 값어치다.** 틀릴 위험이 가장 큰 로직인데
Excel 도 LLM 도 DB 도 없이 리터럴만으로 전부 테스트된다 —
나중에 "왜 이 값이 이렇게 나왔지"를 반드시 재현할 수 있다.

## 4. 단계별 상세

### ① 변경 감지 — 내용 해시

`scanner.py:27` `file_hash()`

```python
def file_hash(path: str) -> str:
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while chunk := f.read(_HASH_CHUNK):
            h.update(chunk)
    return h.hexdigest()
```

**mtime 이 아니라 내용 해시**를 쓴다. mtime 은 복사·이동만 해도 바뀌어 거짓 변경으로 잡히고,
그때마다 배치 전체가 돈다 (파일당 Excel 프로세스가 뜨므로 수십 초).

`scanner.py:80` — `~$파일명.xlsx` 는 건너뛴다. 사람이 엑셀을 열어두면 Excel 이 만드는
잠금 파일이고, 실제 워크북이 아니라 열면 매번 실패한다. **실무에서 가장 흔한 상황이다.**

`scanner.py:62` — `.env` 의 종류 오타(`MES:mess`)는 **즉시 `ValueError`**.
조용히 건너뛰면 운영자는 "IQC 를 읽고 있다"고 믿는데 실제로는 아무것도 안 읽는 상태가 된다.
설정 오류는 데이터 오류와 달리 사람이 고쳐야 하고, 고칠 수 있으려면 먼저 보여야 한다.

`scanner.py:86` — 파일을 못 읽으면(`OSError`) 그 파일만 건너뛰고 `ScanResult.unreadable` 에 담는다.
파일 하나의 실패가 스캔 전체를 죽이면 안 되기 때문이다.

이어서 `pipeline.py:123`:

```python
if unreadable:
    return RunSummary(status="skipped", unreadable_files=unreadable, …)
```

**못 읽은 파일이 하나라도 있으면 배치 자체를 건너뛴다.** 배치는 DB 를 전체 교체하므로,
그냥 진행하면 그 파일의 데이터가 화면에서 조용히 사라진다.

### ② 파일 열기 — 파일당 딱 한 번

`pipeline.py:48`

```python
with open_wb(found.path) as wb:          # ← EXCEL.EXE 기동 (수 초)
    for sheet_name in wb.sheet_names():
        grid, top_left = wb.used_values(sheet_name)
```

- `grid` : 시트 값의 2차원 리스트
- `top_left` : `used_range` 의 좌상단 주소 (예 `"C3"`)

**`used_range` 는 `A1` 에서 시작하지 않을 수 있다.** 이 오프셋이 이후 모든 좌표 계산에 쓰인다
(`layout.py:14` `cell_at()`). 오프셋을 빼먹으면 앵커가 전부 어긋나 캐시가 영원히 미스가 되고
파일마다 LLM 이 다시 돈다.

xlwings 는 COM 스레드에 고정돼 있어 **병렬 처리가 불가능**하다 — 파일을 하나씩 순차로 연다.
openpyxl 을 못 쓰는 환경이라 이 제약을 받아들였다.

### ③ 양식 해석 — LLM 이 관여하는 유일한 지점

`pipeline.py:53`

```python
cached = pick_layout(grid, top_left, registry.load_layouts(conn, found.kind, sheet_name))
layout = cached
if layout is None:
    layout = discover_layout(model, wb, found.kind, sheet_name, config=config)
```

#### 앵커란 무엇인가

에이전트가 직접 지목한 *"여기에 이 텍스트가 있으면 같은 양식이다"* 다.

```python
anchors = [
  AnchorCheck(cell="B4",  text="금형번호"),
  AnchorCheck(cell="B14", text="검사항목"),
  AnchorCheck(cell="B33", text="측정값"),
]
```

`layout.py:32` `anchors_match()` 가 전부 일치할 때만 캐시를 재사용한다.
빈 앵커 목록은 `False` — 판정 근거가 없는 레이아웃을 아무 파일에나 쓰면 안 된다.

> **왜 "헤더 행을 해시"가 아닌가**
> 설계 중 두 번 무너졌다. (a) 헤더가 몇 번째 행인지 모르는 상태에서 헤더를 해시할 수 없다(닭과 달걀).
> (b) 한 시트에 표가 여러 개면 헤더도 여러 개다.
> 양식을 이해한 주체가 "무엇이 같으면 같은 양식인가"를 가장 잘 안다.

`registry.load_layouts()` 는 **최신순**(`ORDER BY id DESC`)으로 돌려준다.
옛 레이아웃을 먼저 대조하면 앵커가 우연히 겹칠 때 바뀐 양식을 옛 규칙으로 파싱한다.
옛 행은 지우지 않는다 — "언제 양식이 바뀌었고 그때 어떻게 해석했는가"가
추출값을 의심할 때 유일한 근거다.

#### 에이전트가 캐시 미스에서 하는 일

기존 엑셀 도구 5종(`app/excel/tools.py`)을 그대로 재사용한다:

```
list_sheets          "시트 3개군"
read_range B1:P40    "상단에 기본정보, 14행부터 표"
find_value "소계"     "31행이 소계행 → 이 표는 summary"
column_profile C     "고유값 27개, 전부 RX 시작 → 금형번호 맞다"
read_range B33:P50   "아래 표가 하나 더"
        ↓
submit_layout(...)   ← 이 도구를 부르면 종료
```

**왜 에이전트인가**: 실물 IQC 시트는 한 장에 카테고리 2개 × 표 2개 = **표 4개**가 있고
2단 병합 헤더까지 섞여 있다. 격자를 한 번 보여주고 매핑을 받는 단발 호출로는 못 잡는다 —
어디에 무엇이 있는지 찾아다녀야 한다.

**왜 `submit_layout` 이 도구인가**: 마지막에 JSON 을 텍스트로 뱉게 하면 파싱이 깨지기 쉽다.
도구 인자로 받으면 Pydantic 이 검증하고, 잘못 채우면 도구 에러가 돌아가
에이전트가 스스로 고쳐 다시 제출한다 (LangGraph 의 `ToolNode` 가 이 왕복을 처리).

제출 없이 끝나면 `LayoutNotSubmittedError` — 빈 레이아웃을 돌려주면
"표가 하나도 없는 시트"로 오인되어 조용히 0건이 들어온다.

#### 단계별로 요구하는 필드 어휘가 다르다

`discover.py` 의 `FIELD_GUIDE`:

| 단계 | 요구 필드 |
|---|---|
| **MES** | `mold_no`, `status`, `line`, `machine`, `date`, `process`, `time`, `shot_count`, `total_installs`, `total_production`, `defect_rate` |
| **IQC** | `mold_no` (필수) + `punch`, `die`, `diff`, `gap`, **나머지 열은 헤더 텍스트를 그대로 필드명으로** |

마지막 줄이 핵심이다. 측정자·조립자·연마자·NG사진 같은 건 미리 예측할 수 없어서,
**헤더 텍스트가 그대로 화면 라벨이 된다.** 고정 스키마와 유연 스키마를 섞는 이유다.

`FIELD_GUIDE` 에 없는 단계로 부르면 `ValueError` — 어휘 안내 없이 돌리면
에이전트가 필드명을 지어내고, `assemble` 이 그 이름을 모르니
**파싱은 되고 쓰이지는 않는** 상태가 된다.

### ④ 값 추출 — 순수 파이썬

`parser.py:103` `parse_rows(grid, top_left, layout, source_file) -> list[Row]`

레이아웃이 지목한 좌표에서 값을 꺼낼 뿐이다. **같은 격자 + 같은 레이아웃 = 항상 같은 결과.**

`parser.py:114` — `role="summary"` 표는 **건너뛴다**:

```python
detail_tables = [t for t in layout.tables if t.role == "detail"]
```

안 그러면 "소계"·"총계"가 금형번호로 읽힌다. 실물 IQC 시트에 summary 표가 두 개나 있다.

`parser.py:86` — `data_end_row` 가 없으면 매핑된 칸이 전부 빈 행에서 멈춘다.
표 아래의 비고·서명란이 금형인 척 딸려오는 걸 막는다.

`parser.py:50` — 컬럼 매핑이 없는 detail 표는 `ValueError`.
`TableBlock.columns` 는 기본값이 `[]` 라 에이전트가 빠뜨려도 스키마 검증을 통과하는데,
막지 않으면 "표는 있는데 행이 0개"라는 추적 불가능한 상태가 된다.

여기서 나오는 `Row` 는 **아직 어느 금형 것인지 모른다.**
IQC 는 금형번호 열로, PQC(2단계)는 시간 조인으로 귀속되는데
그 차이가 파서에 섞이면 읽을 수 없어진다.

### ⑤ 금형 조립 — MES 가 마스터

`assemble.py:129` `assemble(mes_rows, iqc_rows) -> AssembleResult`

**MES 만 금형의 존재를 선언한다.** IQC 는 이미 있는 금형에 덧붙일 뿐이다.
이 방향이 뒤집히면 "대시보드 목록에 무엇이 나오는가"의 정의가 흔들린다.

#### 정규화는 한 곳에만

`normalize.py`:

```python
normalize_mold_no("#RX41194")  → "RX41194"     # 이력표의 # 접두사 제거
normalize_mold_no(" rx28312 ") → "RX28312"
normalize_mold_no("소계")       → None          # 금형이 아님
normalize_status("사용 중")     → "in_use"
normalize_status("가동")        → None          # 인식 못 함 → 추측하지 않음
cell_to_text(28312.0)          → "28312"       # xlwings 는 정수도 float 로 준다
cell_to_text(0)                → "0"           # 0 은 값이다. None 이 아니다
to_float("0.8%")               → 0.008         # 퍼센트는 비율로
to_float(True)                 → None          # bool 은 숫자가 아니다
```

흩어지면 대장의 `RX28312` 와 이력표의 `#RX41194` 가 다른 금형이 되어
이후 어떤 조인도 안 맞는다.

`str(28312.0) == "28312.0"` 이 되면 매칭이 전부 깨지므로 `cell_to_text` 가 소수점을 뗀다.
`bool` 은 파이썬에서 `int` 의 하위 타입이라 숫자 분기보다 **먼저** 처리해야 한다 —
안 그러면 "체크" 표시가 `1` 로 집계된다.

#### 상태 어휘

`normalize.py` 의 `STATUS_MAP`:

```
사용중 / 사용 / 가동중       → in_use
대기중 / 대기 / 보관중 / 보관 → standby
수리중 / 수리 / 정비중        → repair
폐기 / 폐기됨 / 불용          → retired
```

**인식 못 한 값은 추측하지 않고 `None` 을 돌려준다.** 임의로 "대기중"에 넣으면
조용히 틀린 값이 DB 에 남는다. 대신 그 금형을 제외하고 원문을 모아 화면에 드러낸다.

> 이 어휘는 실물 MES 를 보기 전 **추측**이다. 첫 실행 후 화면의
> "인식하지 못한 상태" 목록에 뜨는 문자열이 곧 여기 추가할 값이다.

#### 손실은 전부 셈해서 돌려준다

| 필드 | 뜻 |
|---|---|
| `orphan_mold_nos` | IQC 에 있는데 MES 에 없는 금형 (오타? 진짜 MES 누락?) |
| `unknown_statuses` + `unknown_status_rows` | 인식 못 한 상태 원문과 그 행 수 |
| `skipped_rows` | 금형번호가 없어 버린 행 (소계행·빈 행은 정상) |
| `failed_files` | 파싱 실패한 IQC 파일과 사유 |
| `unreadable_files` | 디스크엔 있는데 못 읽은 파일 |

**조용히 빠지는 데이터가 없어야 한다** — 화면만 봐서는 절대 알 수 없는 손실이기 때문이다.

`assemble.py:70` — 사용중이 아닌 금형은 `line`/`machine` 을 비운다.
남겨두면 화면이 "3-2에 걸려 있다"는 거짓 정보를 보여준다 (대시보드 필터도 같은 규칙).

### ⑥ 저장 — 트랜잭션 안에서 전체 교체

`store.py` + `pipeline.py:177`

```python
conn.execute("BEGIN")
DELETE FROM mold / mold_design / mold_stage / production_run
INSERT INTO mold (...)
INSERT INTO mold_stage (mold_no, 'iqc', 'ok', items_json, ...)
record_files(...)                                    # 파일 이력 갱신
DELETE FROM ingested_file WHERE path IN (사라진 파일)
conn.commit()                                        # ← 여기서 한 번만
```

**upsert 가 아니라 전체 교체다.** MES 가 마스터이고 매번 전체를 다시 읽으므로,
MES 에서 사라진 금형은 대시보드에서도 사라져야 한다. upsert 만 하면 유령 금형이 영원히 남는다.

셋을 한 트랜잭션으로 묶은 이유: 따로 커밋하면 `replace_all` 이 커밋된 뒤 `record_files` 가
실패했을 때 `mold` 는 새 상태, `ingested_file` 은 옛 상태로 갈라져 다음 회차에 전부 재처리된다.

실패하면 전부 롤백돼 이전 상태가 유지된다. **반쯤 교체된 DB — 옛 금형 + 새 IQC — 가 가장 나쁘다.**

#### 테이블

```sql
ingested_file (path PK, kind, content_hash, seen_at)      -- 변경 감지
sheet_mapping (id PK, kind, sheet_name, layout_json, …)   -- 레이아웃 캐시 (누적)
ingest_run    (id PK, status, mold_count, orphan_json, …) -- 배치 요약
mold          (mold_no PK, status, line, machine, …)      -- ↓ 배치마다 전체 교체
mold_design   (mold_no PK, angle_deg, …)                  --   1단계에선 항상 빔
mold_stage    (mold_no, stage, status, error, items_json) --   iqc 행만 생김
production_run(mold_no, install_seq, …)                   --   1단계에선 항상 빔
```

### ⑦ 화면

`IngestPanel.tsx` → `POST /api/ingest/run` → `finally` 에서 `loadMolds()` + `loadOptions()`

`api/ingest.py` 는 수집을 `asyncio.to_thread` 로 워커 스레드에 넘긴다.
Excel COM 은 파일당 수 초가 걸려 이벤트 루프에서 돌리면 그동안 서버 전체가 멈춘다.

**수집 실패는 500 이 아니라 200 + `status="error"`.** 예외로 던지면 화면이 사유를 못 보여주고
"알 수 없는 오류"만 남는다.

`molds/query.py` 가 DB 를 읽어 대시보드 객체로 만든다.
**`mold_stage` 에 행이 없는 것이 곧 `missing`** 이라, 5단계를 순회하며 없는 것을 채운다.
1단계는 IQC 만 적재하니 나머지 4개 탭은 `·` 배지가 뜬다.

## 5. 변경 감지는 3층이다

| 층 | 무엇을 보나 | 결정하는 것 |
|---|---|---|
| **파일** | `sha256(파일 바이트)` | 배치를 돌릴지 말지 |
| **양식** | 앵커 셀의 텍스트 | LLM 을 부를지 말지 |
| **행** | — | **비교 안 함. 그냥 전부 다시 읽음** |

`pipeline.py:135`

```python
changed = [f for f in found if known.get(f.path) != f.content_hash]
removed = set(known) - found_paths
if not changed and not removed:
    return RunSummary(status="skipped", …)   # "변경된 파일이 없어 건너뛰었습니다"
```

**하나라도 바뀌면 배치 전체를 다시 돈다.** 증분 처리를 안 하는 이유:
"부분 갱신 때문에 옛 데이터가 남는" 부류의 버그를 만드는데,
수천 행 규모에서 그 위험을 살 만한 이득이 없다.

## 6. 행이 추가되면 어떻게 인지하나

**행 단위 변경 감지는 아예 없다.** 시스템은 "행이 추가됐다"를 인지하지 않는다.
매번 전부 다시 읽고 DB 를 통째로 교체한다.

행 추가는 **파일 층에서만** 걸린다. 파일 바이트가 바뀌었으니 해시가 달라지고 배치가 돈다.
그 뒤로는 "무엇이 추가됐는지" 따지지 않는다.

### 새 행이 딸려오는 실제 메커니즘

`used_range` 가 커지는 것뿐이다.

```python
grid, top_left = wb.used_values(sheet_name)   # Excel 의 used_range
```

행을 추가하면 `used_range` 가 자동으로 늘어나 `grid` 의 길이가 커진다. 그다음 `parser.py:69`:

```python
hard_end = _last_row_no(grid, top_left)     # base_row + len(grid) - 1
end = (
    min(table.data_end_row, hard_end)
    if table.data_end_row is not None
    else hard_end                            # ← 여기
)

for row_no in range(table.data_start_row, end + 1):
    ...
    if all(v is None for v in values.values()):
        if table.data_end_row is None:
            break                            # 빈 행에서 멈춤
```

**`data_end_row` 가 `None` 이면 상한이 `hard_end`**, 즉 격자가 자란 만큼 그대로 따라간다.
15행이던 표가 20행이 되면 `range(2, 21)` 로 늘어날 뿐이다.

레이아웃에는 "몇 행이었다"는 정보가 **없다.** `data_start_row`(어디서 시작)와
컬럼 매핑(어느 열)만 있다. 끝은 매번 데이터가 정한다.

앵커도 안 건드린다 — 헤더는 `B4`, `B14` 그대로 있고 데이터는 그 아래로만 늘어난다.
**캐시 히트 → LLM 호출 0회.**

```
행 추가
  ↓
해시 변경        → 배치 실행
  ↓
앵커 그대로      → 캐시된 레이아웃 재사용 (LLM 0회)
  ↓
used_range 확장  → 새 행이 자연히 포함
  ↓
DB 전체 교체     → 옛 20행 지우고 새 25행 삽입
```

DB 에도 "추가"라는 개념이 없다. `DELETE` 후 `INSERT` 다.

### 상황별 정리

| 상황 | 해시 | 앵커 | LLM | 새 행 반영 |
|---|---|---|---|---|
| 맨 아래 표에 행 추가 | 변경 | 일치 | 0회 | ✅ |
| 값만 수정 | 변경 | 일치 | 0회 | ✅ |
| **위쪽** 표에 행 추가 (아래 표가 밀림) | 변경 | 불일치 | 1회/시트 | ✅ |
| 컬럼 추가·이름 변경 | 변경 | 불일치 | 1회/시트 | ✅ |
| `data_end_row` 가 숫자로 박힘 | 변경 | 일치 | 0회 | ❌ **조용히 누락** |

## 7. 설계가 지키려는 원칙 4가지

### ① `null` 과 `0` 을 구분한다

값을 모를 때 `0`/`""` 으로 채우면 **"0회(신품)"와 "미상(추출 실패)"이 화면에서 구분되지 않는다.**

```typescript
export const DASH = "—";
export function fmtNumber(v: number | null): string {
  return v === null ? DASH : v.toLocaleString("ko-KR");
}
```

`fmtMeasurePair` 도 같은 이유로 한쪽만 있으면 통째로 `—` 다 — `140×—mm` 는 치수가 아니다.

이 원칙 때문에 대시보드의 수량 필드 5개를 nullable 로 바꿨다
(`shot_count`, `total_installs`, `total_production` 등).

### ② 조용히 빠지는 데이터가 없어야 한다

버려지는 것은 반드시 건수나 목록으로 **화면까지** 도달해야 한다.
API 에만 있으면 아무도 안 본다. `RunSummary` 의 손실 5종이 전부 `IngestPanel` 에 렌더된다.

**한 행의 실패가 파일 전체를 버리지 않고, 한 파일의 실패가 배치를 죽이지 않는다.**
단 MES 실패는 예외 — 마스터가 없으면 금형 목록을 만들 수 없다.

### ③ 같은 입력이면 항상 같은 결과

| 층 | 방식 | 보장 |
|---|---|---|
| 구조 이해 | ReAct 에이전트 | **유연성** — 어떤 양식이 와도 이해한다 |
| 값 추출 | 순수 파이썬 | **일관성** — 같은 파일은 항상 같은 값 |

값 추출까지 LLM 에 맡기면 같은 대장을 어제 읽었을 때 8,412, 오늘 8,142 가 나올 수 있다.
그게 바로 "일관되지 않은 추출"이다.

### ④ 실패는 시끄럽게

조용한 실패를 명시적 예외로 바꾼 곳이 세 군데다:

| 위치 | 조건 | 안 막으면 |
|---|---|---|
| `scanner.py:62` | `.env` 의 종류 오타 | 폴더를 안 읽으면서 화면은 성공 |
| `parser.py:50` | detail 표에 컬럼 매핑 없음 | "표는 있는데 행이 0개" |
| `discover.py` | `FIELD_GUIDE` 에 없는 단계 | 에이전트가 필드명을 지어냄 |

## 8. 조용히 틀릴 수 있는 곳

실물로 돌리기 전에 알아둘 것들이다.

### ⚠️ `data_end_row` 에 숫자가 박히면 새 행이 무시된다

에이전트가 `data_end_row=42` 로 제출했다면 43행부터는 **영원히 안 읽힌다.**
화면은 정상으로 보이고 새 데이터만 조용히 없다.

막으려고 두 군데에 명시해뒀다:

```python
data_end_row: int | None = Field(
    default=None,
    description="데이터 마지막 행 번호. 표 아래에 다른 블록이 없으면 null 로 "
                "두면 빈 행에서 자동으로 멈춘다. 헤더 행 번호를 넣지 마라",
)
```

프롬프트에도 같은 내용이 있다. **에이전트가 따르는지는 실물로 확인해야 한다** —
첫 실행 후 `backend/logs/llm_calls.log` 에서 `submit_layout` 인자를 볼 것.

### ⚠️ 세로로 쌓인 표에서 위쪽 표에 행이 추가되면 앵커가 밀린다

실물 IQC 시트는 표가 4개 세로로 쌓여 있다:

```
행 4   ┌ 측정 이력 summary
행 14  ├ 측정 이력 상세        ← 여기에 5행 추가하면
행 33  ├ 대장 summary          ← 이 아래가 전부 밀린다 (33 → 38)
행 45  └ 대장 상세
```

앵커 `B33="구분"` 이 불일치 → **에이전트 재실행.**

동작 자체는 옳다(레이아웃이 실제로 바뀌었으니 재해석이 맞다).
다만 "양식이 안정적이면 LLM 호출은 평생 몇 번"이라는 기대는 이 시트 형태엔 안 맞는다 —
위쪽 표가 자랄 때마다 시트당 1회씩 돈다.

**맨 아래 표만 자란다면 문제없다.** 대장 상세에 입고 이력이 쌓이는 게 일반적 형태라면
앵커를 안 건드리니 캐시가 계속 히트한다.

### ⚠️ MES 상태 어휘가 하나만 달라도 그 금형들이 목록에서 빠진다

`STATUS_MAP` 밖의 값("가동"/"휴지"/"이관")이 있으면 그 금형이 통째로 제외된다.
화면이 비어 보이면 **"인식하지 못한 상태" 목록부터 확인할 것.**
거기 뜨는 문자열이 곧 `normalize.py` 에 추가할 값이다.

### 알려진 미해결 항목 (2단계 이월)

| 항목 | 내용 |
|---|---|
| 경고 소실 | 파싱 실패한 파일이 이력에 남아, 다음 회차엔 `skipped` 로 끝나 `failed_files` 경고가 화면에서 사라진다. 파일을 고치면 해시가 바뀌어 재시도되므로 데이터 유실은 아니다 |
| 문구 충돌 | "읽지 못한 파일"이 *파싱 실패*와 *열지도 못함* 양쪽에 쓰인다 |
| 이중 계상 | `unknown_status_rows` 와 `skipped_rows` 가 두 줄로 떠 같은 행이 두 번 세어진 것처럼 보인다 |
| 중첩 경로 | `INGEST_STAGE_DIRS=raw/IQC:iqc` 처럼 중첩 경로를 쓰면 잠긴 파일 감지가 깨진다 (기본값은 평면이라 미발동) |
| IQC 다행 | 한 금형에 IQC 행이 여러 개면 같은 라벨의 항목이 중복 나열된다 |
| 다중 시트 | 워크북의 모든 시트마다 에이전트가 1회씩 돈다 (잡시트 포함) |
