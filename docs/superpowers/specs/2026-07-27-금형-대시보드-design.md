# 금형 관리 대시보드 화면 설계

- 날짜: 2026-07-27
- 배경: 기존 채팅 화면(FastAPI + LangGraph 백엔드, React + Vite 프론트엔드)에 더해, 금형 관련 엑셀 문서(IQC/PQC/설계/설치/AI복검 5단계)를 사람이 폴더에 계속 적재하면 AI가 읽고 이해해 정형화된 대시보드로 정리하는 기능이 필요하다.
- 이 문서는 그 전체 기능 중 **첫 번째 서브프로젝트인 "대시보드 화면"** 만 다룬다.

## 전체 그림에서의 위치

요청된 기능은 독립적인 4개 시스템으로 나뉜다. 한 스펙에 담으면 뭉개지므로 각각 별도의 스펙 → 계획 → 구현 사이클로 간다.

| # | 서브프로젝트 | 상태 |
|---|---|---|
| 1 | **대시보드 화면** (필터 · 기본정보 · 생산결과) | **이 문서** |
| 2 | 파일 자동 적재 (폴더 감시, 신규/변경 감지) | 이후 |
| 3 | AI 추출 · 정규화 (엑셀 → 정형 스키마) | 이후 |
| 4 | 추출 데이터 영속화 · 조회 (DB) | 이후 |

①을 먼저 하는 이유는, ①이 확정하는 **데이터 계약이 ③의 목표가 되기 때문**이다. 화면이 무엇을 요구하는지 정해지지 않으면 추출이 무엇을 뽑아야 하는지도 정할 수 없다.

## 목표

- 채팅 화면과 대시보드 화면을 오갈 수 있다(브라우저 뒤로가기·새로고침·링크 공유가 정상 동작).
- 금형 목록을 상태·라인/호기로 필터하고 금형 번호로 검색할 수 있다.
- 선택한 금형의 설계 정보 · 누적 이력 · 현 상태 · 생산 결과를 볼 수 있다.
- 5단계(설계/IQC/PQC/설치/AI복검) 각각의 데이터를 탭으로 나눠 보고, **어느 단계 데이터가 비었는지 한눈에 알 수 있다**.
- AI가 추출할 데이터의 스키마를 코드(Pydantic + TypeScript)로 확정한다.

## 비목표 (이번 스코프 제외)

- 엑셀 파일 감시 · 자동 적재 (서브프로젝트 ②)
- AI 추출 · 정규화 (서브프로젝트 ③)
- DB 테이블 · 영속화 (서브프로젝트 ④) — 이번에는 코드 안의 고정 샘플 데이터를 쓴다
- 대시보드에서의 데이터 편집 (읽기 전용)
- 원본 엑셀 파일 열기/다운로드 (`SourceRef` 필드는 정의하되 UI는 툴팁까지만)
- 차트 · 그래프 (표와 카드로 시작)
- 채팅 세션의 URL 딥링크 (`/chat/:sessionId`) — 라우터 도입으로 가능해지지만 이번 범위 밖

## 확인이 필요한 가정

구현 중 실물과 다르다고 밝혀지면 스펙을 고쳐야 하는 항목이다. 실제 엑셀 파일을 확인하지 못한 상태에서 세운 가정이다.

1. **금형 상태 어휘는 `사용중 / 대기중 / 수리중 / 폐기` 4개다.** 실제 운영 어휘가 다르면 `MoldStatus` 를 교체한다.
2. **생산 결과의 한 행은 "설치 1회분"이다** (`install_seq` 가 키). 한 번 설치해 여러 기간으로 나눠 생산·집계한다면 행 정의를 바꿔야 한다.
3. 금형 번호는 문자열이며 전역 고유하다(`M-1024` 형태 가정, 형식 검증은 하지 않는다).

## 데이터 계약

이 스펙에서 가장 중요한 산출물이다. 화면의 요구사항이 아니라 **서브프로젝트 ③(AI 추출)이 맞춰야 할 목표**이기 때문이다.

### 고정 스키마와 유연 스키마를 섞는다

실제 파일을 확인할 수 없는 상태에서 전부 고정 스키마로 잡으면, IQC/PQC 항목이 예상과 다를 때 백엔드와 프론트를 모두 고쳐야 한다. 반대로 전부 유연하게 하면 타입 안전성이 사라지고 화면이 무엇을 그릴지 알 수 없다.

가르는 기준은 **"필드가 이미 명시되었는가"** 이다.

| 영역 | 방식 | 근거 |
|---|---|---|
| 설계 / 누적이력 / 현상태 / 생산결과 | 고정 | 각도·높이·단차·타수·불량율까지 필드가 지정돼 있다 |
| IQC / PQC / AI복검 | 유연 (label-value 리스트) | 어떤 항목이 있는지 아직 모른다. AI가 무엇을 뽑든 표시할 수 있어야 한다 |

### 타입 정의

프론트는 `frontend/src/types/mold.ts`, 백엔드는 `backend/app/molds/schemas.py`(Pydantic)에 **같은 모양으로** 정의한다. 둘 중 하나만 고치면 어긋나므로, 필드를 바꿀 때는 반드시 양쪽을 함께 고친다.

```ts
type MoldStatus  = "in_use" | "standby" | "repair" | "retired";
type StageKey    = "design" | "iqc" | "pqc" | "install" | "ai_recheck";
type StageStatus = "ok" | "missing" | "error";   // 탭 배지용

// ── 목록 행 (좌측 마스터)
interface MoldSummary {
  mold_no: string;                     // "M-1024"
  status: MoldStatus;
  line: string | null;                 // status !== "in_use" 면 null
  machine: string | null;              // 위와 같음
  shot_count: number;                  // 사용 타수
  latest_defect_rate: number | null;   // 0.008 = 0.8%. 가장 큰 install_seq 의 defect_rate
  total_production: number;
  stage_status: Record<StageKey, StageStatus>;   // 5단계 전부 (탭 배지용)
}

// ── 상세
interface MoldDetail {
  summary: MoldSummary;
  design: DesignSpec;             // 고정 — "설계" 탭
  history: CumulativeHistory;     // 고정 — 요약 카드
  current: CurrentState;          // 고정 — 요약 카드
  productions: ProductionRun[];   // 고정 — "생산결과" 탭
  stages: StagePanel[];           // 유연 — IQC / PQC / AI복검 탭만. 아래 주의 참고
}

interface DesignSpec {            // 모든 필드 nullable — 추출 실패를 표현해야 한다
  angle_deg: number | null;
  height_mm: number | null;
  step_mm: number | null;         // 단차
  overall_mm: number | null;      // 전체
  plate_height_mm: number | null;
  plate_width_mm: number | null;
}

interface CumulativeHistory {
  total_installs: number;         // 총 설치 횟수
  total_production: number;       // 총 생산 수량
  first_installed_at: string | null;
}

interface CurrentState {
  status: MoldStatus;
  line: string | null;
  machine: string | null;
  shot_count: number;             // 사용 타수
  installed_at: string | null;
}

interface ProductionRun {
  install_seq: number;            // 설치 횟수 (37회차)
  line: string;
  machine: string;
  started_at: string;
  ended_at: string | null;        // null = 진행 중
  grind_result: string | null;    // 연마결과: "OK" | "재연마" 등 — 어휘가 미확정이라 문자열
  defect_rate: number | null;
  defects: { label: string; rate: number }[];   // 항목별 불량율 — 항목이 가변
}

// ── 유연 영역
interface StagePanel {
  stage: StageKey;
  status: StageStatus;
  updated_at: string | null;
  error: string | null;           // status === "error" 일 때 실패 사유
  items: StageItem[];
}

interface StageItem {
  label: string;                  // "경도"
  value: string;                  // "HRC 58"  — 표시 전용이므로 문자열로 통일
  judgment: "ok" | "ng" | null;
  source: SourceRef | null;
}

interface SourceRef {
  file: string;                   // "IQC/2026-07-03_M-1024.xlsx"
  sheet: string | null;
  cell: string | null;            // "C12"
}
```

### 5단계와 탭·필드의 대응

`StageKey` 는 5개인데 `MoldDetail.stages` 에는 3개만 들어간다. 헷갈리기 쉬운 지점이므로 명시한다.

| 단계 (`StageKey`) | 탭 이름 | 데이터가 담기는 곳 |
|---|---|---|
| `install` | 생산결과 | `productions` (고정) + `current` 카드 |
| `design` | 설계 | `design` (고정) |
| `iqc` | IQC | `stages[]` 중 `stage === "iqc"` (유연) |
| `pqc` | PQC | `stages[]` 중 `stage === "pqc"` (유연) |
| `ai_recheck` | AI복검 | `stages[]` 중 `stage === "ai_recheck"` (유연) |

- **`stages` 배열에는 유연 단계 3개만** 넣는다. `design`/`install` 을 여기 중복으로 넣지 않는다 — 같은 값이 두 곳에 있으면 어느 쪽이 진실인지 모호해진다.
- **`stage_status` 는 5개 전부** 갖는다. 탭 배지는 다섯 탭 모두에 필요하기 때문이다.
- `design`/`install` 의 `stage_status` 판정 기준: 해당 영역에 값이 하나라도 있으면 `ok`, 전부 `null`/빈 배열이면 `missing`, 추출이 실패했으면 `error`.

### `SourceRef` 를 넣는 이유

`app/excel/agent.py` 의 `EXCEL_SYSTEM_PROMPT` 에는 이미 *"근거가 된 셀 주소를 답변에 함께 제시한다"* 는 규칙이 있다. 대시보드도 같은 원칙을 따라야 한다 — **AI가 뽑은 값이 이상할 때 어느 파일 어느 셀에서 왔는지 즉시 확인할 수 있어야** 한다. 추적 경로가 없으면 값 하나가 틀린 순간 대시보드 전체를 신뢰할 수 없게 된다.

이번 스펙에서는 필드를 정의하고 값 옆 툴팁으로 노출하는 데까지만 한다. 원본 파일 열기는 이후 서브프로젝트에서 다룬다.

### 항목별 불량율을 배열로 두는 이유

`defects: { label, rate }[]` 로 둔 것은 불량 항목(버·크랙·미성형 등)이 제품이나 시기마다 달라질 수 있기 때문이다. 고정 컬럼으로 잡으면 새 불량 유형이 생길 때마다 스키마를 고쳐야 한다. 표는 화면에 있는 행들의 `label` 합집합으로 컬럼을 동적 생성한다.

## 화면 구조

### 라우팅

`react-router-dom` 을 도입한다.

```
/                    → /chat 으로 리다이렉트
/chat                → 기존 채팅 (Sidebar + ChatPanel, 수정 없음)
/dashboard           → 대시보드, 금형 미선택
/dashboard/:moldNo   → 대시보드, 해당 금형 선택
```

zustand 상태로 화면을 전환하는 방법(의존성 0)도 가능하지만 채택하지 않았다. **결정적인 이유는 딥링크가 아니라 뒤로가기다** — 상태 기반 전환은 대시보드에서 브라우저 뒤로가기를 누르면 채팅으로 가는 것이 아니라 앱 밖으로 나간다. 해시 기반 자체 라우팅은 react-router 의 축소판을 직접 만드는 셈이라, 지금 아끼는 의존성보다 이후 유지비가 크다.

### 전환 버튼

두 화면 위에 고정되는 얇은 `AppHeader` 에 둔다. 대시보드에는 채팅의 Sidebar 가 없어 버튼을 넣을 자리가 없고, 화면마다 따로 두면 위치가 어긋난다.

```
┌─ 금형관리   [채팅] [대시보드]          ← AppHeader (고정)
├────────────────────────────────────────
│  (라우트에 따라 ChatLayout 또는 DashboardPage)
```

### 레이아웃 (마스터-디테일)

```
┌ 상태[사용중▼] 호기[전체▼]  ┬─ M-1024 상세 ──────────────────┐
│ 검색 [M-10        ]        │  설계    │ 누적이력  │ 현 상태   │
│                            │  각도    │ 총설치 37 │ 호기 3-2  │
│ ▸ M-1024  3-2   8,412      │  12.5°   │ 총생산1.2M│ 타수8,412 │
│   M-1031  3-5   2,109      ├────────────────────────────────┤
│   M-1002  1-4   5,530      │[생산결과][설계][IQC][PQC][AI⚠] │
│   M-0998  대기    -        ├────────────────────────────────┤
│                            │ 설치#│호기│시간대   │연마 │불량율│
```

### 컴포넌트 트리

```
App
└ BrowserRouter
  └ AppHeader + Routes
     ├ /chat      → ChatLayout          (기존 Sidebar + ChatPanel 재사용)
     └ /dashboard → DashboardPage
        ├ MoldFilterBar      검색 + 상태 + (종속)라인/호기
        ├ MoldList           좌측 마스터
        └ MoldDetailPanel    우측 디테일
           ├ SummaryCards    설계 / 누적이력 / 현 상태 3카드
           └ StageTabs
              ├ ProductionTable   생산결과 (고정 스키마)
              ├ DesignPanel       설계 (고정 스키마)
              └ StageItemPanel    IQC / PQC / AI복검 (유연 — 3탭이 공유)
```

파일은 `frontend/src/components/Dashboard/` 아래에 둔다. 기존 `components/Chat/`, `components/Sidebar/` 패턴을 그대로 따른다.

`StageItemPanel` 하나로 3개 탭을 처리하는 것이 유연 스키마의 이점이다. IQC든 PQC든 AI복검이든 `StageItem[]` 을 그리는 일은 같으므로, 단계가 늘어도 컴포넌트는 늘지 않는다.

### 필터 구조

전역 필터를 세 개 나란히 두지 않는다. 셋의 성격이 다르기 때문이다.

- **금형 번호**는 필터가 아니라 **선택(selection)** 이다. 마스터-디테일에서는 목록 행 클릭이 곧 선택이므로, 금형 번호는 드롭다운이 아니라 목록 위의 **검색창**(부분일치)으로 둔다.
- **설치 호기**는 **금형 상태에 종속**이다. 대기중·수리중·폐기 금형은 호기가 없으므로 "대기중 + 3호기"는 항상 0건이다. 나란히 두면 사용자가 빈 화면을 만들 수 있는 길을 열어주게 된다.

최종 구조:

```
🔍 [M-10        ]                        ← 금형번호 검색 (부분일치)

상태 [사용중 ▼]   라인/호기 [3-2 ▼]      ← 호기는 상태=사용중일 때만 표시
```

- 상태 기본값은 **`사용중`** 이다. 화면을 열면 호기 드롭다운이 바로 보여 "3-2에 뭐가 걸렸지"를 한 번에 물을 수 있다.
- 상태를 `사용중` 이외의 값으로 바꾸면 라인/호기 드롭다운은 사라지고 필터 값도 초기화된다.
- 전체를 보려면 상태를 `전체` 로 바꾼다. **`전체` 는 `MoldStatus` 값이 아니라 UI 전용 선택지**이며, 선택 시 `status` 쿼리 파라미터를 아예 보내지 않는다(라인/호기도 마찬가지). 즉 드롭다운의 선택지는 `전체 | 사용중 | 대기중 | 수리중 | 폐기` 5개다.

### 상태 관리

기존 `store/store.ts` 는 채팅 관심사로 응집돼 있다. 대시보드 상태를 여기 넣으면 한 파일이 두 화면을 떠안게 되므로 **`store/dashboardStore.ts` 로 분리**한다.

| 상태 | 위치 | 근거 |
|---|---|---|
| 선택된 금형 (`moldNo`) | URL path | 링크 공유·뒤로가기의 핵심 |
| 필터 (검색어·상태·라인/호기) | zustand | 일시적. URL에 넣는 복잡도 대비 이득이 작다 |
| 목록·상세 데이터, 로딩·에러 | zustand | 기존 채팅 스토어와 같은 패턴 |

## API 계약

```
GET /api/molds?status=in_use&line=3&machine=2&q=M-10   → MoldSummary[]
GET /api/molds/{mold_no}                               → MoldDetail   (없으면 404)
GET /api/molds/filters                                 → { statuses, lines, machines }
```

- 모든 쿼리 파라미터는 선택이다. 없으면 필터하지 않는다.
- `q` 는 금형 번호 부분일치(대소문자 무시).
- `/filters` 를 따로 두는 이유: 라인·호기 목록을 프론트에 하드코딩하면 라인이 늘 때마다 프론트를 배포해야 한다. 서버가 실제 데이터에서 뽑아 준다.

### 백엔드 스텁의 범위

기존 `app/excel/` 패턴을 따라 배치한다.

```
backend/app/api/molds.py          라우터
backend/app/molds/schemas.py      Pydantic 모델 (데이터 계약의 서버 쪽 정의)
backend/app/molds/sample_data.py  고정 샘플 금형 3~5대
backend/app/molds/query.py        필터링 로직
```

**필터링 로직은 스텁이라도 실제로 구현한다.** 고정 JSON을 그대로 돌려주면 필터 UX를 검증할 수 없다. 메모리 리스트를 실제로 거르면 프론트가 완성 상태로 동작하고, 서브프로젝트 ④에서 `query.py` 내부만 DB 쿼리로 바뀌면 된다.

샘플 데이터는 화면의 모든 상태를 덮도록 구성한다:

- 사용중 금형 (라인/호기 있음, 생산 이력 여러 건)
- 대기중 금형 (라인/호기 `null`, 생산 이력 있음)
- 수리중 금형
- **일부 단계가 `missing` 인 금형** (탭 배지 확인용)
- **일부 단계가 `error` 인 금형** (실패 표시 확인용)
- **`design` 필드 일부가 `null` 인 금형** (`—` 렌더 확인용)

Pydantic 으로 응답을 고정하면 FastAPI 가 OpenAPI 문서를 자동 생성하므로, 서브프로젝트 ③이 "이 스키마에 맞춰 채워 넣기"로 명확해진다.

### 설정

이번 스펙에서 `.env` 에 추가할 설정은 없다. 샘플 데이터가 코드 안에 있어 경로 설정이 불필요하다. 서브프로젝트 ②에서 감시 폴더 경로를 추가할 때 `Settings` 필드와 `backend/.env.example` 에 함께 넣는다(프로젝트 규칙: 설정의 단일 출처는 `backend/.env`).

## 빈 상태와 에러 처리

AI가 채우는 대시보드이므로 **"값이 없다"가 정상 상태**다. 이를 대충 처리하면 화면을 신뢰할 수 없게 된다.

| 상황 | 처리 |
|---|---|
| 목록 0건 | "조건에 맞는 금형이 없습니다" + **필터 초기화** 버튼 |
| 금형 미선택 (`/dashboard`) | 우측 패널에 "왼쪽에서 금형을 선택하세요" |
| 없는 금형 번호로 직접 진입 | 404 안내 + 목록으로 돌아가기 |
| 단계 문서 없음 (`missing`) | 탭에 회색 표식, 패널에 "아직 문서가 없습니다" |
| 추출 실패 (`error`) | 탭에 ⚠, 패널에 `error` 사유 표시 |
| 개별 값 `null` | **`—` 로 렌더** |
| API 실패 | 화면 상단 배너 + 재시도 버튼 |

`null` 을 `—` 로 그리는 것은 사소해 보이지만 중요하다. `null` 을 `0` 으로 렌더하면 "사용 타수 0회(신품)"와 "사용 타수 미상(추출 실패)"이 화면에서 구분되지 않고, 현장에서 오판으로 이어진다.

## 테스트

### 프론트엔드 (vitest, 기존 설정 그대로)

- 상태를 `사용중` 이외로 바꾸면 라인/호기 드롭다운이 사라지고 필터 값이 초기화된다 (종속 필터의 핵심 동작)
- `defects` 배열의 `label` 합집합으로 생산결과 표 컬럼이 동적 생성된다
- `null` 필드가 `—` 로 렌더된다 (`0` 이 아니라)
- 목록 행 클릭 시 URL 이 `/dashboard/M-1024` 로 바뀐다
- `stage_status` 가 `missing`/`error` 인 탭에 표식이 붙는다

### 백엔드 (pytest, 기존 설정 그대로)

- 필터 조합별 결과 건수 (`status=in_use&line=3`)
- `q` 부분일치가 대소문자를 무시한다
- 없는 금형 번호 → 404
- `/filters` 가 샘플 데이터에 실제로 존재하는 라인·호기만 돌려준다
- 응답이 Pydantic 스키마를 만족한다 (필드 누락·타입 불일치 회귀 방지)

## 다음 단계

이 서브프로젝트가 끝나면 다음 순서를 제안한다.

1. **② 파일 자동 적재** — 감시 폴더 구조와 파일명 규칙을 정하고, 신규/변경 감지를 구현한다. 여기서 처음으로 실제 엑셀 파일을 봐야 하므로, 이 문서의 "확인이 필요한 가정" 을 검증하는 시점이기도 하다.
2. **④ 영속화** — ②가 감지한 파일과 ③이 뽑은 값을 담을 테이블. `query.py` 내부를 DB 쿼리로 교체한다.
3. **③ AI 추출** — 기존 `app/excel/` 의 도구(`read_range`, `find_value`, `column_profile`, `aggregate`)를 재사용해 이 문서의 스키마를 채운다. 유연 영역(`StageItem[]`)이 있어 파일마다 항목이 달라도 대응할 수 있다.

②를 ③보다 먼저 하는 이유는, 실제 파일을 봐야 추출 프롬프트를 쓸 수 있기 때문이다.
