# 금형 데이터 수집 파이프라인 설계

- 날짜: 2026-07-28
- 배경: 대시보드 화면(서브프로젝트 ①, PR #4)이 머지됐다. 지금 대시보드가 보여주는 데이터는
  `backend/app/molds/sample_data.py` 의 하드코딩 샘플이다. 이 문서는 그 자리를 **실제 엑셀 파일에서
  추출한 데이터**로 채우는 파이프라인을 설계한다.
- 선행 문서: `docs/superpowers/specs/2026-07-27-금형-대시보드-design.md`

## 요구사항

1. 각 부서 사람들이 단계별(IQC, PQC …) 엑셀 파일을 정해진 폴더에 계속 업로드한다.
2. **MES 엑셀이 금형 정보의 마스터 데이터다.** 금형번호 목록과 기본정보(사용 상태, 불량율)를
   가지고 있고, 계속 갱신된다.
3. 금형번호 검색 시 전체 목록이 나와야 한다 — 그 목록의 출처가 MES다.
4. 각 금형에 대해 IQC · PQC 문서에서 관련 정보를 추출해 대시보드에 보여준다.
5. **PQC 문서에는 금형번호가 없다.** 날짜·공정·호기·시간으로 MES 행과 맞춰 금형을 찾는다.
6. 최종 결과를 마스터 엑셀(금형별 1행 요약)로 관리자 폴더에 갱신한다.

## 전체 그림에서의 위치

선행 스펙은 전체를 4개 서브프로젝트로 나눴다. 이 문서는 그중 ②③④를 **하나의 파이프라인**으로
다룬다 — 세 조각의 계약이 서로 맞물려 있어 따로 설계하면 어긋나기 때문이다.
구현은 4단계로 나눠 진행한다(아래 "구현 단계" 절).

## 목표

- MES 에 있는 모든 금형이 대시보드 목록에 나온다.
- 각 금형의 IQC 측정값과 PQC 불량 이력이 그 금형 아래에 붙어 보인다.
- 사람이 파일 양식을 바꿔도 시스템이 스스로 알아채고 재해석한다.
- **같은 입력이면 항상 같은 결과가 나온다.**
- 추출·조인에 실패한 건수가 **반드시 눈에 보인다.**

## 비목표

- 대시보드에서의 데이터 편집 (읽기 전용 유지)
- 추출 결과 승인/검토 큐 화면 — 실패는 `error` 표시로 충분하다는 결정
- 사람이 마스터 엑셀을 고치면 시스템으로 역류하는 양방향 동기화
- 실시간성 (수동 트리거 → 자동 폴링 순으로 확장, 분 단위 지연 허용)
- MES 자체의 생성·관리 (외부 시스템의 산출물로 간주)

## 데이터 소스

### MES (마스터)

한 행 = **생산 이벤트 1건** (날짜 + 시간별). 수백~수천 행. **파일이 계속 덮어쓰기된다.**

제공하는 것: 금형번호, 사용 상태, 불량율, 호기, 날짜/공정/시간.

**대시보드가 MES 에서 받아야 하는 것과 실제 보유 여부**:

| 대시보드 필드 | MES 보유 |
|---|---|
| `mold_no` | 확인됨 |
| `status` (사용 상태) | 확인됨 |
| `line` / `machine` (호기) | 확인됨 |
| `latest_defect_rate` (불량율) | 확인됨 |
| `shot_count` (사용 타수) | **미확인** |
| `total_installs` (총 설치 횟수) | **미확인** |
| `total_production` (총 생산 수량) | **미확인** |
| `install_seq` (설치 회차) | **미확인** — 생산이벤트 행에는 없을 가능성 |
| `grind_result` (연마결과) | **미확인** |

### IQC

금형번호가 **있다.** 실물 sheet1 구조:

```
sheet1
├─ 카테고리 A: "Stack 금형 측정 이력"
│   ├─ summary 표   유형1(양극 성형/음극 성형/음극 절단/소계)
│   │               유형2(상면 성형/하면 성형/상면 절단/하면 절단/소계/총계)
│   └─ 상세 표      No │ 모델 │ 기종 │ 1차 명칭 │ 관리 번호 │ 업체 │ 26년 측정일
│                   1  │ 양극 성형 │ H104 │ 1차 양극 Notching │ #RX41194 │ 일신 │ …
│
└─ 카테고리 B: "Stack H104 금형 측정 대장"
    ├─ summary 표   구분 │ 내용(검사 수량/불량 수량/불량률) │ 1월 │ … │ 합계
    └─ 상세 표      2단 멀티헤더
                    행13: No │ 입고시간 │ 금형번호 │   성형부    │   절단부
                    행14:    │         │         │ 정극성형│부극성형│양극절단│음극절단
                    … 측정자 │ 조립자 │ 출고시간 │ 측정결과 PUNCH │ 측정결과 DIE │ 연마자 │ NG 사진
                    행15: 1 │2026.07.01│ RX28312 │ - │ - │ 체크 │ - │ 홍길동 │ 홍길동 │ … │ A │ A │ 구군 │ -
```

**가져올 것**: 금형번호 행에서 punch, die부, 차이, 간극 수치.

### PQC

금형번호가 **없다.** 컬럼:

```
날짜 │ 공정 │ 기종 │ 호기 │ 시간 │ Lot │ Cell ID │ PO │ 등급 │ 불량현상 │
(Burr)위치 │ (Burr)방향 │ 원인 │ 대책 │ 결과 확인 │ 작업자 │ 책임반장 │ 불량 사진
```

**가져올 것**: 불량현상 (+ 등급, Burr 위치/방향, 원인, 대책).
**금형 귀속**: `(날짜, 공정, 호기, 시간)` 으로 MES 행과 정확 일치 조인 → 그 MES 행의 금형번호.

## 확정된 결정과 근거

각 결정의 **근거**를 함께 적는다 — 근거가 바뀌면 결정도 다시 봐야 하기 때문이다.

### 1. MES 가 마스터, 대시보드 금형 목록의 유일한 출처

**근거**: 사용자 요구. 금형번호 검색 시 전체 목록이 나와야 하는데, 그 "전체"의 정의가 필요하다.
IQC/PQC 는 특정 금형에 대한 부속 정보일 뿐 금형의 존재를 선언하지 않는다.

**따라오는 것**: MES 에 없는 금형번호가 IQC 에서 발견되면 **대시보드에 넣지 않는다.** 다만 조용히
버리지 않고 "MES 에 없는 금형 N건" 으로 남긴다 — 진짜 MES 누락일 수도, 오타일 수도 있다.

### 2. 마스터 엑셀은 산출물, DB 가 원본

`molds.db` (SQLite) 가 유일한 원본이고, 마스터 엑셀은 거기서 생성해 관리자 폴더에 갱신한다.

**근거**: 엑셀을 원본으로 삼으면 누군가 파일을 열어둔 동안 쓰기가 막히고, 파일이 손상되면
전체 이력을 잃는다. 산출물로 두면 잠기거나 깨져도 재생성하면 복구된다.

### 3. `molds.db` 는 기존 `app.db` 와 별도 파일

**근거**: `app.db` 는 LangGraph 체크포인터가 채팅 턴마다 쓴다. 같은 파일에 수집 워커가 쓰면
SQLite 쓰기 락을 두고 경합해 `database is locked` 가 나거나 양쪽이 느려진다.

### 4. 구조 이해는 LLM 에이전트, 값 추출은 순수 파이썬

| 층 | 방식 | 보장 |
|---|---|---|
| 구조 이해 | ReAct 에이전트 + 엑셀 도구 | **유연성** — 어떤 양식이 와도 이해한다 |
| 값 추출 | 순수 파이썬 함수 | **일관성** — 같은 입력은 항상 같은 결과 |

**근거**: 값 추출까지 LLM 에 맡기면 같은 대장을 어제 읽었을 때 8,412, 오늘 8,142 가 나올 수
있다. 그게 바로 "일관되지 않은 추출"이다. 구조는 한 번 이해하면 되지만 값은 매번 정확해야 한다.
또한 수천 행짜리 MES 를 매번 LLM 컨텍스트에 넣는 것은 물리적으로 불가능하다.

### 5. 실행은 문서 중심, 결과는 금형 중심

요구사항은 "금형번호를 토대로 각 문서에서 정보를 추출"이다. 그대로 구현하면 안 된다:

```
금형 100개 × 문서 3개 = 문서를 300번 연다
xlwings 는 파일당 EXCEL.EXE 기동 = 수 초
→ 15분 이상
```

같은 결과를 문서당 1회 열기로 얻는다:

```
1. MES 읽기  → 금형 목록 + 조인 인덱스        (파일 1회)
2. IQC 읽기  → 인덱스: 금형번호 → 행들         (파일 1회)
3. PQC 읽기  → 인덱스: 조인키 → 행들           (파일 1회)
4. 금형별 조립 → 메모리에서 인덱스 조회         (I/O 0회)
```

4단계가 요구사항의 "금형 번호를 토대로 관련 정보를 다 추출"에 해당하며, 그것이 메모리에서
일어날 뿐이다. **결과는 동일하고 금형 중심이라는 의도도 그대로다.**

### 6. 어느 파일이든 바뀌면 배치 전체를 다시 돈다

증분 처리를 하지 않는다.

**근거**: MES 가 계속 덮어쓰기되고 수백~수천 행이다. 매번 전체를 읽어도 수 초다. 증분 로직은
"부분 갱신 때문에 옛 데이터가 남는" 부류의 버그를 만드는데, 그 위험을 살 만큼의 이득이 없다.

**따라오는 것**: DB 갱신은 **트랜잭션 안에서 전체 교체**(delete-all → insert-all)다. upsert 만
하면 MES 에서 사라진 금형이 유령으로 영원히 남는다. 실패 시 롤백되어 이전 상태가 유지된다.
이 결정으로 이전 초안의 "(금형, 단계) 최신 승리 / (금형, 회차) 누적" 병합 규칙이 **불필요해졌다.**

### 7. 캐시 무효화는 에이전트가 지목한 앵커로

**근거**: 처음에는 "헤더 행 텍스트를 해시"로 설계했으나 두 번 무너졌다.
(a) 헤더가 몇 번째 행인지 모르는 상태에서 헤더를 해시할 수 없다(닭과 달걀).
(b) 한 시트에 표가 여러 개면 헤더 행도 여러 개다.
양식을 이해한 주체가 "무엇이 같으면 같은 양식인가"를 가장 잘 안다 — 그래서 에이전트가
`anchors` 를 직접 제출한다.

### 8. 실패는 대시보드 `error` 표시로 끝낸다

검토 큐 화면을 만들지 않는다.

**근거**: 대시보드가 이미 `stage_status: "error"` 와 `StagePanel.error` 를 렌더한다.
새 UI 없이 곧바로 동작하고, 사람이 원본 엑셀을 고쳐 다시 올리면 내용 해시가 바뀌어 자동으로
재처리된다.

### 9. xlwings 전용 (openpyxl 사용 불가)

**근거**: 사용자 환경 제약. `backend/app/excel/workbook.py` 가 이미 이 제약 위에 설계돼 있다.

**따라오는 제약**:
- 파일 하나 읽는 데 EXCEL.EXE 가 뜬다 (수 초) → **파일당 한 번만 열어서 다 끝낸다**
- COM 스레드 제약 → **병렬 처리 불가, 순차 처리**
- FastAPI 이벤트 루프를 막으면 안 됨 → **백그라운드 실행**
- 현재 `workbook.py` 는 읽기 전용 → 마스터 엑셀 쓰기 경로를 같은 스레드 규약 위에 추가해야 함

부수 효과(긍정): Excel 이 직접 여니 `.xls`, 매크로 파일, 수식 결과까지 읽힌다.

## PQC 조인 — 이 설계의 최대 위험

금형번호가 없는 문서를 시간 정보로 붙이는 것이 **조용히 틀릴 수 있는 유일한 지점**이다.

```
PQC:  2026-07-02 │ 14:30 │ 3호기 │ Burr 발생
MES:  2026-07-02 │ 14:30 │ 3호기 │ 금형 RX28312
                                    ↑ 이게 맞나?
```

틀리면 **다른 금형에 불량이 붙는다.** 파싱 실패는 눈에 띄지만 잘못된 조인은 안 띈다 — 값이
그럴듯해 보이기 때문이다.

### 구체적 위험

| 위험 | 내용 |
|---|---|
| 시간 형식 | `14:30` / `14:30:00` / 엑셀 직렬값 `0.604166…` / `datetime` 객체 — 같은 시각이 네 가지로 저장된다 |
| 정밀도 차이 | PQC 는 *불량을 발견한* 시각, MES 는 *생산* 시각. 몇 분 어긋날 수 있다 |
| 다중 매칭 | 같은 `(날짜, 공정, 호기, 시간)` 에 MES 행이 여러 개면 어느 금형인지 알 수 없다 |
| 무매칭 | PQC 에는 있는데 MES 에 대응 행이 없다 |

### 정책: 틀리느니 빠뜨린다

- **다중 매칭** → 붙이지 않는다. 건수를 노출한다.
- **무매칭** → 붙이지 않는다. 건수를 노출한다.
- **정확히 1건 매칭** → 붙인다. 조인 근거를 `SourceRef` 에 남긴다("MES 42행과 매칭").

**근거**: 잘못된 금형에 불량 이력이 붙으면 그 금형에 대한 모든 판단이 오염되는데, 아무도
눈치채지 못한다. 빠진 것은 건수로 드러나 사람이 원인을 찾을 수 있다.

### 조인 키 정규화

**반드시 한 곳에만 둔다.** 양쪽에서 다르게 정규화하면 절대 매칭되지 않거나 잘못 매칭된다.

```python
def normalize_join_key(date, process, machine, time) -> JoinKey:
    """엑셀 셀 값(datetime / float / str)이 무엇으로 오든 하나의 표준형으로 만든다.

    - 날짜: date 객체로 통일 (datetime → .date(), 문자열 "2026.07.01"/"2026-07-01" 파싱)
    - 시간: 분 단위 정수로 통일 (datetime → h*60+m, 엑셀 직렬값 → round(v*24*60))
    - 공정/호기: strip + upper
    """
```

시간을 **분 단위**로 자르는 것은 의도적이다 — 초 단위까지 맞기를 기대하는 것은 비현실적이고,
분보다 거칠게 자르면 다중 매칭이 급증한다. 실물을 보고 조정할 수 있도록 이 함수 하나만 고치면
되게 둔다.

## 금형번호 정규화

**반드시 한 곳에만 둔다.** 두 군데서 다르게 정규화되면 같은 금형이 둘로 갈라진다.

```python
def normalize_mold_no(raw: str) -> str:
    """'#RX41194' → 'RX41194',  ' rx28312 ' → 'RX28312'"""
    return raw.strip().lstrip("#").strip().upper()
```

원본 문자열은 `source_file` 과 함께 보존해 추적 가능하게 둔다.

## 데이터 계약

### 레이아웃 스키마 (에이전트가 제출)

```python
class ColumnMap(BaseModel):
    field: str      # 고정 필드명 또는 헤더 텍스트 그대로
                    # 멀티헤더는 결합 라벨: "성형부/정극 성형"
    column: str     # "C"

class KeyValueItem(BaseModel):
    """표가 아닌 블록. 라벨 옆/아래에 값이 있는 형태(상단 기본정보 등)."""
    field: str
    value_cell: str                  # "D5"
    label_cell: str | None = None    # 어느 라벨을 보고 판단했는지 (근거)

class TableBlock(BaseModel):
    name: str                              # "금형 측정 대장 — 상세"
    role: Literal["detail", "summary"]     # summary 는 레코드로 파싱하지 않는다
    category: str | None = None            # "측정 이력" / "금형 측정 대장"
    header_rows: list[int]                 # [13, 14] — 멀티헤더는 여러 행
    data_start_row: int
    data_end_row: int | None = None        # None = 빈 행 만날 때까지
    columns: list[ColumnMap]

class AnchorCheck(BaseModel):
    """'여기에 이 텍스트가 있으면 같은 양식이다' — 에이전트가 직접 지목한다."""
    cell: str       # "B4"
    text: str       # "금형번호"

class SheetLayout(BaseModel):
    sheet_name: str
    key_values: list[KeyValueItem] = []
    tables: list[TableBlock] = []
    anchors: list[AnchorCheck]
    notes: str | None = None                # 에이전트가 애매하다고 판단한 점 (로그용)
```

`role="summary"` 인 표는 파싱하지 않는다. 구분하지 않으면 "소계"를 금형번호로 읽는 사고가 난다.

### 파서 출력은 일반 행

`parser.py` 는 더 이상 금형 귀속을 하지 않는다. 귀속 방식이 소스마다 다르기 때문이다
(MES·IQC 는 금형번호 열, PQC 는 조인).

```python
class Row(BaseModel):
    source_file: str
    sheet: str
    row_no: int                  # 원본 행 번호 (추적용)
    values: dict[str, str | None]   # field → 셀 값(정규화 전 원문)
```

### DB 스키마

```sql
-- 처리 이력. 배치 전체를 다시 돌지 여부를 판정한다.
ingested_file(path PK, content_hash, stage, processed_at,
              status, error, row_count)

-- 양식 해석 결과. 단계당 몇 개뿐.
sheet_mapping(id PK, stage, sheet_name, layout_json,
              created_at, source_path)
-- 조회는 (stage, sheet_name) 으로 걸러 created_at DESC 순으로 앵커를 대조하고,
-- 처음 일치하는 것을 쓴다. 양식이 바뀌면 새 행이 쌓이고 옛 행은 남는다 —
-- "언제 양식이 바뀌었고 그때 어떻게 해석했는가" 가 추출값을 의심할 때
-- 유일한 근거이기 때문이다.

-- 배치 실행 요약. 조인 손실을 드러내는 자리.
ingest_run(id PK, started_at, finished_at, status,
           mold_count, iqc_matched, pqc_matched,
           pqc_ambiguous, pqc_unmatched, orphan_mold_count, error)

-- 아래 5개는 대시보드 스키마와 1:1 대응한다. 배치마다 전체 교체된다.
mold(mold_no PK, status, line, machine, shot_count,
     total_installs, total_production, first_installed_at,
     installed_at, latest_defect_rate, source_file, updated_at)

mold_design(mold_no PK, angle_deg, height_mm, step_mm,
            overall_mm, plate_height_mm, plate_width_mm,
            source_file, updated_at)

mold_stage(mold_no, stage, status, error, items_json,
           source_file, updated_at, PK(mold_no, stage))

production_run(mold_no, install_seq, line, machine,
               started_at, ended_at, grind_result, defect_rate,
               defects_json, source_file, updated_at,
               PK(mold_no, install_seq))
```

`source_file` 을 모든 테이블에 두는 이유는 `SourceRef` 를 실제로 채우기 위해서다 — 값이
이상할 때 어느 파일에서 왔는지 되짚을 수 없으면 대시보드 전체를 신뢰할 수 없다.

**`mold_stage` 에 행이 없는 것이 곧 `missing` 이다.** 별도로 `status="missing"` 행을 만들지
않는다. `query.py` 가 5단계를 순회하며 행이 없으면 `missing` 을 채운다.

## 에러 처리

| 실패 | 처리 | 근거 |
|---|---|---|
| **MES 파일 없음/실패** | **배치 전체 중단**, 이전 DB 상태 유지 | 마스터가 없으면 금형 목록을 만들 수 없다. 부분 갱신은 옛 금형과 새 부속정보가 섞인 상태를 만든다 |
| **파일이 열려 있음(사람이 편집 중)** | 배치 건너뛰고 **이력에 남기지 않음** → 다음 회차 재시도 | 실무에서 가장 흔하다. 실패로 기록하면 영영 읽히지 않는다 |
| IQC/PQC 파일 열기 실패 | 그 단계만 `error`, 나머지는 진행 | 부속 정보 하나가 없다고 금형 목록을 버릴 이유가 없다 |
| 에이전트가 `submit_layout` 을 못 부름 | 그 파일 `error` | recursion 초과 등 |
| 앵커는 맞는데 파싱 결과가 이상 | **캐시 무효화 → 에이전트 1회 재실행** → 그래도 실패면 `error` | 헤더는 그대로인데 값 형식만 바뀐 경우 |
| 금형번호가 빈 행 | 그 행만 건너뜀 | 소계행·빈 행은 정상이다 |
| **PQC 다중 매칭** | 붙이지 않음, `pqc_ambiguous` 증가 | 틀린 금형에 붙이느니 빠뜨린다 |
| **PQC 무매칭** | 붙이지 않음, `pqc_unmatched` 증가 | 동일 |
| **MES 에 없는 금형이 IQC 에 등장** | 넣지 않음, `orphan_mold_count` 증가 | MES 가 마스터다. 다만 조용히 버리지 않는다 |
| 숫자여야 할 칸에 문자 | 그 필드만 `None` → 대시보드 `—` | `null` 과 `0` 을 구분하는 대시보드 원칙 그대로 |
| DB 쓰기 예외 | 트랜잭션 롤백 | 반쯤 교체된 상태를 만들지 않는다 |

**모든 손실은 `ingest_run` 에 건수로 남고 `GET /api/ingest/status` 로 보인다.** 조용히 빠지는
데이터가 없어야 한다 — 특히 조인 손실은 화면만 봐서는 절대 알 수 없다.

`join.py` 와 `parser.py` 테스트가 전체의 절반 이상이어야 한다.

**`join.py` 가 반드시 다뤄야 할 경우**:
- 시간이 `datetime` / 엑셀 직렬값 / 문자열로 올 때 모두 같은 키가 나오는가
- 날짜 형식 `2026.07.01` / `2026-07-01` / `datetime` 이 모두 같은 키가 되는가
- 다중 매칭 시 **붙이지 않고** 카운트가 오르는가
- 무매칭 시 **붙이지 않고** 카운트가 오르는가
- 호기/공정의 공백·대소문자 차이가 매칭을 막지 않는가

**`parser.py` 가 반드시 다뤄야 할 경우**:
- 표 하나 / 표 여러 개
- summary 표를 레코드로 파싱하지 않는가
- 멀티헤더 결합 라벨
- 빈 행 / 소계 행 / "합계" 행
- 타입 불일치 → 그 필드만 `None` 인가
- `#` 접두사 정규화

## 구현 단계

전부 한 PR 에 넣으면 실제 엑셀을 처음 보는 순간까지 아무것도 검증되지 않는다. 위험이 가장 큰
것부터 얇게 세로로 자른다.

| 단계 | 범위 | 격리되는 위험 |
|---|---|---|
| **1** | 수동 트리거 + **MES + IQC** + DB + 대시보드 연결 | 에이전트가 실물 양식을 읽어내는가 |
| **2** | **PQC 조인** | 시간 기반 조인이 실제로 맞는가 |
| **3** | 자동 폴링 + 나머지 단계(설계/설치/AI복검) + summary 대조 검증 | 운영 중 견디는가 |
| **4** | 마스터 엑셀 출력 | — |

**1단계의 최소 단위가 MES + IQC 인 이유**: MES 없이는 금형 목록조차 없어 화면이 비어 있다.
IQC 를 함께 넣어야 "금형에 부속 정보가 붙는다"는 것이 검증된다.

**PQC 를 2단계로 미루는 이유**: 조인은 다른 종류의 위험이다. 1단계에서 양식 해석 문제와
조인 문제를 동시에 디버깅하면 어느 쪽이 원인인지 가려내기 어렵다.

### 1단계 상세 범위

**포함**: `schemas` · `scanner` · `registry` · `layout` · `discover` · `parser` · `assemble` ·
`store` · `pipeline`, `POST /api/ingest/run`, `GET /api/ingest/status`, `query.py` 를 DB 로 전환,
MES + IQC 폴더, **대시보드 데이터 계약 변경**(아래)

**제외**: `join.py`(2단계) · 자동 폴링(3단계) · 나머지 3개 단계 폴더(3단계) · 마스터 엑셀(4단계)

`sample_data.py` 는 삭제하지 않고 **테스트 픽스처 겸 시드**로 강등한다. 빈 DB 로 시작해도 화면을
확인할 수 있어야 한다.

MES + IQC 만 적재되면 나머지 3개 탭은 `missing` 으로 뜬다 — 대시보드가 이미 그 상태를 처리하므로
새로 만들 UI 가 없다.

## 대시보드 데이터 계약을 고쳐야 한다

MES 가 사용상태와 불량율을 주는 것은 확인됐다. 그러나 **사용 타수·총 설치 횟수·총 생산 수량이
MES 에 있는지는 미확인**이고, 현재 계약은 이 셋을 필수로 잡고 있다.

```python
class MoldSummary(BaseModel):
    shot_count: int         # 0 을 넣으면 "신품" 이라는 거짓말이 된다
    total_production: int
class CumulativeHistory(BaseModel):
    total_installs: int
    total_production: int
class CurrentState(BaseModel):
    shot_count: int
```

0 으로 채우면 대시보드가 스스로 세운 원칙 — **"0회(신품)"와 "미상(추출 실패)"을 구분한다** —
을 정면으로 위반한다. 화면에는 `0` 이 뜨는데 실제로는 모르는 값이다.

**고칠 것** (백엔드 `schemas.py` + 프론트 `types/mold.ts` 를 **반드시 함께**):

| 필드 | 현재 | 변경 |
|---|---|---|
| `MoldSummary.shot_count` | `int` | `int \| None` |
| `MoldSummary.total_production` | `int` | `int \| None` |
| `CumulativeHistory.total_installs` | `int` | `int \| None` |
| `CumulativeHistory.total_production` | `int` | `int \| None` |
| `CurrentState.shot_count` | `int` | `int \| None` |

표시 함수(`fmtNumber`)가 이미 `null → —` 를 처리하므로 화면 코드 변경은 최소다.

**`MoldStatus` 에 `unknown` 을 추가하지는 않는다** — MES 가 마스터이고 사용 상태를 주므로,
대시보드에 있는 금형은 항상 상태를 가진다.

## 설정 (`.env` 단일 출처)

`CLAUDE.md` 규칙에 따라 `Settings` 필드와 `backend/.env.example` 에 함께 넣는다.

```
INGEST_ROOT=./data/uploads
INGEST_STAGE_DIRS=MES:mes,IQC:iqc,PQC:pqc,설계:design,설치:install,AI복검:ai_recheck
MOLDS_DB_PATH=./molds.db
MASTER_XLSX_PATH=./data/관리자/금형현황.xlsx
INGEST_POLL_SECONDS=0          # 0 = 자동 감시 끔 (1단계는 수동 트리거만)
```

읽기 범위를 설정으로 두지 않는다. 에이전트는 도구로 필요한 범위를 스스로 읽고, 앵커 대조는
앵커가 지목한 셀만 직접 읽는다 — 고정된 스캔 창을 두면 그 밖에 있는 표와 앵커를 영영 못 본다.

## 확인이 필요한 가정

구현 중 실물과 다르다고 밝혀지면 스펙을 고쳐야 하는 항목이다.

1. **MES 와 PQC 의 `(날짜, 공정, 호기, 시간)` 이 실제로 같은 값이다.** 사용자가 "MES 문서 내에도
   동일하게 있다" 고 확인했으나, 시간 정밀도(분 단위)가 실제로 맞는지는 실물로 검증해야 한다.
   어긋나면 무매칭이 대량 발생한다 — `ingest_run.pqc_unmatched` 가 그 신호다.
2. **MES 는 전체 이력을 담고 있고, 롤링 윈도우로 잘려나가지 않는다.** 만약 최근 N일치만 남기고
   과거가 잘린다면, 전체 교체 방식이 과거 이력을 지운다. 배치마다 금형·생산이력 건수를
   `ingest_run` 에 남겨 급감을 감지할 수 있게 한다.
3. **금형번호는 `RX28312` 형태이고, IQC 이력표의 `#RX41194` 는 `#` 만 떼면 같은 식별자다.**
   (사용자 확인 완료. 대소문자만 다른 별개 금형이 존재하면 `upper()` 가 잘못 병합한다.)
4. **부서별 양식은 대체로 고정이고, 변경은 예외적이다.**
5. **한 파일의 시트 전체를 메모리에 올릴 수 있다.** MES 가 수천 행이면 문제없다. 수만 행이 되면
   분할 읽기가 필요하다.
6. IQC 의 "유형1 / 유형2" 가 무엇을 가리키는지 아직 모른다 — summary 표라 건너뛰므로 당장은
   막히지 않는다.
7. **PQC 불량 이력을 `mold_stage[pqc].items` 에 시간순 나열하는 것으로 충분하다.** 건수가 많으면
   표 형태가 필요할 수 있다 — 화면 변경이므로 실물을 보고 판단한다.
8. 선행 스펙의 가정 1(금형 상태 어휘 4종)과 2(생산결과 한 행 = 설치 1회분) 는 **여전히 미검증**이다.
   MES 를 처음 읽는 1단계에서 확인된다.

## 선행 스펙에서 고칠 것

- 가정 3의 금형번호 형식 예시 `M-1024` → 실제 `RX28312`
- `sample_data.py` 의 금형번호를 실제 형식으로 교체 (테스트가 이 값에 의존하므로 함께 수정)
- 위 데이터 계약 변경 반영

## 설계가 바뀐 경위

기록으로 남긴다 — 같은 실수를 반복하지 않기 위해서다.

1. **단발 LLM 호출 → ReAct 에이전트.**
   처음에는 "헤더 부근 격자를 한 번 보여주고 매핑을 받는다"로 설계했다. 사용자가 "한 시트 안에도
   여러 개의 테이블 구조로 작성한 경우가 많다"고 지적했고, 실물 IQC 파일이 그것을 확인해줬다
   (시트 하나에 표 4개). 탐색이 필요한 문제였다.

2. **헤더 행 해시 → 에이전트가 지목한 앵커.**
   "헤더 행을 해시해 지문을 만든다"는 두 번 무너졌다. 헤더 위치를 모르는 상태에서 헤더를 해시할
   수 없었고(닭과 달걀), 표가 여러 개면 헤더도 여러 개였다.

3. **파일 중심 → 금형 중심 (MES 마스터).**
   초안은 "어느 파일에서든 처음 등장한 금형을 생성"하는 구조였다. 사용자가 MES 를 마스터로
   지정하면서 금형 목록의 출처가 단일화됐다. 이로써 "IQC 로만 발견된 금형의 상태를 알 수 없다"
   는 초안의 결함이 해소됐고, 대신 "MES 에 없는 금형이 IQC 에 있으면?"(고아 데이터)이라는
   반대 방향의 문제가 생겨 `orphan_mold_count` 로 드러내기로 했다.

4. **병합 규칙 → 전체 교체.**
   초안은 `(금형, 단계)` 최신 승리와 `(금형, 회차)` 누적이라는 병합 규칙을 뒀다. MES 가 계속
   덮어쓰기되고 매번 전체 재처리한다는 것이 확인되면서 이 규칙이 불필요해졌다 — 오히려 upsert
   만 하면 MES 에서 사라진 금형이 유령으로 남는다.

5. **`parser` 출력이 `MoldRecord` → `Row`.**
   PQC 에 금형번호가 없다는 사실이 드러나면서, 금형 귀속을 파싱에서 분리해야 했다. IQC 는
   금형번호 열로, PQC 는 조인으로 귀속되는데 그 차이가 한 모듈에 섞이면 읽을 수 없다.
