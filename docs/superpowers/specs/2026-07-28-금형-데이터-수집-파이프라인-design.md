# 금형 데이터 수집 파이프라인 설계

- 날짜: 2026-07-28
- 배경: 대시보드 화면(서브프로젝트 ①, PR #4)이 머지됐다. 지금 대시보드가 보여주는 데이터는
  `backend/app/molds/sample_data.py` 의 하드코딩 샘플이다. 이 문서는 그 자리를 **실제 엑셀 파일에서
  추출한 데이터**로 채우는 파이프라인을 설계한다.
- 선행 문서: `docs/superpowers/specs/2026-07-27-금형-대시보드-design.md`

## 요구사항 (사용자 원문)

1. IQC, PQC 등 각 단계별로 각 부서 사람들이 자신들이 정리한 엑셀 파일을 특정 폴더에 계속 업로드한다.
2. 각 문서들의 내용을 LLM이 이해해서 대시보드에 표현 가능한 내용들을 추출한다.
3. 최종 결과 내용을 하나의 마스터 엑셀 파일에 정리해서 누적 관리한다. 관리자 폴더에 계속 업데이트한다.

## 전체 그림에서의 위치

선행 스펙은 전체를 4개 서브프로젝트로 나눴다. 이 문서는 그중 ②③④를 **하나의 파이프라인**으로
다룬다 — 세 조각의 계약이 서로 맞물려 있어 따로 설계하면 어긋나기 때문이다.

| # | 서브프로젝트 | 상태 |
|---|---|---|
| 1 | 대시보드 화면 | 완료 (PR #4) |
| 2 | 파일 자동 적재 | **이 문서** |
| 3 | AI 추출·정규화 | **이 문서** |
| 4 | 영속화·조회 | **이 문서** |

다만 **구현은 한 번에 하지 않는다.** 아래 "구현 단계" 절 참고.

## 목표

- 부서가 정해진 폴더에 엑셀을 올리면, 그 내용이 대시보드에 나타난다.
- 사람이 파일 양식을 바꿔도 시스템이 스스로 알아채고 재해석한다.
- **같은 파일을 다시 처리하면 항상 같은 값이 나온다.**
- 추출에 실패한 단계는 대시보드에 사유와 함께 `error` 로 표시된다.
- 금형별 현황 요약을 마스터 엑셀로 내보내 관리자 폴더에 갱신한다.

## 비목표

- 대시보드에서의 데이터 편집 (읽기 전용 유지)
- 추출 결과 승인/검토 큐 화면 — 실패는 `error` 표시로 충분하다는 결정
- 원본 엑셀 파일 열기/다운로드 UI
- 사람이 마스터 엑셀을 고치면 그 값이 시스템으로 역류하는 양방향 동기화
- 실시간성 (분 단위 지연 허용)

## 확정된 결정과 근거

브레인스토밍에서 사용자와 함께 정한 것들이다. 각 결정의 **근거**를 함께 적는다 —
근거가 바뀌면 결정도 다시 봐야 하기 때문이다.

### 1. 마스터 엑셀은 산출물, DB가 원본

`molds.db` (SQLite) 가 유일한 원본이고, 마스터 엑셀은 거기서 생성해 관리자 폴더에 갱신한다.

**근거**: 엑셀을 원본으로 삼으면 누군가 파일을 열어둔 동안 쓰기가 막히고, 파일이 손상되면
전체 이력을 잃는다. 산출물로 두면 잠기거나 깨져도 재생성하면 복구된다.

### 2. `molds.db` 는 기존 `app.db` 와 별도 파일

**근거**: `app.db` 는 LangGraph 체크포인터가 채팅 턴마다 쓴다. 같은 파일에 수집 워커가 쓰면
SQLite 쓰기 락을 두고 경합해 `database is locked` 가 나거나 양쪽이 느려진다.

### 3. 구조 이해는 LLM 에이전트, 값 추출은 순수 파이썬

| 층 | 방식 | 보장 |
|---|---|---|
| 구조 이해 | ReAct 에이전트 + 엑셀 도구 | **유연성** — 어떤 양식이 와도 이해한다 |
| 값 추출 | 순수 파이썬 함수 | **일관성** — 같은 파일은 항상 같은 값 |

**근거**: 값 추출까지 LLM 에 맡기면 같은 대장을 어제 읽었을 때 8,412, 오늘 8,142 가 나올 수
있다. 그게 바로 "일관되지 않은 추출"이다. 구조는 한 번 이해하면 되지만 값은 매번 정확해야 한다.
또한 300행짜리 대장을 매번 LLM 컨텍스트에 넣는 것은 사내 LLM 에서 물리적으로 불가능할 수 있다.

### 4. 캐시 무효화는 에이전트가 지목한 앵커로

**근거**: 처음에는 "헤더 행 텍스트를 해시"로 설계했으나 두 번 무너졌다.
(a) 헤더가 몇 번째 행인지 모르는 상태에서 헤더를 해시할 수 없다(닭과 달걀).
(b) 한 시트에 표가 여러 개면 헤더 행도 여러 개다.
양식을 이해한 주체가 "무엇이 같으면 같은 양식인가"를 가장 잘 안다 — 그래서 에이전트가
`anchors` 를 직접 제출한다.

### 5. 실패는 대시보드 `error` 표시로 끝낸다

검토 큐 화면을 만들지 않는다.

**근거**: 대시보드가 이미 `stage_status: "error"` 와 `StagePanel.error` 를 렌더한다.
새 UI 없이 곧바로 동작하고, 사람이 원본 엑셀을 고쳐 다시 올리면 내용 해시가 바뀌어 자동으로
재처리된다.

### 6. xlwings 전용 (openpyxl 사용 불가)

**근거**: 사용자 환경 제약. `backend/app/excel/workbook.py` 가 이미 이 제약 위에 설계돼 있다
("openpyxl 을 못 쓰는 환경을 위해 실제 Excel(COM) 을 구동한다").

**따라오는 제약**:
- 파일 하나 읽는 데 EXCEL.EXE 가 뜬다 (수 초) → **파일당 한 번만 열어서 다 끝낸다**
- COM 스레드 제약 → **병렬 처리 불가, 순차 큐**
- FastAPI 이벤트 루프를 막으면 안 됨 → **백그라운드 워커**
- 현재 `workbook.py` 는 읽기 전용 → 마스터 엑셀 쓰기 경로를 같은 스레드 규약 위에 추가해야 함

부수 효과(긍정): Excel 이 직접 여니 `.xls`, 매크로 파일, 수식 결과까지 읽힌다.

## 실물 IQC 파일에서 확인된 구조

사용자가 제공한 실제 IQC 파일 sheet1 의 구조다. 설계를 두 번 고치게 만든 근거라서 남긴다.

```
sheet1
├─ 카테고리 A: "Stack 금형 측정 이력"
│   ├─ summary 표   유형1(양극 성형/음극 성형/음극 절단/소계)
│   │               유형2(상면 성형/하면 성형/상면 절단/하면 절단/소계/총계)
│   └─ 상세 표      No │ 모델 │ 기종 │ 1차 명칭 │ 관리 번호 │ 업체 │ 26년 측정일
│                   1  │ 양극 성형 │ H104 │ 1차 양극 Notching │ #RX41194 │ 일신 │ …
│
└─ 카테고리 B: "Stack H104 금형 측정 대장"
    ├─ summary 표   구분 │ 내용(검사 수량/불량 수량/불량률) │ 1월 │ 2월 │ … │ 합계
    └─ 상세 표      2단 멀티헤더
                    행13: No │ 입고시간 │ 금형번호 │   성형부    │   절단부
                    행14:    │         │         │ 정극성형│부극성형│양극절단│음극절단
                    … 측정자 │ 조립자 │ 출고시간 │ 측정결과 PUNCH │ 측정결과 DIE │ 연마자 │ NG 사진
                    행15: 1 │2026.07.01│ RX28312 │ - │ - │ 체크 │ - │ 홍길동 │ 홍길동 │ … │ A │ A │ 구군 │ -
```

이 구조가 확인해준 것:

- **에이전트 방식이 필요하다.** 시트 하나에 표 4개 + 멀티헤더 + 월별 피벗. 단발 프롬프트로는 안 된다.
- **유연 스키마가 옳았다.** 측정자·조립자·연마자·측정결과 PUNCH/DIE·NG 사진은 미리 고정 필드로
  잡을 수 있는 항목이 아니었다. 헤더 텍스트가 그대로 `StageItem.label` 이 된다.
- **summary 를 detail 과 구분해야 한다.** 구분하지 않으면 "소계" 를 금형번호로 읽는 사고가 난다.

## 데이터 계약

### 레이아웃 스키마 (에이전트가 제출)

```python
class ColumnMap(BaseModel):
    field: str      # 고정 단계면 정해진 키, 유연 단계면 헤더 텍스트 그대로
                    # 멀티헤더는 결합 라벨: "성형부/정극 성형"
    column: str     # "C"

class KeyValueItem(BaseModel):
    """표가 아닌 블록. 라벨 옆/아래에 값이 있는 형태(상단 기본정보 등)."""
    field: str
    value_cell: str                  # "D5"
    label_cell: str | None = None    # 어느 라벨을 보고 판단했는지 (근거)

class TableBlock(BaseModel):
    name: str                              # "금형 측정 대장 — 상세"
    role: Literal["detail", "summary"]     # summary 는 금형 레코드로 파싱하지 않는다
    category: str | None = None            # "측정 이력" / "금형 측정 대장"
    header_rows: list[int]                 # [13, 14] — 멀티헤더는 여러 행
    data_start_row: int
    data_end_row: int | None = None        # None = 빈 행 만날 때까지
    mold_no_column: str | None = None      # None 이면 시트 전역 금형번호 사용
    columns: list[ColumnMap]

class AnchorCheck(BaseModel):
    """'여기에 이 텍스트가 있으면 같은 양식이다' — 에이전트가 직접 지목한다."""
    cell: str       # "B4"
    text: str       # "금형번호"

class SheetLayout(BaseModel):
    sheet_name: str
    scope: Literal["per_row", "single_mold"]
    sheet_mold_no_cell: str | None = None   # scope == "single_mold" 일 때
    key_values: list[KeyValueItem] = []
    tables: list[TableBlock] = []
    anchors: list[AnchorCheck]
    notes: str | None = None                # 에이전트가 애매하다고 판단한 점 (로그용)
```

### 금형번호 정규화

**반드시 한 곳에만 둔다.** 두 군데서 다르게 정규화되면 같은 금형이 둘로 갈라진다.

```python
def normalize_mold_no(raw: str) -> str:
    """'#RX41194' → 'RX41194',  ' rx28312 ' → 'RX28312'"""
    return raw.strip().lstrip("#").strip().upper()
```

원본 문자열은 `source_file` 과 함께 보존해 추적 가능하게 둔다.

### DB 스키마

```sql
-- 처리 이력. 내용 해시가 같으면 다시 읽지 않는다.
ingested_file(path PK, content_hash, stage, processed_at,
              status, error, record_count, skipped_count)

-- 양식 해석 결과. 단계당 몇 개뿐.
sheet_mapping(id PK, stage, sheet_name, layout_json,
              created_at, source_path)
-- 조회는 (stage, sheet_name) 으로 걸러 created_at DESC 순으로 앵커를 대조하고,
-- 처음 일치하는 것을 쓴다. 양식이 바뀌면 새 행이 쌓이고 옛 행은 남는다 —
-- 지우지 않는 이유는 "언제 양식이 바뀌었고 그때 어떻게 해석했는가" 가
-- 추출값을 의심할 때 유일한 근거이기 때문이다. 단계당 몇 개 수준이라
-- 순회 비용은 무시할 수 있다.

-- 아래 5개는 대시보드 스키마와 1:1 대응한다.
mold(mold_no PK, status, line, machine, shot_count,
     total_installs, total_production, first_installed_at,
     installed_at, updated_at)

mold_design(mold_no PK, angle_deg, height_mm, step_mm,
            overall_mm, plate_height_mm, plate_width_mm,
            source_file, updated_at)

mold_stage(mold_no, stage, status, error, items_json,
           source_file, updated_at, PK(mold_no, stage))

production_run(mold_no, install_seq, line, machine,
               started_at, ended_at, grind_result, defect_rate,
               defects_json, source_file, updated_at,
               PK(mold_no, install_seq))
```

`source_file` 을 모든 테이블에 두는 이유는 `SourceRef` 를 실제로 채우기 위해서다 — 값이
이상할 때 어느 파일에서 왔는지 되짚을 수 없으면 대시보드 전체를 신뢰할 수 없다.

**`mold_stage` 에 행이 없는 것이 곧 `missing` 이다.** 별도로 `status="missing"` 행을 만들지
않는다. `query.py` 가 5단계 전부를 순회하며 행이 없으면 `missing` 을 채운다 — 그래야 "아직
그 단계 파일이 안 올라왔다" 와 "올라왔는데 비어 있다" 를 DB 에 억지로 구분해 넣지 않아도 된다.

### 병합 규칙

**`(금형번호, 단계)` 단위로 최신 파일이 이긴다.** 단계가 다르면 충돌 자체가 없다 —
IQC 파일은 `mold_stage` 의 iqc 행만, 설계 파일은 `mold_design` 만 건드린다.

**예외 하나**: 생산 이력은 `(금형번호, 설치회차)` 로 upsert 누적한다. 7월 대장이 6월 대장을
덮어쓰면 안 된다.

두 규칙 모두 SQL 기본키의 upsert 로 처리된다 — 별도 병합 코드가 필요 없다.

### `submit_layout` 을 도구로 만드는 이유

에이전트가 마지막에 JSON 을 텍스트로 뱉게 하면 파싱이 깨지기 쉽다. 도구 인자로 받으면
Pydantic 이 검증하고, 잘못 채우면 도구 에러가 나서 에이전트가 스스로 고쳐 다시 제출한다.
LangGraph 의 `ToolNode` 가 이 왕복을 이미 처리한다.

### 모듈

```
backend/app/ingest/
  schemas.py    SheetLayout, TableBlock, KeyValueItem, AnchorCheck, MoldRecord
  scanner.py    폴더 훑기 → (경로, 단계, 내용해시)       표준 라이브러리만
  registry.py   molds.db 의 ingested_file / sheet_mapping 접근
  layout.py     앵커 검증 → 캐시 hit/miss 판정           ★ 순수 함수
  discover.py   ReAct 에이전트 + submit_layout → SheetLayout
  parser.py     격자 + SheetLayout → list[MoldRecord]    ★ 순수 함수
  store.py      MoldRecord → molds.db upsert
  pipeline.py   위를 엮어 파일 하나를 처리
  worker.py     단일 스레드 폴링 큐                       (2단계)
  export.py     molds.db → 마스터.xlsx                    (3단계)

backend/app/api/ingest.py
  POST /api/ingest/run       수동 트리거
  GET  /api/ingest/status    최근 처리 이력
```

의존 방향은 한쪽으로만 흐른다:

```
parser.py   → schemas 만          (LLM✗ COM✗ DB✗ 파일✗)
layout.py   → schemas 만          (동일)
scanner.py  → 표준 라이브러리만
discover.py → schemas, excel.tools, llm
store.py    → schemas, sqlite3
pipeline.py → 전부                ← 조립은 여기서만
```

**`parser.py` 와 `layout.py` 가 순수 함수인 것이 이 설계의 값어치다.** 틀릴 위험이 가장 큰
로직인데, 엑셀도 LLM 도 DB 도 없이 격자 리터럴만으로 전부 테스트할 수 있다. "왜 이 값이 이렇게
나왔지" 를 물을 때 그 격자와 레이아웃만 있으면 재현된다.

## 에러 처리

| 실패 | 처리 | 근거 |
|---|---|---|
| **파일이 열려 있음(사람이 편집 중)** | 건너뛰고 **이력에 남기지 않음** → 다음 회차 재시도 | 실무에서 가장 흔하다. 실패로 기록하면 영영 읽히지 않는다 |
| 워크북 열기 실패(손상) | `status=error`, 사유 기록 | 사람이 고쳐 올리면 해시가 바뀌어 자동 재시도 |
| 에이전트가 `submit_layout` 을 못 부름 | 파일 `error` | recursion 초과 등 |
| `submit_layout` 인자 검증 실패 반복 | 파일 `error` | |
| 앵커는 맞는데 파싱 결과가 이상 | **캐시 무효화 → 에이전트 1회 재실행** → 그래도 실패면 `error` | 헤더는 그대로인데 값 형식만 바뀐 경우 |
| 금형번호가 빈 행 | 그 행만 건너뜀, `skipped_count` 증가 | 소계행·빈 행은 정상이다 |
| 숫자여야 할 칸에 문자 | 그 필드만 `None` → 대시보드 `—` | `null` 과 `0` 을 구분하는 대시보드 원칙 그대로 |
| DB 쓰기 예외 | 트랜잭션 롤백, 파일 `error` | 반쯤 들어간 상태를 만들지 않는다 |

두 원칙:

- **한 파일의 실패가 다른 파일을 막지 않는다.** 큐는 계속 돈다.
- **한 행의 실패가 파일 전체를 버리지 않는다.** 10건 중 1건이 깨졌으면 9건은 반영하고
  `record_count=9, skipped_count=1` 을 남긴다. 오타 하나 때문에 대장 전체가 안 들어오는 게 더
  나쁘다 — 다만 **몇 건이 빠졌는지는 반드시 노출한다.** 조용히 9건만 들어가는 것이 최악이다.

## 구현 단계

전부 한 PR 에 넣으면 실제 엑셀을 처음 보는 순간까지 아무것도 검증되지 않는다. 위험이 가장 큰
것부터 얇게 세로로 자른다.

| 단계 | 범위 | 이걸로 알게 되는 것 |
|---|---|---|
| **1** | 수동 트리거 + **IQC 폴더 하나** + DB + 대시보드 연결 | **실물 양식을 에이전트가 읽어내는가.** 스펙의 가정이 맞는가 |

## 설정 (`.env` 단일 출처)

`CLAUDE.md` 규칙에 따라 `Settings` 필드와 `backend/.env.example` 에 함께 넣는다.

```
INGEST_ROOT=./data/uploads
INGEST_STAGE_DIRS=IQC:iqc,PQC:pqc,설계:design,설치:install,AI복검:ai_recheck
MOLDS_DB_PATH=./molds.db
```

읽기 범위를 설정으로 두지 않는다. 에이전트는 도구로 필요한 범위를 스스로 읽고, 앵커 대조는
앵커가 지목한 셀만 직접 읽는다 — 고정된 스캔 창(예: 상위 40행)을 두면 그 밖에 있는 표와 앵커를
영영 못 본다.

`INGEST_STAGE_DIRS` 로 폴더명↔단계를 매핑하므로, 나중에 공유드라이브로 옮기거나 폴더명을 바꿔도
코드는 그대로다.

## 확인이 필요한 가정

구현 중 실물과 다르다고 밝혀지면 스펙을 고쳐야 하는 항목이다.

1. **금형번호는 `RX28312` 형태이고, 이력 테이블의 `#RX41194` 는 `#` 만 떼면 같은 식별자다.**
   (사용자 확인 완료. 대소문자가 섞여 들어오는 경우 `upper()` 로 합치는 것은 아직 미검증 —
   대소문자만 다른 별개 금형이 존재하면 잘못 병합된다.)
2. **부서별 양식은 대체로 고정이고, 변경은 예외적이다.** 매 파일 양식이 다르면 에이전트 호출이
   파일 수에 비례해 비용·시간이 문제가 된다.
3. **한 파일의 시트 전체를 메모리에 올릴 수 있다.** 수만 행짜리 시트가 오면 분할 읽기가 필요하다.
4. IQC 의 "유형1 / 유형2" 가 무엇을 가리키는지 아직 모른다 — summary 표라 1단계에서는 건너뛰므로
   당장은 막히지 않는다.
5. 선행 스펙의 가정 1(금형 상태 어휘 4종)과 2(생산결과 한 행 = 설치 1회분) 는 **여전히 미검증**이다.
   설치 단계 파일을 처음 보는 2단계에서 확인된다.

## 대시보드 데이터 계약을 고쳐야 한다 (셀프 리뷰에서 발견)

**1단계는 IQC 만 적재한다. 그런데 IQC 파일에는 금형의 상태·타수·생산량이 없다.**
현재 대시보드 계약은 이 세 필드를 필수로 잡고 있어서, IQC 로만 발견된 금형을 표현할 수 없다.

```python
class MoldSummary(BaseModel):
    status: MoldStatus      # ← 필수. IQC 만으로는 알 수 없다
    shot_count: int         # ← 필수. 0 을 넣으면 "신품" 이라는 거짓말이 된다
    total_production: int   # ← 동일

class CumulativeHistory(BaseModel):
    total_installs: int     # ← 동일
    total_production: int   # ← 동일
```

0 으로 채우면 대시보드가 스스로 세운 원칙 — **"0 회(신품)"와 "미상(추출 실패)"을 구분한다** —
을 정면으로 위반한다. 화면에는 `0` 이 뜨는데 실제로는 모르는 값이다.

**고칠 것** (백엔드 `schemas.py` + 프론트 `types/mold.ts` 를 **반드시 함께**):

| 필드 | 현재 | 변경 |
|---|---|---|
| `MoldStatus` | `in_use \| standby \| repair \| retired` | `+ unknown` |
| `MoldSummary.shot_count` | `int` | `int \| None` |
| `MoldSummary.total_production` | `int` | `int \| None` |
| `CumulativeHistory.total_installs` | `int` | `int \| None` |
| `CumulativeHistory.total_production` | `int` | `int \| None` |
| `CurrentState.shot_count` | `int` | `int \| None` |

프론트는 `STATUS_LABEL` 에 `unknown: "미상"` 을 추가한다. 표시 함수(`fmtNumber`)는 이미
`null → —` 를 처리하므로 화면 코드 변경은 최소다. `filter_options().statuses` 는 고정 5종이 된다.

`unknown` 을 필터 드롭다운에 노출할지는 열어둔다 — 노출하면 "아직 설치 정보가 안 들어온 금형"
을 찾는 유용한 조회가 되지만, 상태 어휘가 도메인 용어가 아닌 시스템 사정을 드러내는 면도 있다.
구현 계획에서 결정한다.

## 설계 중 두 번 바뀐 지점

기록으로 남긴다 — 같은 실수를 반복하지 않기 위해서다.

1. **단발 LLM 호출 → ReAct 에이전트.**
   처음에는 "헤더 부근 격자를 한 번 보여주고 매핑을 받는다"로 설계했다. 사용자가 "한 시트 안에도
   여러 개의 테이블 구조로 작성한 경우가 많다"고 지적했고, 실물 IQC 파일이 그것을 확인해줬다
   (시트 하나에 표 4개). 탐색이 필요한 문제였다.

2. **헤더 행 해시 → 에이전트가 지목한 앵커.**
   "헤더 행을 해시해 지문을 만든다"는 두 번 무너졌다. 헤더 위치를 모르는 상태에서 헤더를 해시할
   수 없었고(닭과 달걀), 표가 여러 개면 헤더도 여러 개였다. 양식을 이해한 주체가 무엇이 같으면
   같은 양식인지 가장 잘 안다.
