# 교육자료 2편·3편 설계: 프롬프트·LangGraph / Tool calling

**작성일**: 2026-07-25
**대상 청중**: LLM 활용법을 배우려는 사내 실무자 (개발자 아닌 사람 포함 가능)
**진행 방식**: 따라치기 실습형 — 실습 파일을 직접 실행하며 슬라이드를 따라간다
**전작**: `docs/교육자료/사내LLM연결_LangChain입문.pptx` (1편, 12슬라이드) — `backend/examples/connect_llm.py` 와 짝

## 배경 및 목표

1편은 "사내 LLM에 연결하기"까지 다뤘고, 마지막 슬라이드는 "다음 단계 → 주제 2: 디버그 로깅"을 예고했다. 그러나 디버그 로깅은 이번 시리즈에서 **다루지 않기로 결정**했다(실무자 대상 교육으로는 우선순위가 낮음). 대신 실무자가 LLM을 실제로 "부려먹는" 데 필요한 두 가지를 2편·3편으로 만든다:

- **2편**: 프롬프트를 어떻게 구성하는지, LangChain과 LangGraph 코드 사용법이 어떻게 다른지
- **3편**: tool-calling 코드 작성 방법과 원리

두 편 모두 1편과 같은 "코드 뜯어보기" 슬라이드 패턴 + 실행 가능한 단일 파일 실습을 유지해 시리즈의 톤을 통일한다.

## 시각 스타일

1편(`사내LLM연결_LangChain입문.pptx`)과 동일한 톤을 유지한다:
- 제목 슬라이드 → AGENDA → 개념 1~2장 → 코드 뜯어보기 ①②③(코드 + 포인트 카드) → 동작원리 다이어그램 1장 → 정리 1장

## 2편: 프롬프트 입력 & LangChain vs LangGraph

### 실습 파일 `backend/examples/prompt_and_graph.py`

`--step N` 인자로 개별 단계 실행, 인자 없으면 전체 순서 실행(공통 골격은 "실습 진행 방식" 절 참조).

| Step | 코드 포인트 | 슬라이드에서 강조 |
|---|---|---|
| 1 | `llm.invoke("자기소개해줘")` — 문자열 하나만 전달 | 역할(System) 지정이 안 됨, 재사용 불가 |
| 2 | `ChatPromptTemplate.from_messages([...])` + `{topic}` 변수 → `\| model` 체인 | "프롬프트 = 템플릿 + 변수". 실무자가 실제로 쓸 형태 |
| 3 | LangChain만으로 멀티턴 — `messages` 리스트에 응답을 손으로 `append` | 불편을 직접 겪게 함: 턴마다 히스토리 관리를 직접 해야 함 |
| 4 | 같은 대화를 `StateGraph` + `MemorySaver`로 — `add_messages` 리듀서가 자동 누적 | "대화의 상태·흐름을 대신 관리해주는 게 LangGraph" |

### "우리 앱은 이렇게" 슬라이드

`backend/app/graph/builder.py`(22줄) + `backend/app/graph/nodes/chat.py`의 `make_chat_node` + `backend/app/prompts.py`의 `CHAT_SYSTEM_PROMPT`를 한 컷에 보여준다 — "지금 배운 걸 실제 프로젝트가 그대로 쓰고 있다"는 확인.

### 정리 슬라이드 핵심 문장

"LangChain은 **모델 호출**을 표준화하고, LangGraph는 **대화의 상태·흐름**을 표준화한다. 한 번 묻고 끝이면 LangChain만으로 충분하고, 여러 턴에 걸친 기억·분기·반복이 필요하면 LangGraph."

## 3편: Tool calling

### 실습 파일 `backend/examples/tool_calling_step_by_step.py`

| Step | 코드 포인트 | 강조 |
|---|---|---|
| 1 | LLM에게 큰 수 곱셈을 도구 없이 시키기 | 틀린 답 → "왜 도구가 필요한가" |
| 2 | `@tool` 데코레이터로 `multiply` 정의 | docstring이 곧 LLM용 설명서 |
| 3 | `model.bind_tools([multiply]).invoke(...)` → `resp.tool_calls` 출력 | **LLM은 함수를 실행하지 않는다 — "부르고 싶다"고 말할 뿐** |
| 4 | 수동 루프: `tool_calls` 파싱 → 실제 파이썬 함수 실행 → `ToolMessage`로 결과를 붙여 재호출 | tool calling의 실제 왕복 원리(10줄 내외) |
| 5 | `create_react_agent(model, [multiply])` 한 줄 | 4단계를 대체하는 이유 |
| 6 | 엑셀 셀 write→read 왕복 (`verify_tool_calling.py`의 `_make_excel_roundtrip_tools` 패턴을 교육용으로 재구성) | "실무 데이터(엑셀)에도 그대로 적용된다" |

Step 6은 xlwings/Excel이 없는 PC에서는 `verify_tool_calling.py`와 동일한 컨벤션으로 `SKIP` 처리한다(새 예외 처리 패턴을 만들지 않고 기존 것을 재사용).

### 다음 단계 예고 슬라이드

"엑셀 분석 에이전트는 이미 설계·사전검증 완료(`verify_tool_calling.py` PASS 기준) — 다음 자료에서 이어감"으로 `docs/superpowers/plans/2026-07-24-excel-analysis-agent.md`와 연결한다.

## 실습 진행 방식 (2편·3편 공통 골격)

```python
def step_1(): ...
def step_2(): ...
...
STEPS = {1: step_1, 2: step_2, ...}

def main():
    args = ...  # --step N 파싱, --backend internal|ollama 지원(1편 connect_llm.py 방식 재사용)
    steps = [STEPS[args.step]] if args.step else STEPS.values()
    for fn in steps:
        print(f"\n{'='*60}\n[Step] {fn.__doc__}\n{'='*60}")
        fn()
```

- 각 스텝 함수의 docstring이 곧 실행 시 출력되는 헤더가 되어, 슬라이드의 "실행 명령 + 기대 출력"과 그대로 대응한다.
- 두 파일 모두 1편 `connect_llm.py`처럼 프레임워크 설정 로딩 없이 `backend/.env`를 직접 읽는 단일 파일로 만든다(추가 의존성 없이 바로 실행 가능해야 하므로).
