2026-08-11 · feat/ingest-phase1 · 이 문서의 예시는 전부 실제 backend/molds.db 에서 뽑은 값이다

이 문서는 앞선 설명(전체 동작 원리와 Excel Agent)의 후속편이다. 앞 문서가 “구조를 어떻게 알아내는가”에 초점을 뒀다면, 이번에는 그렇게 알아낸 구조로 값을 꺼내 데이터베이스에 어떻게 눕히는가, 그리고 엑셀에서 한 줄을 고쳤을 때 그 변화가 DB 어디까지 번지는가를 다룬다. 앞 문서를 안 읽었어도 따라올 수 있게 필요한 배경은 다시 깔았다.

이 페이지 쓰는 법

읽다가 궁금한 게 생기면 “질문 메모” 상자에 적으면 된다. 적는 즉시 이 브라우저에 자동 저장되고, 맨 아래 질문 저장 버튼을 누르면 같은 파일 이름으로 질문이 박힌 사본이 다운로드된다. 그 파일로 원본을 덮어쓴 뒤 Claude 에게 “질문 답해줘”라고 하면 답이 그 자리에 채워진다.

1. 배경 — 엑셀은 왜 그냥 DB 가 될 수 없나

1.1 완전 기초 (아는 사람은 건너뛰어도 좋다)

엑셀 파일도 표이고 데이터베이스 테이블도 표인데, 왜 옮겨 담는 수고를 할까? 세 가지가 다르다.

엑셀 시트DB 테이블
모양한 장에 표가 여러 개, 헤더 2단, 소계행 섞임, 표 밖에 라벨한 테이블 = 한 표. 컬럼이 고정
타입같은 열에 숫자·문자·날짜가 섞임. 정수도 28312.0 으로 옴컬럼마다 타입이 정해짐
질문“불량율 1% 넘는 금형만 보여줘”를 하려면 사람이 눈으로 훑어야 함WHERE latest_defect_rate > 0.01 한 줄

대시보드는 필터·검색·정렬을 밀리초 안에 해야 한다. 그래서 엑셀을 미리 한 번 읽어 질문하기 좋은 모양으로 눕혀두는 것이다. 이 “미리 한 번”이 배치(batch) 이고, 이 문서의 주제다.

알아둘 용어 넷

SQLite — 서버가 없는 파일 하나짜리 데이터베이스. 이 프로젝트의 molds.db 가 그 파일이다.
트랜잭션 — “전부 되거나 전부 안 되거나”를 보장하는 묶음. 중간에 실패하면 시작 전으로 되돌아간다(롤백).
해시(sha256) — 파일 내용을 64자리 지문으로 요약한 값. 내용이 1바이트만 달라도 지문이 완전히 바뀐다.
스냅샷 — 어느 시점의 전체 상태를 통째로 뜬 사진. 이 시스템의 DB 는 “변경 내역”이 아니라 스냅샷이다.

1.2 molds.db 의 8개 테이블 = 두 가족

이 문서를 관통하는 가장 중요한 구분이다. molds.db 안의 테이블은 성격이 정반대인 두 무리로 나뉜다.

이 문서에서 하나만 기억한다면

결과 테이블에는 “수정”이 없다. 배치마다 전부 지우고 새로 넣는다.
엑셀이 원본(source of truth)이고 DB 는 그 사진일 뿐이라, 사진을 고치는 게 아니라 다시 찍는다.

왜 UPDATE/UPSERT 가 아니라 전멸-재생성일까? 관리대장이 마스터이고 매번 전체를 다시 읽으므로, 관리대장에서 사라진 금형은 대시보드에서도 사라져야 하기 때문이다. upsert 만 하면 한 번 들어온 금형이 영원히 남는다 — 유령 금형이다.

질문 메모 “기억/결과” 구분에서 헷갈리는 점이 있으면 적어두세요.

2. 직관 — 언제 · 무엇을 · 어떻게

2.1 언제 도는가

자동으로 돌지 않는다. INGEST_POLL_SECONDS 기본값이 0 이라 사람이 대시보드에서 “수집 실행”을 누를 때만 돈다. 눌렀다고 항상 읽는 것도 아니다 — 세 개의 문지기를 차례로 통과해야 한다.

문지기 ②를 조금 더 보자. 이것이 “변경된 파일이 없어 건너뛰었습니다”의 정체다.

2.2 어떤 파일을 어떤 순서로

파일 이름은 아무 상관이 없다. 어느 폴더에 있느냐가 종류를 정한다. 그리고 그 종류를 읽는 순서가 곧 의존성이다.

2.3 값 하나가 DB 한 칸이 되는 여정

추상적으로 설명하는 대신 실제 셀 하나를 끝까지 따라가 보자. 관리대장 워크북, 시트 이름 #RX39513, 셀 B5 에 들어 있는 날짜 하나다.

같은 여정을 “숫자”로 한 번 더 보면 정규화가 왜 필요한지 드러난다. MES 시트의 설비코드 칸이다.

질문 메모 값 변환 체인에서 “이 단계는 왜 필요하지?” 싶은 곳을 적어두세요.

이 표에서 세 가지를 읽을 수 있다.

  • 3번 구간만 설비가 다르다(_02). 금형이 옮겨 다녔다는 뜻이고, 그래서 구간마다 “그때 그 설비”의 실적이 붙는다. 기준정보의 현재 설비 하나로 뭉뚱그리면 과거 구간이 틀린다.
  • mold.latest_defect_rate(0.007333) = 4번 구간의 값이다. 전체 평균이 아니다.
  • 1번 구간은 4일(07-01~07-04)을 덮는데 defects_json 에는 3일치뿐이다. MES/ 폴더에 2026-07-03 파일이 없기 때문이다. 이 사실은 missing_mes_days 로 화면에 보고된다.
왜 날짜별 원값을 JSON 으로 남기나

불량율 0.012534 하나만 저장하면 “이 수치 어디서 나왔냐”에 답할 수 없다. (120+157+92) ÷ (9480+10627+9332) = 369 ÷ 29439 = 0.012534 — 원값이 남아 있어야 이 검산이 가능하다. 그리고 화면은 이 배열의 길이로 “4일 중 3일치 반영됨”을 표시한다.

ingested_file — “이미 읽었다”의 근거

3. 구현 — 읽기 경로와 쓰기 경로

3.1 한 파일의 일생: _read_file

파일 하나가 행 목록이 되기까지다. Excel 기동은 여기서 파일당 딱 한 번이고, 그 안에서 모든 시트를 순회한다.

3.2 레이아웃 캐시의 수명 (실제 5건 분석)

지금 sheet_mapping 에는 5건이 들어 있다. 실물을 보면 이 캐시가 어떻게 늙는지가 한눈에 보인다.

idkindsheet_name저장된 앵커표
1jig_master기준정보B2="Shop명" G2="JIG ID" K2="설비명"detail 1개, 10열
2ees관리대장B2="JIG ID" C2="이벤트시간" H2="설비명"detail 1개, 24열
3mes생산이벤트D4="공정" I4="금형번호" F4="라인"detail 1개, 13열
4mes불량현황D4="라인" E4="설비코드" G4="투입수량"detail 1개, 20열, 헤더 2단 [4,5]
5iqcSheet1B33="No" C33="입고 시간" D33="금형 번호"표 4개, 마지막 표만 20열

id 2·3 이 흥미롭다. 둘은 이미 죽은 캐시다.

  • id=3 은 MES 가 “생산이벤트” 양식이던 시절의 것이다. 지금 MES 파일의 시트 이름은 불량현황 이고 D4 에는 “라인”이 있지 “공정”이 없다 → 앵커 불일치 → 절대 안 뽑힌다.
  • id=2 는 관리대장에 JIG ID 열이 있던 시절의 것이다. 지금 샘플 생성기(make_sample_uploads.py)가 만드는 관리대장은 B2 = "이벤트시간" 으로 시작하고 JIG ID 열이 아예 없다(시트 이름이 그 역할을 한다) → B2="JIG ID" 앵커가 어긋난다.
그래서 다음 배치는 이렇게 된다

jig_master·mes·iqc 는 앵커가 맞아 캐시 히트(LLM 0회)지만, ees 는 캐시 미스다. 관리대장 워크북의 시트 7개 중 첫 시트에서 에이전트가 한 번 돌고, 그 결과가 sheet_mapping 에 id=6 으로 저장되면 나머지 6개 시트는 그 새 레이아웃으로 통과한다 (load_layouts 가 ORDER BY id DESC 로 최신을 먼저 주기 때문이다).

즉 다음 수집은 “LLM 1회 + 나머지는 캐시”로 끝난다. 옛 id=2 는 지워지지 않고 그냥 영원히 안 맞을 뿐이다.

옛 행을 지우지 않는 이유는 감사(audit)다 — “언제 양식이 바뀌었고 그때 어떻게 해석했는가”가 추출값을 의심할 때 유일한 근거다. 대신 최신순 조회로 낡은 규칙이 먼저 걸리는 일을 막는다.

질문 메모 레이아웃 캐시의 수명·재사용 규칙에 대해 궁금한 점을 적어두세요.

3.3 쓰기 경로: 하나의 트랜잭션

모든 파일을 읽고 조립이 끝나면, 저장은 단 한 번의 트랜잭션으로 일어난다.

실패하면

어느 단계에서든 예외가 나면 rollback() 으로 배치 시작 전 상태가 그대로 유지된다. 반쯤 교체된 DB — 옛 금형과 새 부속정보가 섞인 상태 — 는 어느 쪽도 믿을 수 없어 가장 나쁘기 때문이다. 그리고 실패했다는 사실 자체는 ingest_run 에 status="error" 로 남는다.

install_seq 는 저장 시점에 매겨진다. enumerate(r.runs, start=1) 이고, runs 는 이미 started_at 순으로 정렬돼 있으므로 1번이 가장 오래된 구간이다. 그래서 배치를 다시 돌려도 같은 구간에는 같은 번호가 붙는다 — 앞에 구간이 하나 끼어들지 않는 한.

3.4 테이블 8개 레퍼런스

테이블가족키 / 주요 컬럼누가 쓰고 언제 지워지나
ingested_file기억 path PK · kind · content_hash · seen_at registry.record_files 가 UPSERT. 디스크에서 사라진 파일의 행만 삭제
sheet_mapping기억 id PK · kind · sheet_name · layout_json · source_path registry.save_layout 이 INSERT 후 즉시 커밋. 절대 삭제하지 않음

mold결과 mold_no PK · status · line · machine · 수량 4종 배치마다 전멸/재생성
production_run결과 (mold_no, install_seq) PK · started_at · ended_at · defect_rate · defects_json 배치마다 전멸/재생성
mold_stage결과 (mold_no, stage) PK · items_json 배치마다 전멸/재생성. 행이 없는 것이 곧 missing
mold_design결과 mold_no PK · 치수 6종 배치마다 전멸/재생성. 1단계에서는 항상 빔(설계 폴더 미처리)
스키마를 늘릴 때의 함정

CREATE TABLE IF NOT EXISTS 는 이미 있는 테이블에 새 컬럼을 붙여주지 않는다. 그래서 db.py 에는 _ADDED_COLUMNS 딕셔너리가 따로 있고, init_db 가 PRAGMA table_info 로 확인해 없는 컬럼만 ALTER TABLE 로 붙인다. 이걸 빼먹으면 옛 molds.db 를 쓰던 환경에서 record_run 이 “no such column”으로 터져 배치가 통째로 실패하는데, 화면에는 error 만 뜨고 원인을 알 수 없다.

3.5 읽기(조회) 경로: DB → 화면

대시보드는 엑셀을 절대 건드리지 않는다. molds.db 만 읽는다.

조회 계층이 하는 “약간의 계산”이 두 군데 있는데, 둘 다 이유가 분명하다.

  • days_covered vs days_expected — defects_json 의 길이가 실제 반영된 날 수(3), covered_dates() 를 다시 불러 구한 것이 덮여야 할 날 수(4). 24시간 올림 규칙을 조회 쪽에 다시 구현하지 않고 수집과 같은 함수를 부른다 — 각자 계산하면 언젠가 조용히 어긋나고, 그때 화면의 “3/4일”이 무슨 뜻인지 아무도 확신할 수 없게 된다.
  • install 단계 배지 — mold_stage 에는 install 행을 만들지 않는다(그 데이터는 production_run 에 있다). 그것을 안 보면 표에 구간이 가득한데도 탭에는 “없음” 배지가 붙어 화면이 스스로와 모순된다. 그래서 production_run 에 행이 하나라도 있으면 install = ok 로 채운다.
질문 메모 쓰기 트랜잭션이나 조회 계층에서 궁금한 점을 적어두세요.

4. 엑셀 행이 바뀌면 — 시나리오 5개

드디어 본론이다. 각 시나리오마다 같은 형식으로 본다: 엑셀에서 무엇이 바뀌었나 → 어떤 문지기가 열리나 → LLM 이 도나 → DB 가 어떻게 달라지나.

모든 시나리오의 공통 규칙

DB 에는 “이 행만 업데이트” 같은 게 없다. 어떤 시나리오든 결과는 항상 “결과 테이블 4개를 전부 지우고, 방금 읽은 엑셀 전체로 다시 채운다”이다. 달라지는 것은 LLM 이 도느냐와 새 스냅샷이 이전과 어디가 다르냐뿐이다.

S1. 관리대장 맨 아래에 이벤트 추가 — 금형이 설비에 들어감

가장 흔한 변경이다. 현장에서 금형 RX39513 을 설비에 걸었고, 담당자가 관리대장 시트 #RX39513 맨 아래에 한 줄을 적었다.

왜 total_production 과 최신 불량율은 안 바뀌나

새 구간은 아직 안 끝났다. covered_dates(시작, None) 은 빈 목록을 돌려주므로 MES 조회 자체를 하지 않는다. latest_defect_rate 는 “가장 최근 구간”이 아니라 “불량율이 있는 가장 최근 구간”이라 4번 구간 값을 그대로 유지한다 — 가동 중이라 비어 있는 것을 “불량율 없음”으로 오해하지 않기 위해서다.

화면에서 이 상태는 open_runs 로 구분된다: “가동 중 1건(불량율 미확정)”.

질문 메모 S1 시나리오에서 헷갈리는 부분을 적어두세요.

S2. MES 셀 값 하나 수정 — 불량수량 정정

이 값은 RX39513 의 1번 구간(07-01 07:00 ~ 07-05 07:00)에만 들어간다. 그 구간이 덮는 날짜는 07-01·02·03·04 이고, 그중 MES 파일이 있는 날은 3일이다.

여기서 오해하기 쉬운 것

“불량수량을 두 배 넘게 올렸는데 목록 화면의 불량율이 그대로다?” — 맞다. 목록에 보이는 latest_defect_rate 는 가장 최근 구간 하나의 값이지 전체 평균이 아니다. 바뀐 값은 금형 상세의 ‘기간별 불량율’ 표 1번 행에서 확인해야 한다.

이 설계를 택한 이유는 “지금 이 금형이 어떤 상태냐”가 목록의 질문이기 때문이다. 한 달 전 구간의 수치를 평균에 섞으면 최근 악화가 묻힌다.

질문 메모 S2 의 계산이나 “왜 목록 값이 안 바뀌는가”에 대해 궁금하면 적어두세요.

S3. 표 구조가 바뀜 — 앵커가 깨지는 경우

지금까지는 캐시가 살아 있었다. 이번엔 헤더 위치나 문구가 달라지는 경우다. 세 가지 형태가 있다.

현실적 기대치

“양식이 안정적이면 LLM 호출은 평생 몇 번”이라는 기대는 맨 아래 표만 자라는 시트에서만 맞다. 실물 IQC 시트처럼 표 4개가 세로로 쌓인 형태에서는 위쪽 표가 자랄 때마다 시트당 1회씩 돈다. 동작 자체는 옳다 — 레이아웃이 실제로 바뀌었으니 재해석이 맞다.

S4. 파일 삭제 — 금형이 사라져야 할 때

관리대장 파일을 지우면 어떻게 될까? changed 는 비어 있지만 removed 가 차므로 배치는 돈다. 그리고 문지기 ③에서 “관리대장 파일이 없다”로 error 가 되어 DB 는 그대로 유지된다.

반면 MES 파일 하나(2026-07-02_불량현황.xlsx)만 지우면 배치가 정상적으로 끝나고, 이렇게 된다.

S5. 조용히 반영되지 않는 경우 — 반드시 알아둘 것

지금까지는 전부 “제대로 반영되는” 이야기였다. 반영되지 않는 경우가 하나 있고, 이게 가장 위험하다.

data_end_row 에 숫자가 박히면

에이전트가 data_end_row=40 으로 제출했다면 41행부터는 영원히 안 읽힌다. 파일 해시는 바뀌고, 배치는 돌고, 앵커도 맞고, 아무 경고도 안 뜬다. 화면은 정상으로 보이고 새 데이터만 없다.

실제로 지금 캐시에 그런 레이아웃이 둘 있다 — jig_master(end=8)와 iqc의 표들(end=13/22/30/40). 기준정보에 금형을 7번째로 추가하면 그 행은 안 읽힌다.

5. 이해도 점검 퀴즈 5문항

Q1. 배치가 성공적으로 끝났다. mold 테이블의 RX39513 행은 어떻게 되었나?

store.replace_all 은 결과 테이블 4개를 통째로 비우고 다시 채운다. 이렇게 하는 이유는 관리대장에서 사라진 금형이 대시보드에서도 사라져야 하기 때문이다 — upsert 만 하면 유령 금형이 영원히 남는다. 이력이 쌓이는 것은 결과 테이블이 아니라 기억 테이블(sheet_mapping, ingest_run)이다.

Q2. 관리대장 시트 #RX39513 맨 아래에 “위치=설비” 이벤트를 추가했다. mold.latest_defect_rate 는?

assemble 은 “가장 최근 구간”이 아니라 “불량율이 있는 가장 최근 구간”을 찾는다(reversed(mold_runs) 를 훑으며 defect_rate is not None 인 첫 값). 마지막 구간이 가동 중이라 비어 있으면 그 앞 구간으로 거슬러 올라간다. ④번이 왜 틀린지도 중요하다 — 투입이 0 이거나 조회할 날짜가 없을 때 0.0 을 넣으면 “불량 없음”이라는 거짓말이 되므로 코드는 항상 None 을 쓴다.

Q3. MES 파일에서 어느 하루의 불량수량을 120 → 300 으로 고치고 수집을 다시 돌렸다. 금형 목록 화면의 불량율이 그대로다. 왜인가?

목록의 latest_defect_rate 는 전체 평균이 아니라 최근 구간 하나의 값이다. 바뀐 값은 금형 상세의 ‘기간별 불량율’ 표 1번 행에서 확인해야 한다. ②번도 그럴듯하지만 틀렸다 — 불량율은 MES 의 PPM 컬럼을 가져다 쓰는 게 아니라 투입·불량 raw 수량을 합쳐 코드가 다시 계산한다(생산량이 다른 날을 같은 무게로 세지 않기 위해).

Q4. sheet_mapping 에 지금 ees 레이아웃이 하나 있는데, 앵커가 B2="JIG ID" 이고 현재 관리대장 파일의 B2 는 "이벤트시간" 이다. 다음 배치에서 무슨 일이 일어나나?

핵심은 load_layouts 가 시트 이름으로 거르지 않고 kind 로만 거른다는 점이다. 관리대장은 시트 이름이 곧 금형번호라 시트마다 이름이 다른데, 시트명으로 걸렀다면 양식이 똑같은 7개 시트가 각각 LLM 발견을 돌았을 것이다(=②번). 첫 시트가 발견을 마치면 그 결과가 즉시 커밋되고, ORDER BY id DESC 라 다음 시트가 그것을 먼저 만난다. 옛 레이아웃은 지워지지 않고 그냥 영원히 안 맞을 뿐이다(감사 목적).

Q5. 다음 중 엑셀에는 새 데이터가 있는데 화면에는 아무 경고 없이 안 나타나는 경우는?

나머지 셋은 전부 이름 붙은 손실로 화면에 보고된다 — 그 날짜의 MES 파일이 없으면 missing_mes_days, 기준정보에 없는 JIG ID 는 unknown_jig_id, 열어둔 파일은 unreadable_files + skipped. “조용히 빠지는 데이터가 없어야 한다”가 이 파이프라인의 원칙이라 버려지는 것마다 이름이 있다.

data_end_row 만 예외인 이유는 완전성 검증이 캐시 재사용 경로에는 없기 때문이다. find_layout_gaps(“이 레이아웃이 시트를 다 덮었나”)는 submit_layout 을 호출한 그 순간에만 돈다. 그때는 41행이 아직 없었으니 통과했고, 이후 배치는 앵커만 대조하고 곧장 파싱으로 간다 — 다시 검사할 기회 자체가 없다. 그래서 손실 카운터에도 잡히지 않는다.
질문 메모 틀린 문제나 해설이 이해 안 되는 부분을 적어두세요.
