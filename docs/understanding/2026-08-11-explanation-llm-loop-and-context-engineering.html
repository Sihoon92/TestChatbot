이 문서는 세 번째 편이다. 1편은 시스템의 전체 지도를, 2편은 엑셀 변경이 DB 에 어떻게 반영되는지를 — 둘 다 “무엇이 일어나는가(현상)”를 다뤘다.

이번에는 “어떻게 일어나는가(기전)”다. 그중에서도 가장 불투명한 부분, 즉 LLM 을 부르는 그 순간을 연다. 무엇이 정확히 전송되고, 왜 그렇게 생겼고, 루프가 어떻게 돌고 언제 멈추며, 컨텍스트가 어떻게 자라고 어디서 잘리는가.

이 페이지 쓰는 법

읽다가 궁금한 게 생기면 “질문 메모” 상자에 적으면 된다. 적는 즉시 이 브라우저에 자동 저장되고, 맨 아래 질문 저장 버튼을 누르면 같은 파일 이름으로 질문이 박힌 사본이 다운로드된다. 그 파일로 원본을 덮어쓴 뒤 Claude 에게 “질문 답해줘”라고 하면 답이 그 자리에 채워진다.

쉬운 버전이 따로 있다

이 문서를 읽고 나온 다섯 질문 — 도구 호출도 출력 토큰인가 · 출력 토큰 10K 는 어디서 나왔나 · Pydantic 은 어떻게 형식을 맞추나 · 왜 LLM 을 여러 번 부르나 · sheet_mapping 은 왜 있나 — 에 대한 답이 아래 초록색 “질문 메모” 상자들에 채워져 있다.

같은 내용을 비유와 그림 위주로 훨씬 쉽게 풀어 쓴 문서도 있다: 말밖에 못 하는 친구에게 엑셀을 읽히는 법. 이 문서가 어렵게 느껴지면 그쪽을 먼저 읽어도 좋다.

1. 배경 — LLM 을 부른다는 것

1.1 완전 기초 (아는 사람은 건너뛰어도 좋다)

“에이전트가 엑셀을 살펴본다”는 표현은 편리하지만 오해를 부른다. 실제로 일어나는 일은 훨씬 건조하다.

가장 중요한 사실

LLM 은 기억이 없다. 매 호출은 완전히 독립적이다. “아까 시트 목록을 봤잖아”가 성립하려면, 그 대화 전체를 매번 다시 보내야 한다. 에이전트의 ‘기억’은 모델 안이 아니라 우리 쪽 메시지 리스트에 있다.

그래서 LLM 호출 한 번은 이렇게 생겼다.

알아둘 용어 다섯

토큰 — 모델이 세는 글자 단위. 영어는 대략 4자에 1토큰, 한글은 글자당 1~3토큰이라 훨씬 비싸다.
컨텍스트 윈도 — 한 번에 넣을 수 있는 토큰 상한. 넘치면 잘린다.
도구(tool) 호출 — 모델이 “이 함수를 이 인자로 불러줘”라고 구조화된 형식으로 말하는 능력.
ReAct 루프 — 생각→도구 호출→관찰을 모델이 스스로 멈출 때까지 반복하는 구조.
그래프 — 그 반복을 노드와 엣지로 표현한 것. LangGraph 가 실행을 맡는다.

1.2 이 저장소의 그래프는 둘이다

헷갈리기 쉬운 지점이라 먼저 갈라놓는다. 이름은 둘 다 “그래프”지만 성격이 정반대다.

도구없음. 순수 대화7종(엑셀 6 + submit_layout)
메모리있다. SQLite 체크포인터가 thread_id=session_id 로 턴을 이어붙인다없다. 매 호출이 빈 상태에서 시작해 그 자리에서 끝난다
수명세션 단위(며칠도 이어짐)시트 하나 분석 동안만. 끝나면 메시지 전부 버려진다

질문 메모 컨텍스트 예산 그림에서 궁금한 점을 적어두세요.
tool_call 로 submit_layout 을 출력하면 이것은 파이썬 호출함수로 실행될텐데, llm output 토큰으로 사용되는 구조인가?

그렇다. 전부 출력 토큰이다. LLM 은 도구를 실행하지 않는다 — 도구를 부르는 문장(이름 + 인자 JSON)을 지어낼 뿐이고, 지어낸 글자는 한 자도 빠짐없이 completion(출력) 토큰으로 계산된다.

도구 한 번에 토큰이 두 번 든다.

  • 출력 — 모델이 submit_layout({...}) 이라고 말하는 순간 (실측 평균 526 토큰, 최대 2,535자)
  • 0 토큰 — 파이썬이 실제로 그 함수를 실행하는 단계. LLM 이 관여하지 않으므로 공짜다
  • 입력 — 반환값("레이아웃을 접수했다…")이 ToolMessage 로 붙어 다음 호출의 입력에 실린다

submit_layout 이 유독 비싼 이유는 이 방향성 때문이다. read_range 는 부탁이 짧고 답이 길지만 (출력 평균 30토큰), submit_layout 은 부탁이 길고 답이 짧다 — 그리고 비싼 쪽은 부탁이다.

3.2 PROMPT: 두 조각의 합성과 규칙의 내력

시스템 프롬프트는 공통 절차와 종류별 어휘의 합이다.

규칙 하나하나에 실패의 내력이 있다

프롬프트를 읽다 보면 이상하리만치 구체적인 문장들이 나온다. 전부 실제로 당한 뒤 추가된 것이다.

프롬프트의 문장막으려는 실패
“sheet_outline 을 먼저 호출한다.” 모델이 read_range 로 시작하면 30행까지만 보여 33행부터 시작하는 표를 통째로 놓친다
“‘16칸’은 값이 있는 칸 수, ‘B~U’는 그 값들이 걸쳐 있는 열 범위, 그 뒤는 앞쪽 4칸의 미리보기일 뿐이다” 미리보기에 안 보이는 열을 “없다”고 판단하는 것. 실물에서 20열 표를 J 로 찍어 K 이후를 존재조차 모른 채 지나갔다
“오른쪽 끝은 윤곽이 알려준 열 범위를 그대로 쓴다. 위 예라면 B33:U41 이다” 범위를 찍어서 좁게 자르는 것. 구체적 예시까지 준 이유는 추상 규칙만으로는 안 지켜졌기 때문
“읽은 표를 윤곽과 대조하라. 16칸이라는데 4개만 보인다면 범위 바깥이다” 자가검증 절차를 아예 프롬프트에 심었다 — 모델이 스스로 “덜 읽었다”를 알아채게
“쓸모없어 보이거나 값이 비어 보인다고 빼지 마라” 빈 열을 생략하는 것. 빠뜨린 열의 값은 그 뒤 어디에도 나타나지 않는다
“data_end_row 는 … 없으면 null 로 둬라” 숫자가 박히면 그 아래 새 행이 영원히 안 읽힌다 (2편의 S5 함정)
“데이터 값이 아니라 헤더 텍스트를 골라라 — 데이터는 행이 추가되면 바뀐다” 앵커로 데이터 셀을 고르면 행이 하나 늘 때마다 캐시가 깨진다
“그 뒤에는 더 이상 도구를 부르지 말고 ‘완료’ 라고만 답하라” 종료 조건을 명시적으로 준다. 이게 없으면 모델이 계속 도구를 부르다 recursion_limit 에 걸린다
실측: 마지막 규칙은 완벽히 지켜지지 않는다

로그를 보면 #RX39513 시트에서 모델이 submit_layout 을 두 번 연속 호출했다 (메시지 8개 → 10개). 첫 번째가 이미 “접수했다”를 받았는데도 한 번 더 불렀다. 프롬프트로 종료를 요청할 수는 있어도 강제할 수는 없다는 뜻이고, 그래서 recursion_limit 같은 하드 상한이 별도로 필요하다.

질문 메모 프롬프트 규칙 중 “왜 이렇게 썼지?” 싶은 문장이 있으면 적어두세요.
pydantic으로 스키마를 설정하면 llm 출력이 어떻게 해당 스키마에 맞게 출력을 할 수 있는 것인가? 원리가 어떻게되나? 그냥 json으로 출력해달라고 해서 나온 것을 구조에 맞추는 작업을 하는 것인가? 즉, 도구 호출의 원리 및 pydantic의 원리에 대한 설명 필요.

“받아서 끼워 맞추는” 것이 아니다. 세 겹으로 되어 있다.

1겹 — 스키마를 프롬프트로 만든다. SheetLayout.model_json_schema() 가 Pydantic 클래스를 JSON Schema(실측 5,314자)로 바꾸고, 그것이 도구 정의에 담겨 모델에게 간다. Field(description=...) 에 적은 한국어가 그 스키마 안에 문자열로 그대로 실린다 — ColumnMap 의 docstring 이 “에이전트는 Python 주석이 아니라 JSON 스키마만 본다”고 직접 적어둔 이유다.

2겹 — 형식을 벗어나기 어렵게 만든다. 두 가지가 겹쳐 작동한다. ① 요즘 모델은 도구 호출 형식을 훈련 단계에서 익혔고, ② 런타임이 스키마를 문법(grammar)으로 바꿔 토큰 선택 단계에서 벗어나는 글자를 후보에서 지우기도 한다. 그래서 “JSON 으로 답해줘”와 달리 답이 문장 속에 섞여 오지 않고 이름 + args 라는 정해진 자리에 담겨 온다 — 정규식으로 뜯을 필요가 없다.

3겹 — 그래도 틀릴 수 있으니 검증한다. args_schema=SheetLayout 이므로 LangChain 이 도착한 args 를 Pydantic 으로 검증한다. 실제로 돌려본 결과:

anchors 누락    → ValidationError: anchors  Field required
data_start_row  → ValidationError: tables.0.data_start_row
   = "세번째줄"        Input should be a valid integer

이 오류 문장은 버려지지 않는다. ToolNode 가 repr(e) 로 감싼 ToolMessage 로 만들어 다음 호출의 입력에 넣어주고, 모델이 그걸 읽고 고쳐서 다시 낸다. 형식 오류가 사람 손 없이 수렴하는 이유다.

→ 시험지 비유와 그림으로: 후속 문서 Q3

3.3 숨은 프롬프트: 도구 스키마

여기가 이 저장소에서 가장 영리한 부분이고, 동시에 가장 놓치기 쉬운 부분이다.

핵심

Pydantic 모델의 description 은 주석이 아니라 프롬프트다. args_schema=SheetLayout 로 붙는 순간, 그 설명문이 JSON 스키마가 되어 모델에게 그대로 전달된다.

ColumnMap 의 docstring 이 이 사실을 직접 말하고 있다.

변환된 결과의 일부를 보면 감이 온다. AnchorCheck 의 클래스 docstring까지 description 으로 실려 나간다.

왜 JSON 을 텍스트로 받지 않는가

“마지막에 JSON 을 출력해줘”라고 시키는 방법도 있다. 이 저장소가 그렇게 하지 않는 이유는 세 가지다.

텍스트로 JSON 을 받으면도구 인자로 받으면
코드 블록·설명문이 섞여 파싱이 깨진다구조화된 args 로 도착한다 — 파싱 자체가 없다
타입/필수값 검증을 직접 짜야 한다Pydantic 이 검증한다. 틀리면 ToolNode 가 에러를 메시지로 되돌려 모델이 스스로 고친다
모델이 언제 끝났는지 애매하다도구 호출이 곧 종료 신호다 — 호출됐으면 holder 에 결과가 담긴다
결과를 반환값이 아니라 클로저로 받는 이유

discover_layout 은 그래프의 반환값을 쓰지 않는다. _make_submit_tool(holder, …) 의 holder dict 에 담긴 것을 꺼낸다. 검증이 통과한 그 시점의 Pydantic 인스턴스를 그대로 붙잡기 위해서다 — 그래프 반환값에서 다시 파싱하면 같은 실수를 반복하게 된다.

왜 상한이 “예외로 끝나야” 하는가

recursion_limit 을 명시하지 않으면 기본값(~25)에 조용히 걸린다. 두 에이전트 모두 40으로 명시한 이유는, 약한 모델이 수렴하지 못했을 때 GraphRecursionError 로 끝나야 호출자가 “이 파일은 error”로 처리할 수 있기 때문이다. 스텝을 조용히 다 쓰고 어정쩡한 답을 내는 것보다 시끄럽게 실패하는 편이 낫다.

질문 메모 루프 중첩이나 컨텍스트 압축에서 궁금한 점을 적어두세요.
시트별로 submit_layout 생성되는데 submit_layout 마다 llm이 여러번 호출되는데, 어떤 원리로 여러번 호출되는 것인지 로직에 대해 설명해줘

규칙은 하나다. 모델은 한 번 응답하면 그 턴이 끝난다. 도구 결과를 “보려면” 그 결과를 메시지로 붙여 다시 호출하는 수밖에 없다. 그래서 도구를 부를 때마다 LLM 호출이 정확히 하나씩 더 생긴다.

LLM 호출 횟수 = 도구 호출 횟수 + 1

마지막 +1 은 “더 이상 도구를 안 부르겠다”고 말하는 턴이고, 그 응답에 tool_calls 가 비어 있는 것이 곧 종료 조건이다(agent 노드의 조건부 엣지가 그것만 본다).

실제 로그의 기준정보 시트 — LLM 4회 / 도구 3회:

1회 (msgs 2)  18,055ms → sheet_outline('기준정보')
2회 (msgs 4)   6,771ms → read_range('B2:K8')     ← 1회 답을 보고서야 범위를 정할 수 있다
3회 (msgs 6)  17,534ms → submit_layout({...})
4회 (msgs 8)   9,133ms → "완료"                   ← tool_calls 없음 → END

여기에 두 가지가 더 붙을 수 있다.

  • 되돌려보내기 — find_layout_gaps 가 빠진 열을 찾으면 문자열로 돌려보내고, 모델이 고쳐 재제출한다. 그때마다 LLM 호출이 2회씩 늘어난다(재제출 + 마무리). 상한은 2회.
  • 모델이 지시를 안 따를 때 — 실제로 #RX39513 시트에서 이미 “접수했다”를 받고도 submit_layout 을 한 번 더 불렀다(메시지 8 → 10). 프롬프트로 종료를 요청할 수는 있어도 강제할 수는 없어서, recursion_limit=40 이라는 하드 상한이 따로 필요하다.

4. 엑셀이 바뀌면 — LLM 관점의 실행 경로

2편에서 “무엇이 바뀌는가”를 봤다면, 이제 같은 사건을 LLM 이 깨어나는가 / 무엇을 받는가의 관점에서 본다.

4.1 경로 A: 앵커 일치 → LLM 이 아예 안 깨어난다

관리대장 맨 아래에 이벤트 행을 하나 추가한 경우(2편의 S1)다. 코드가 실제로 밟는 경로는 이렇다.

0회LLM 호출
0자전송된 프롬프트
~21ms시트당 소요
3회문자열 비교 (앵커 대조)

여기서 앵커가 왜 “헤더 텍스트여야 하는지”가 결정적이 된다. 앵커가 데이터 셀을 가리켰다면 행이 하나 늘 때마다 값이 달라져 경로 B 로 빠지고, 매번 35분짜리 LLM 루프가 돌았을 것이다.

4.2 경로 B: 캐시 미스 → 새 대화가 시작된다

헤더 문구가 바뀌었거나 표가 밀린 경우다. 이때 만들어지는 첫 입력은 항상 똑같은 모양이다 — 이전 실행에서 무엇을 알아냈든 하나도 이어받지 않는다.

4.3 경로 C: 되돌려보내기 루프 (실측 9/28)

제출이 곧 종료는 아니다. 로그에서 submit_layout 결과 블록 28개 중 9개가 되돌려보내기였다. 실제 되돌림 메시지는 이렇게 생겼다.

이것이 “루프 엔지니어링”의 핵심 아이디어

모델의 출력을 결정론적 코드로 채점해서, 그 채점 결과를 다시 모델에게 먹인다. 격자는 표의 끝이 어디인지 알고 있고, 모델은 추측한다. 아는 쪽이 확인해야 한다. 이 되먹임이 있으면 약한 모델로도 완전한 레이아웃에 도달할 수 있다.

단 무한하면 안 된다. 그래서 2회다 — 이 상한이 “완전한 레이아웃”과 “아예 없는 레이아웃” 사이의 타협점이다.

되돌려보낼 때 예외가 아니라 평범한 문자열을 돌려주는 것도 그래프 구조 때문이다. ToolException 은 ToolNode 를 그대로 통과해 그래프 밖으로 나가버려서, 되돌려보내려던 제출이 파일 전체의 실패가 된다 — 검증이 막으려던 것보다 나쁜 결과다.

4.4 실제로 관측된 사고와 그 수정

이 로그에는 성능 사고 하나가 통째로 찍혀 있다. 관리대장 워크북의 시트 7개에 대해 에이전트가 각각 돌았다.

원인은 프롬프트도 모델도 아니었다. 캐시 조회 키였다.

수정 후 예상 동작

첫 시트에서 에이전트가 1회 돌고 → 결과가 sheet_mapping 에 즉시 커밋되고 → 나머지 6개 시트는 ORDER BY id DESC 로 그 레이아웃을 먼저 만나 앵커가 맞는다. LLM 호출이 약 30회에서 4~5회로 줄어든다(추정치: 30회 × 18.8초 ≈ 9분 → 약 1.5분).

여기서 배울 점은 방법론이다. “느리다”를 프롬프트 튜닝으로 접근했다면 못 고쳤다. 호출 로그를 세어보니 같은 양식을 일곱 번 분석하고 있었다 — 관측이 먼저다.

질문 메모 LLM 실행 경로 A/B/C 나 관측된 사고에 대해 궁금한 점을 적어두세요.
에이전트가 돌고 sheet_mapping 에 내용을 저장한다는 내용이 있다. 이 배경 스토리를 잘 모르겠다. sheet_mapping 에 왜 저장을 하는지, 언제/어떻게 사용하는지 등

왜 저장하나: 에이전트 1회가 약 50초 · 출력 토큰 수백 개다(실측 평균 18.8초 × 4회 왕복). 그런데 양식은 대개 안 바뀐다. 같은 양식을 매번 다시 분석하는 것은 순수한 낭비라, 비싸게 얻은 결과를 재사용하려고 sheet_mapping 테이블에 넣는다. 저장되는 것은 값이 아니라 좌표뿐이다(어느 열이 무엇인지, 표가 몇 행부터인지).

언제 저장하나: _read_file 에서 parse_rows 가 성공한 뒤에만, 그리고 save_layout 이 즉시 커밋한다. 순서가 중요하다 — 저장을 파싱보다 앞에 두면 파싱 불가능한 레이아웃이 캐시에 박히는데, 즉시 커밋이라 배치 롤백으로도 못 지운다(그 파일은 영구 실패). 즉시 커밋이라서 얻는 이득도 있다: 같은 배치의 다음 시트가 바로 꺼내 쓸 수 있다.

어떻게 쓰나: 시트를 열 때마다 pick_layout(grid, top_left, load_layouts(conn, kind)) 이 돈다. kind 로만 조회해 ORDER BY id DESC(최신순)로 받고, 각 레이아웃의 앵커 3개를 격자와 대조해 전부 일치하는 첫 레이아웃을 쓴다. 맞으면 LLM 호출 0회 — 프롬프트조차 만들어지지 않는다.

옛 레이아웃을 안 지우는 이유: “언제 양식이 바뀌었고 그때 어떻게 해석했는가”가 나중에 추출값을 의심할 때 유일한 근거다. 안 맞는 레이아웃은 앵커에서 걸러지므로 그냥 잠들어 있을 뿐이다 — 지금 DB 의 5장 중 #2 ees·#3 mes 가 그런 상태다.

배경 사고 하나: 예전에는 조회 키가 (kind, sheet_name) 이었다. 그런데 관리대장은 시트 이름이 곧 금형번호라 시트마다 달라서 서랍을 열어보지도 못하고 7개 시트가 각각 에이전트를 돌렸다 (약 30회 호출 ≒ 9분). 커밋 1d932df 가 kind 만 남겨 고쳤고, “어느 레이아웃이 맞는지는 앵커가 판정한다 — 원래 그러라고 만든 장치다”가 그 커밋의 논리다.

5. 이해도 점검 퀴즈 5문항

Q1. ReAct 루프의 4번째 LLM 호출에서, 모델에게 전송되는 것은?

LLM 은 상태가 없다. “기억”은 모델 안이 아니라 우리 쪽 메시지 리스트에 있고, 매 호출마다 처음부터 전부 재전송된다. 로그의 INPUT (n messages) 가 2 → 4 → 6 → 8 로 자라는 것이 그 증거다. 도구 스키마(실측 4,892자)도 매번 함께 간다. 그래서 루프를 한 바퀴 아끼는 것은 “호출 1회”가 아니라 “점점 커지는 입력 1회”를 아끼는 일이다.

Q2. SheetLayout 의 Field(description="...") 문구를 고치면 무엇이 달라지나?

args_schema=SheetLayout 로 붙는 순간 그 설명문이 JSON 스키마(실측 5,314자)가 되어 모델에게 그대로 전달된다. ColumnMap 의 docstring 이 이 사실을 직접 적어두고 있다 — “에이전트는 Python 주석이 아니라 JSON 스키마만 본다”. 그리고 submit_layout 하나가 도구 전체 스키마의 64%(3,120/4,892자)를 차지하므로, 필드를 늘리면 컨텍스트 예산이 그만큼 줄어든다. ④는 틀렸다 — 설명문은 검증 규칙이 아니다(타입·필수 여부가 검증을 정한다).

Q3. OLLAMA_NUM_CTX 를 명시하지 않아 런타임 기본값 4096 으로 서빙되면 무슨 일이 생기나?

이 실패가 특히 나쁜 이유는 아무도 오류를 보고하지 않는다는 데 있다. 호출자가 보는 것은 “빈 응답”뿐이라 프롬프트 품질 문제로 오해하기 쉽다. 실측 도구 스키마만 4,892자라 4096 토큰 창에는 대화가 한 줄도 없어도 이미 안 들어간다. config.py 가 ollama_num_ctx: int = 16384 를 굳이 명시하고 긴 주석을 단 이유가 이것이다 — 도구나 프롬프트를 늘릴 때 함께 올려야 한다.

Q4. submit_layout 이 “덮이지 않은 열이 있다”고 판단했을 때, 3번째 제출에서 여전히 빈틈이 있으면?

_MAX_SUBMIT_REJECTIONS = 2 다. 무제한이면 못 맞추는 모델이 걸렸을 때 왕복만 하다 recursion_limit(40)에 걸려 레이아웃을 하나도 못 얻는다. 이 상한은 “완전한 레이아웃”과 “아예 없는 레이아웃” 사이의 의도된 타협점이다. 참고로 되돌려보낼 때 ②처럼 ToolException 을 쓰면 안 된다 — 그 예외는 ToolNode 를 그대로 통과해 그래프 밖으로 나가버려서, 되돌려보내려던 제출이 파일 전체의 실패가 된다.

Q5. 관리대장 워크북(양식이 동일한 시트 7개)에서 에이전트가 시트마다 한 번씩, 총 30회 가까이 돌았다. 근본 원인은?

커밋 1d932df 가 WHERE kind = ? AND sheet_name = ? 를 WHERE kind = ? 로 바꿔 해결했다. 어느 레이아웃이 이 시트에 맞는지는 앵커 대조가 판정한다 — 원래 그러라고 만든 장치인데, 조회 단계에서 미리 걸러버려 그 장치가 일할 기회가 없었다. ④도 그럴듯하지만 반대다: save_layout 은 즉시 커밋하므로 다음 시트가 바로 읽을 수 있다(그래서 파싱 성공 후에 저장하는 순서가 중요하다). 이 사례의 교훈은 방법론이다 — “느리다”를 프롬프트 튜닝으로 접근했다면 못 고쳤을 것이고, 호출 로그를 세어본 것이 원인을 드러냈다.
질문 메모 틀린 문제나 해설이 이해 안 되는 부분을 적어두세요.

로그를 cl100k_base 로 실제로 세어봤다. 수집 1회 실행에 출력 토큰 17,491개(LLM 112회 응답)다. “10K 이상”과 자릿수가 맞는다. 그리고 어디서 나갔는지는 명확하다.

세 가지가 곱해져서 이 숫자가 된다.

  1. 시트 수 — 워크북마다 시트가 여러 개이고 시트마다 한 번씩 제출한다(이 실행은 20개)
  2. 재제출 — 30번 중 9번이 “덮이지 않은 열이 있다”로 되돌려보내졌고, 도구 인자는 부분 수정이 불가능해서 레이아웃 전체를 처음부터 다시 말해야 한다
  3. 레이아웃 크기 — 열이 20개인 표는 컬럼 매핑만으로도 수백 토큰이다

줄이는 방법은 사실상 캐시를 맞히는 것 하나다(맞으면 100% 절약). 되돌려보내기 상한 2회도 같은 목적의 장치다.
