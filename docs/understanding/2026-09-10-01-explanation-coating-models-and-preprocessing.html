1배경 — 이 파이프라인이 풀려는 문제

이 절은 공정을 처음 보는 사람을 위한 것이다. 이미 코팅 라인을 아는 사람은 1.2부터 읽어도 된다.

1.1 코팅이라는 공정, 25개의 볼트

넓은 필름이 롤에서 풀려 나오고, 그 위에 액체를 얇게 발라 말린다. 이게 코팅이다. 품질의 핵심은 딱 하나다 — 바른 두께가 폭 방향으로 균일한가.

액체는 다이(die)라는 긴 입술 모양 노즐에서 나온다. 이 입술의 벌어진 틈을 폭 방향으로 25개 구역(zone)으로 나눠, 각 구역마다 볼트로 미세하게 조인다. 볼트를 조이면 그 자리 틈이 좁아지고 → 액체가 덜 나오고 → 그 자리가 얇아진다.

볼트 25개 말고도 폭 전체에 한꺼번에 작용하는 손잡이가 넷 더 있다. 펌프 회전수(pump_rpm, 액체를 얼마나 밀어내나), 백프레셔 밸브 개도 (bp_open_rate), 그리고 다이 양쪽 끝 간격(os_gap, ds_gap)이다. 이 넷은 전체를 통째로 올리거나 내린다.

여기서 이미 모델이 둘로 갈린다

제어 손잡이가 두 종류다. 전체를 통째로 올리는 것 4개(스칼라)와 한 자리를 국소적으로 바꾸는 것 25개(zone별 gap). 물리적으로 하는 일이 다르니, 이 둘을 하나의 모델에 뭉뚱그리면 서로를 방해한다. 이것이 레벨 모델과 커널이 따로 존재하는 이유의 전부다.

질문 메모 공정 자체가 낯설다면 여기 적어보세요.

1.3 목표: 초기조건 도출

새 제품 lot 을 시작할 때, 작업자는 제어값을 대충 잡고 시작해서 Wet 을 보며 몇십 분간 볼트를 조여 나간다. 그 튜닝 시간 동안 나오는 필름은 전부 로스다.

이 프로젝트가 없애려는 것이 그 로스다. "이 제품이면 처음부터 이 조건으로 시작해라"를 과거 기록에서 배워 내는 것. 그러려면 제어값을 이만큼 바꾸면 두께가 이만큼 변한다는 관계를 알아야 하고, 그 관계를 데이터에서 뽑아내는 것이 이 파이프라인 전체의 일이다.

이 프로젝트의 고정 조건

우리는 실험을 할 수 없다. 라인을 세우고 "볼트 13번만 5단위 돌려 보자"를 못 한다 — 그 필름이 전부 불량이 되기 때문이다. 그래서 작업자가 평소에 한 조정을 실험으로 삼는다. 전처리의 거의 모든 복잡함이 여기서 나온다. 통제된 실험이 아닌 기록에서 실험을 발굴해야 하니까.

질문 메모 문제 설정에 대해 궁금한 점을 적어보세요.

2.1 ① parse.py — 파일을 표로

이 모듈만 파일을 만진다. 나머지는 전부 DataFrame 만 받는 순수 함수다. 하는 일은 셋:

  • 인코딩 판별. BOM 을 먼저 보고(파일이 스스로 밝힌 정답), 없으면 utf-8-sig → cp949 순서로 시도한다. 순서가 중요한 이유가 주석에 적혀 있다 — utf-8 한글을 cp949 로 읽으면 예외 없이 조용히 깨진 글자가 되어 끝까지 흘러간다. 반대 방향은 거의 항상 즉시 예외라 복구된다.
  • 바이너리 시그니처 감지. 엑셀을 이름만 .csv 로 바꿔 넣는 일이 잦아서, PK\x03\x04(xlsx), %PDF, 사내 DRM 헤더를 직접 알아보고 "인코딩 문제"가 아니라 진짜 원인을 말해 준다.
  • item_id 를 문자열로 고정. 이게 이 파일이 존재하는 거의 유일한 이유다.
조용한 실패 — 이 파일의 존재 이유

pandas 는 30030838 처럼 숫자로 보이는 열을 int64 로 읽는다. 그런데 항목 사전의 키는 문자열 "30030838" 이다. 그대로 조인하면 예외가 안 나고 전부 미매칭이 되어 빈 결과가 나온다. 그래서 원본은 전부 문자열로 읽고, 숫자·시각 변환은 _finalize 가 표준 컬럼명 위에서 한 번에 한다.

# app/coating/parse.py:249-264
def _finalize(raw, dict_path, encodings, path=None):
    raw = normalize(raw, path)              # 컬럼 별칭 → 표준 이름, 타입 변환
    raw[S.ROW_NO] = range(len(raw))       # ← 파일에 적힌 순서를 열로 박는다
    return raw.merge(load_item_dictionary(dict_path, encodings),
                     on=S.ITEM, how="left")

강조한 row_no 한 줄이 다음 단계의 전제다. 정렬·groupby 를 여러 번 거쳐도 "파일에 나중에 적힌 것"이 무엇인지 잃지 않기 위해서다.

질문 메모 인코딩·타입 관련해 궁금한 점.

2.2 ② dedupe_minute — 같은 분의 중복 접기

2.3 ③ compress_runs — 계단에서 변곡점만

여기가 전처리에서 가장 많은 행을 없애는 곳이자, 동시에 조정 이벤트가 처음으로 눈에 보이게 되는 곳이다.

값이 계단형이므로 "바뀐 시점"만 남기면 정보 손실 없이 데이터가 수십 분의 일로 준다. zone 1 의 gap 을 예로 들면: 

# app/coating/pivot.py:29-38
def compress_runs(deduped):
    d = deduped.sort_values([S.LOT, S.ITEM, S.AT])
    prev = d.groupby([S.LOT, S.ITEM])[S.VALUE].shift()      # 한 칸 뒤로 민 값
    changed = prev.isna() | (d[S.VALUE] != prev)            # NaN=lot 첫 관측, 또는 값이 변함
    out = d.loc[changed, [S.LOT, S.ITEM, S.AT, S.VALUE]].copy()
    out[S.PREV_VALUE] = prev.loc[changed].to_numpy()        # ← 이 열이 다음 단계의 열쇠
    return out.sort_values([S.LOT, S.AT, S.ITEM]).reset_index(drop=True)
핵심 구분 — 시작값 vs 변경

prev_value 가 NaN 이면 그건 lot 안에서 그 항목의 첫 관측이다. 사람이 바꾼 게 아니라 원래 그랬던 값이다. prev_value 에 숫자가 있으면 그때가 진짜 조정이다.

이 구분이 파이프라인 전체에서 반복해서 쓰인다 — build_events, tuning_end_last_change, _control_change_times 가 전부 prev_value.notna() 로 시작값을 걸러낸다.

질문 메모 압축 로직이나 prev_value 에 대해 궁금한 점.

2.5 ⑤ build_events — 손질 한 번을 하나로 묶기

작업자는 볼트를 하나만 돌리지 않는다. 12·13·14번을 몇십 초 사이에 연달아 만진다. 이건 세 번의 조정이 아니라 한 번의 손질이다. 묶어야 한다.

문제는 어떻게 묶느냐다. 코드에는 두 가지 규칙이 나란히 구현돼 있고, 그 차이가 이 파이프라인의 중요한 교훈 하나를 담고 있다.

규칙 A — 앵커 묶음 (_anchor_groups, 현재 규칙)

# app/coating/events.py:12-27
def _anchor_groups(times, merge_minutes):
    w = pd.Timedelta(minutes=merge_minutes)
    out = np.empty(len(times), dtype=int)
    g, anchor = 0, None
    for i, t in enumerate(times):
        if anchor is None or t - anchor > w:    # ← 직전 값이 아니라 '앵커'와 비교
            g += 1; anchor = t
        out[i] = g
    return out

규칙 B — 연쇄 묶음 (_run_groups, 옛 규칙)

# app/coating/events.py:30-37
def _run_groups(times, merge_minutes):
    gap = times.diff()                                   # ← 직전 변경과의 간격
    return (gap.isna() | (gap > pd.Timedelta(minutes=merge_minutes))).cumsum().to_numpy()

같은 데이터, 다른 결과 — merge_minutes = 2

def build_level_model(alpha, numeric):
    pre = ColumnTransformer([
        ("num",  make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), numeric),
        ("prod", OneHotEncoder(handle_unknown="ignore"), [PRODUCT_COL]),

3.2 커널 — "볼트 하나가 만드는 퍼짐 모양"

정의 — 커널 (kernel)

zone 하나의 gap 을 1단위 바꿨을 때, 주변 zone 들의 Wet 이 각각 얼마나 변하는지를 적은 짧은 숫자 벡터. k=2 면 길이 5: [g₋₂, g₋₁, g₀, g₊₁, g₊₂] — 왼쪽 2칸, 자기 자리, 오른쪽 2칸.

모델식:  Δweti = Σj=−k..k gj · Δgapi+j

# app/coating/model/profile.py:33-60 (요약)
def fit_kernel(delta_gap, delta_wet, k, alpha):
    y = delta_wet - np.nanmean(delta_wet, axis=1, keepdims=True)   # ← 레벨 성분 제거
    y = y.reshape(-1)
    x = build_design(delta_gap, k).reshape(n_events, n_zones, width)
    x = x - np.nanmean(x, axis=1, keepdims=True)                  # ← 설계행렬에도 같은 제거
    x = x.reshape(-1, width)
    ok = np.isfinite(y) & np.isfinite(x).all(axis=1)
    x, y = x[ok], y[ok]
    return np.linalg.solve(x.T @ x + alpha * np.eye(width), x.T @ y)   # 릿지 정규방정식
양쪽에 같은 변환을 걸어야 한다 — 실측으로 확인된 함정

y 에서 이벤트 평균을 뺐으면 x 에서도 빼야 한다. 한쪽만 빼면 추정이 편향된다. docstring 이 실측값까지 적어 놨다 — 참값 대비 전 성분 약 −0.07. 이유는 y 에서 뺀 이벤트 평균 m_e = Σ g_j·mean(Δgap) 자체가 Δgap 과 상관돼 있어서, 설계행렬을 그대로 두면 그 상관만큼 커널이 통째로 눌리기 때문이다.

3.3 그래서 왜 둘 다 필요한가

세 가지 이유가 겹친다.

이유설명
물리적 원인이 다르다 펌프 RPM 을 올리면 25개가 다 같이 올라간다. 볼트 13번을 조이면 12~14번만 움직인다. 하나의 모델에 넣으면 서로의 효과를 흡수해 버린다.
데이터 소스가 다르다 레벨은 absolute_samples(상태), 커널은 delta_samples(변화)를 쓴다. 전처리 2.7절에서 표가 갈리는 이유가 정확히 이것이다.
안 나누면 커널이 망가진다 fit_kernel 이 평균을 빼는 이유. 레벨 변화가 섞여 들어오면 커널이 상수항을 흡수해서 모양이 뭉개진다.
한 문장으로

레벨 모델은 "얼마나 두껍게"를 맞히고, 커널은 "얼마나 고르게"를 맞힌다. 현장에서 불량이 나는 이유가 둘 다이기 때문에 둘 다 필요하다.

질문 메모 레벨/커널 분리에 대해 궁금한 점.

4야코비안 행렬 — 이 프로젝트의 진짜 납품물

4.1 정의부터, 아주 천천히

고등학교에서 배운 기울기를 떠올리자. y = 3x 에서 기울기는 3이다. "x 를 1 올리면 y 가 3 오른다"는 뜻이다.

그런데 우리 문제는 입력도 25개(gap), 출력도 25개(Wet)다. 그러면 기울기가 하나로는 부족하다. "입력 j 를 1 올리면 출력 i 가 얼마나 오르나"를 모든 (i, j) 쌍에 대해 적어야 한다. 25×25 = 625개의 숫자가 나오고, 이걸 표로 적은 것이 야코비안 행렬이다.

정의 — 야코비안 행렬 (Jacobian)

출력이 여러 개, 입력이 여러 개일 때의 기울기 표. i행 j열 칸의 값은 ∂Weti / ∂gapj — "j번 볼트를 1단위 조이면 i번 zone 의 두께가 얼마나 변하나".

이 저장소에서는 이걸 영향행렬 G 라고 부른다.

4.2 커널과 야코비안의 관계

좋은 소식: 우리는 이미 커널을 배웠고, 커널을 펼치면 그게 곧 야코비안이다. Toeplitz 가정 덕분에 5개 숫자가 625칸을 다 채운다. 

# app/coating/model/profile.py:62-71
def kernel_to_matrix(kernel, n_zones=25):
    """커널을 25×25 영향행렬로 펼친다. 가장자리는 잘린다."""
    k = (len(kernel) - 1) // 2
    g = np.zeros((n_zones, n_zones))
    for i in range(n_zones):
        for j, off in enumerate(range(-k, k + 1)):
            src = i + off
            if 0 <= src < n_zones:            # zone 1 의 왼쪽 이웃은 없다 → 0
                g[i, src] = kernel[j]

4.3 왜 이게 납품물인가 — 예측이 아니라 개입

여기가 이 프로젝트를 이해하는 데 가장 중요한 지점이다.

현장이 원하는 건 "내일 두께가 18.2 일 것이다"라는 예측이 아니다. "지금 이 상태에서 볼트를 어떻게 돌리면 목표에 가장 가까워지나"다. 그건 예측이 아니라 개입(intervention)이고, 개입에 답하는 건 기울기다. 

# app/coating/model/inverse.py:16-57 — 역산의 심장부
def recommend_gap(g, current_gap, current_profile, target_profile,
                  bounds, max_step, lam_move, lam_smooth):
    want = np.nan_to_num(target_profile - current_profile)   # 만들고 싶은 변화

    def cost(delta):
        err = g @ delta - want                    # ← 야코비안 G 가 여기 쓰인다
        step = np.diff(delta)
        return (float(err @ err)
                + lam_move   * float(delta @ delta)     # 적게 움직여라
                + lam_smooth * float(step @ step))     # 인접 zone 단차를 줄여라

    def grad(delta):
        err = g @ delta - want
        ...
        return 2 * (g.T @ err + lam_move * delta + lam_smooth * d2)   # ← 기울기를 직접 준다

    lo = np.maximum(bounds[0] - current_gap, -max_step)    # 물리 한계 ∩ 1회 이동 한계
    hi = np.minimum(bounds[1] - current_gap,  max_step)
    res = minimize(cost, np.zeros(n), jac=grad, method="L-BFGS-B", bounds=list(zip(lo, hi)))
    return current_gap + res.x

lam_move 항이 실무적으로 결정적이다. 수학적으로 똑같이 좋은 해가 여러 개일 때, 작업자가 지금 값에서 가장 적게 움직여 도달할 수 있는 해를 고르게 한다. 아무리 정확해도 볼트 25개를 전부 돌리라고 하면 아무도 안 쓴다.

가장 중요한 결과 — 이 문서 전체의 핵심

야코비안이 납품물이라는 사실에서 이런 게 따라 나온다: Wet 을 아주 잘 맞히면서 기울기가 물리와 어긋난 모델은, 잘 맞히지 못하는 모델보다 더 위험하다.

왜냐면 그 모델은 확신을 가지고 틀린 방향으로 볼트를 돌리라고 하기 때문이다. 예측 정확도(MAE)는 좋게 나오고, 현장에서는 불량이 는다. 그리고 아무도 원인을 모른다.

질문 메모 야코비안 개념이나 "예측 vs 개입" 구분에 대해.

5Ridge 란 무엇인가

5.1 최소제곱에 벌점 하나를 더한 것

보통의 선형회귀(최소제곱, OLS)는 이걸 최소화한다:

‖ y − Xβ ‖²   — "예측이 정답에서 얼마나 벗어났나"

Ridge 는 여기에 한 항을 더한다:

‖ y − Xβ ‖² + α‖β‖²   — "그리고 계수가 크면 벌점"

한 문장 정의

Ridge = "잘 맞히되, 확신이 없으면 작게 대답해라". α(코드에서 coating_ridge_alpha, 기본 1.0)가 그 압박의 세기다. α=0 이면 보통 최소제곱, α가 크면 모든 계수가 0 쪽으로 눌린다.

5.2 왜 필요한가 — 두 가지 상황

① 공선성 — 변수들이 서로 닮았을 때

os_gap 과 ds_gap(다이 양 끝 간격)을 작업자가 거의 항상 같이 움직인다고 하자. 그러면 OLS 는 답을 못 고른다:

후보os_gap 계수ds_gap 계수예측 성능
A+0.5+0.5완전히 동일
B+100.0−99.0완전히 동일
C−50.0+51.0완전히 동일

셋 다 훈련 데이터에서는 오차가 똑같다. OLS 는 이 중 아무거나 고르고, 데이터가 조금만 흔들려도 B ↔ C 처럼 미친 듯이 튄다. Ridge 는 ‖β‖² 벌점 때문에 A 를 고른다. 그리고 A 만이 야코비안으로 쓸 수 있는 답이다 — B 를 믿고 볼트를 돌리면 재앙이다.

② 소표본 — 방정식보다 미지수가 많을 때

커널 추정에서 alpha * np.eye(width) 를 더하는 이유가 이것이다. XᵀX 가 특이행렬(inverse 가 없음)이면 OLS 는 아예 못 푼다. + αI 는 대각선을 조금 올려서 항상 풀리게 만든다. 

# app/coating/model/profile.py:59
return np.linalg.solve(x.T @ x + alpha * np.eye(width), x.T @ y)
#                              ↑ 이 한 항이 Ridge 의 전부다
이 저장소에서 Ridge 가 쓰이는 두 곳
  • level.py — sklearn 의 Ridge(alpha=1.0), 파이프라인 마지막 단계
  • profile.py — 정규방정식을 직접 푼다. Toeplitz 구조를 sklearn 에 넣을 방법이 없어서 손으로 짰다.

5.3 Ridge 의 숨은 선물 — 계수를 사람이 볼 수 있다

# app/coating/model/level.py:41-53
def coefficients(model, feats):
    """피처별 계수. 부호가 물리와 맞는지 사람이 볼 수 있어야 한다.

    크기 비교가 아니라 **부호와 상대 크기**를 보는 용도다 - 토출량↑ ⇒ 로딩↑ 이
    안 나오면 그 자체가 발견이다(데이터가 물리와 어긋났거나 교란변수가 있다)."""
    ridge = model.named_steps["ridge"]
    return {name: float(c) for name, c in zip(feats, ridge.coef_[: len(feats)])}

그리고 리포트는 이 계수의 부호를 자동으로 검사한다: 

# app/coating/report.py:552-558
rpm = lv["coefficients"].get("pump_rpm")
if rpm is not None and rpm < 0:
    lines.append("  - ⚠ Pump RPM 계수가 음수다. 토출량↑ ⇒ 로딩↑ 이라는 물리와"
                 " 어긋난다. 교란변수(고형분·점도)가 빠졌을 가능성을 먼저 본다.")

이게 다음 절로 가는 다리다. 트리 앙상블에는 이런 계수가 없다. 따라서 이 검사를 할 대상 자체가 없다.

질문 메모 Ridge·공선성·정규화에 대해 궁금한 점.

6왜 GBoost · Random Forest 를 그냥 쓸 수 없나

먼저 분명히 하자. "트리 앙상블이 나쁘다"가 아니다. 표 형식 데이터에서 트리 앙상블은 대체로 최강이다. 문제는 이 문제가 예측 문제가 아니라는 것이다.

6.1 거르개 네 개

거르개왜 필요한가
① 기울기가 물리와 맞아야 납품물이 야코비안이다. Wet 을 잘 맞히면서 기울기가 뒤집힌 모델은 확신 있게 틀린 조정을 낸다.
② 기울기가 살아 있고 외삽이 돼야 L-BFGS-B 가 jac=grad 를 먹는다. 그리고 추천이 필요한 지점은 관측 범위 밖인 경우가 많다.
③ 반증 가능해야 이 저장소엔 커널의 종 모양·랭크·SNR 을 각각 검사하는 관문이 이미 있다. 걸 자리가 없는 모델은 틀려도 틀린 줄 모른다.
④ 정보량 = 독립 임펄스 수 "수만 분이니 표본이 많다"는 착시다. 실질 정보는 조정 묶음 수와 공간 랭크(≈22)가 정한다.

6.2 트리는 ②에 정면으로 걸린다

level.py 의 docstring 이 이걸 정확히 예견해 놨다: 

# app/coating/model/level.py:1-7
"""레벨 모델 — zone 평균 Wet 을 예측한다.

릿지를 베이스라인으로 둔다. 이 문제는 물리적으로 단조롭고(토출량↑ ⇒ 로딩↑)
변수가 몇 개 안 된다. 트리 앙상블을 먼저 쓰면 구간별로 계단처럼 튀는 예측이
나오고, 그게 역산 최적화에서 이상한 해를 만든다. HistGradientBoosting 이
유의미하게 못 이기면 릿지를 채택한다(비교는 evaluate 모듈이 한다)."""

6.3 커널 쪽은 더 근본적으로 불가능하다

프로파일 모델이 하는 일의 전부는 파라미터 공유다 — Toeplitz 가정으로 625개를 5개로 줄이는 것. 트리에는 그 구조를 넣을 자리가 없다. 25개 zone 을 서로 독립적인 피처로 보고, 랭크 22짜리 데이터에서 "각 zone 마다 다른 규칙"을 배우려 들다가 과적합한다.

6.4 그리고 폐루프에서는 더 위험하다

작업자는 Wet 을 보고 볼트를 돌린다. 즉 gap 이 Wet 의 원인이자 동시에 결과다. 이걸 폐루프(closed loop)라고 한다.

신경망·트리가 특히 위험한 이유

표현력이 큰 모델일수록 작업자의 제어 법칙 C 를 더 잘 외운다. 그러면 Wet 예측 정확도(MAE)는 올라가는데 야코비안은 더 틀려진다. 예측 성능이 좋아지는 것이 오히려 나쁜 신호일 수 있다는 뜻이다.

그리고 이 실패는 조용하다. 지표는 전부 좋게 나온다.

6.5 그렇다면 트리를 어디에 쓸 수 있나 — 정당한 용도 둘

공정하게 말하자. 트리 앙상블에는 이 프로젝트에서도 진짜 쓸모가 있다. 다만 역산 모델이 아니라 진단 도구로서다.

① standard_table 판정의 신뢰도를 올린다 — 이게 제일 크다

지금 Ridge 가 나이브 베이스라인을 못 이기면 리포트는 standard_table("ML 이 답이 아니다, 제품별 표준 조건표를 써라")을 낸다. 그런데 그 판정에는 두 가지가 섞여 있다:

  • 제어값에 신호가 없다 → 표준 조건표가 진짜 정답
  • 관계가 비선형이라 Ridge 로 못 잡았다 → 모델을 바꿔야 함

GBM 도 같이 지면 앞쪽이 확정된다. 지금은 이 둘을 가를 수 없어서 standard_table 판정이 실제보다 약하다.

② 비선형·상호작용 탐지기

GBM 이 Ridge 를 크게 이기면 그 자체가 발견이다 — "선형으로는 못 잡는 구조가 있다". 그럼 Ridge 에 교호항이나 구간을 추가하면 된다. GBM 자체를 역산에 쓰는 게 아니라, GBM 이 알려준 것을 선형 모델에 반영한다.

결과뜻다음 행동
Ridge·GBM 둘 다 나이브에 짐제어값에 신호가 없다 (확정)standard_table 이 정답. 표준 조건표로 간다
Ridge ≈ GBM, 둘 다 나이브 이김관계가 선형이다Ridge 유지. 역산에 그대로 쓸 수 있다
GBM ≫ Ridge (10%+)비선형·상호작용 있음Ridge 에 교호항 추가. GBM 은 역산에 안 쓴다
GBM ≫ Ridge 인데 계수 부호가 물리와 반대폐루프 신호되먹임 강도 측정이 먼저. 여기서 모델을 키우면 틀린 방향으로 간다
질문 메모 "트리를 왜 못 쓰나"에 반론이 있으면 여기 적어보세요.

7코드 리뷰 — 지금 상태와 발견된 것

7.1 잘 되어 있는 것

  • 순수 함수 분리가 철저하다. parse.py 만 파일을 만지고, 나머지는 DataFrame 만 받는다. docstring 에 ★순수 표식까지 붙여 규율을 유지한다.
  • 주석이 "무엇" 이 아니라 "왜" 를 적는다. 특히 실패에서 배운 것을 남긴다 — fit_kernel 의 "실측: 참값 대비 전 성분 약 −0.07", parse.py 의 인코딩 순서 이유.
  • 판정을 먼저, 숫자는 그 다음. _verdict, response.verdict, _level_verdict 가 전부 "숫자를 낼 수 있는가"를 먼저 묻는다.
  • 실패가 트레이스백이 아니라 문장으로 나온다. 사내 PC 에서 돌리는 사람이 원인을 되돌려 줄 수 있게 하는 설계다.

7.2 발견 ① — 리포트가 거짓을 찍는다

격리가 0건일 때, report.py 가 zone 진단에 격리 이후의 Δgap 을 그대로 먹인다: 

# app/coating/report.py:113 → 189
ds = features.delta_samples(usable, dl, wet, valid, ...)   # usable = 격리 통과분 (0행)
dg = ds[GAP_DELTA_COLS].to_numpy() if len(ds) else np.zeros((0, 25))
...
zones = profile.zone_adjustment_diagnostics(dg)              # ← 0행짜리를 먹는다

실제로 돌려 본 결과:

n_adjusted      : 0
never_adjusted  : [1, 2, 3, 4, 5, 6] ... (총 25 개)
effective_rank  : 0

리포트에 "작업자가 25개 zone 을 하나도 안 만졌다"가 찍힌다. 사실은 정반대다 — 5분마다 만지고 있어서 격리가 0건이 된 것이다.

두 함수가 다른 질문을 한다

zone_adjustment_diagnostics = "작업자가 zone 을 골고루 만지고 있나" → 격리와 무관하다. 격리 이전의 전체 Δgap 을 먹여야 한다.

rank_diagnostics = "커널을 풀 자격이 있나" → 격리 통과분을 먹는 게 맞다.

지금은 앞쪽에 뒤쪽 데이터를 먹이고 있다. 한 줄 수정이다.

7.3 발견 ② — 코드가 자기 약속을 안 지켰다

6.2절에서 인용한 level.py docstring 이 이렇게 적어 놨다:

"HistGradientBoosting 이 유의미하게 못 이기면 릿지를 채택한다(비교는 evaluate 모듈이 한다)."

그런데 코드베이스 전체를 검색하면 트리 계열 사용이 0건이다. 이 docstring 한 줄이 유일한 언급이다. compare_level_models 는 Ridge vs 나이브 2종만 비교하고 끝난다.

즉 "릿지를 채택한다"는 결론이 비교 없이 내려져 있는 상태다. 사용자가 "GBoost 쓰면 안 되나?" 라고 물은 것이 정확히 이 빈 자리를 짚은 것이다.

7.4 발견 ③ — 역산이 파이프라인에 연결돼 있지 않다

inverse.recommend_gap — 4절에서 본, 이 프로젝트의 최종 산출물을 만드는 유일한 함수 — 의 호출처가 테스트 파일뿐이다. 그리고 학습된 모델을 저장하는 코드가 없다(joblib/pickle 0건).

이건 미완성이라기보다 의도된 순서다. report.py 첫 줄이 그렇게 적어 놨다 — "모델이 얼마나 정확한가 보다 이 데이터로 학습이 가능한가 가 먼저다." 관문을 통과한 뒤에 붙일 마지막 조각으로 남겨 둔 것이다.

질문 메모 리뷰 결과에 대해 궁금하거나 동의하지 않는 점.

9한 장 요약

질문답
전처리가 하는 일 스냅샷 로그(수십만 행) → 변경점만 남기고(compress_runs) → 손질 단위로 묶고(build_events) → 홀로 선 것만 고르고(isolation) → 두 개의 샘플 표. 통제된 실험이 없으니 작업자의 조정을 실험으로 발굴하는 과정이다.
레벨 모델 전역 손잡이 4개 + 제품 → 평균 두께 한 숫자. Ridge 회귀. 입력은 absolute_samples. "얼마나 두껍게"를 맡는다.
커널 볼트 하나가 만드는 퍼짐 모양 — 길이 5짜리 벡터. Toeplitz 가정으로 파라미터 625 → 5. 입력은 delta_samples. "얼마나 고르게"를 맡는다.
왜 둘 다 물리적 원인이 다르고, 데이터 소스가 다르고, 안 나누면 커널이 레벨 변화를 흡수해서 뭉개진다.
야코비안 커널을 25×25 로 펼친 영향행렬 G. ∂Weti/∂gapj. 현장이 원하는 건 예측이 아니라 개입이고, 개입에 답하는 건 기울기다. recommend_gap 이 이걸 먹고 "볼트를 얼마나 돌려라"를 낸다.
Ridge 최소제곱 + α‖β‖². "잘 맞히되 확신이 없으면 작게 대답해라." 공선성 아래에서 안정적인 계수를 고르고, 소표본에서도 항상 풀리게 한다. 덤으로 계수 부호를 사람이 검사할 수 있다.
왜 GBoost/RF 를
그냥 못 쓰나		 납품물이 예측값이 아니라 기울기인데, 트리는 구간별 상수라 기울기가 0이고 외삽이 안 된다. 반증 관문에 걸 자리도 없다. 폐루프에서는 작업자 습관을 외워 예측은 좋아지고 야코비안은 나빠진다. 단, 레벨 모델의 진단 도구로는 값어치가 크다 — standard_table 판정을 확정시킨다.
이 문서 전체를 한 문장으로

이 파이프라인은 예측기를 만들고 있지 않다. "이 손잡이를 이만큼 돌리면 결과가 이만큼 바뀐다"는 물리적 관계를 재고 있고, 전처리부터 모델 선택까지 모든 결정이 그 한 가지 목표에서 따라 나온다. 모델을 고를 때 물어야 할 질문이 "얼마나 잘 맞히나"가 아니라 "그 기울기를 믿고 볼트를 돌릴 수 있나"인 이유다.
