1. 배경 — 우리가 다루는 데이터가 무엇인가

1-1. 아주 깊은 배경 (이미 아시면 건너뛰세요)

코팅 라인은 넓은 필름을 옆으로 길게 펼쳐 놓고, 그 위에 액체를 얇게 발라 지나가게 하는 설비입니다. 필름의 폭 방향을 25칸으로 나눠 각 칸을 zone 이라고 부릅니다. 왼쪽 끝이 1번, 오른쪽 끝이 25번입니다.

칸마다 액이 얼마나 두껍게 발렸는지를 재는데, 그 두께 측정값이 Wet 입니다. Wet 이 목표보다 두꺼우면 재료가 낭비되고, 얇으면 불량입니다. 25칸이 고르게 나와야 좋은 제품입니다.

두께를 조절하는 방법은 액이 나오는 틈새의 간격을 조이거나 여는 것입니다. 이 틈새를 Gap 이라고 하고, zone 마다 따로 조절할 수 있습니다. 그래서 Gap 25개(입력) 와 Wet 25개(출력) 가 짝을 이룹니다.

우리가 궁극적으로 알고 싶은 것은 "Gap 을 이만큼 바꾸면 Wet 이 얼마나 변하나" 입니다. 그걸 알면 새 제품을 시작할 때 작업자가 손으로 더듬지 않고 처음부터 맞는 값을 넣을 수 있습니다.

그런데 우리는 설비를 마음대로 실험해 볼 수 없습니다. 양산 라인이니까요. 대신 작업자가 평소에 하는 조작 하나하나가 이미 실험입니다. "Gap 을 바꿨다 → Wet 이 변했다" 가 데이터 안에 이미 수천 번 들어 있습니다. 그걸 골라내는 것이 이 문서의 주제입니다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

1-2. 좁은 배경 — 원본 로그가 어떻게 생겼나

설비가 남기는 기록은 아주 단순한 모양입니다. 한 줄이 (로트, 시각, 항목번호, 값) 네 개로 끝납니다.

Lot ID작업일시항목 ID값

GRQC48XP2901-31 19:0030030839400
GRQC48XP2901-31 19:009003061118.2
… 29개 제어 항목 + 25개 Wet 항목이 매 분 전부 다시 …
GRQC48XP2901-31 19:0130030838300
GRQC48XP2901-31 19:0130030839400

여기서 중요한 성질이 두 개 있고, 이 둘이 전처리 전체를 결정합니다.

핵심 성질 1 — 스냅샷 로그

설비는 모든 항목을 매 시점 다시 기록합니다. 값이 안 바뀌어도 계속 찍습니다. 그래서 원본은 수십만~수백만 줄입니다.

핵심 성질 2 — 값은 계단형

Gap 값은 저절로 변하지 않습니다. 사람이 손으로 바꾼 순간부터 새 값이 계속 반복 기록됩니다. 300, 300, 300, …, 305, 305, 305, … 이런 모양입니다.

이 두 성질을 합치면 아주 유용한 결론이 나옵니다. 값이 직전 기록과 달라진 시점만 남기면, 정보를 하나도 잃지 않으면서 데이터가 수십 분의 일로 줄어듭니다. 300이 500번 반복된 것은 "300이었다" 한 줄로 충분하니까요. 그리고 남은 그 몇 줄이 곧 사람이 설비를 만진 순간 입니다.

질문 메모 스냅샷 로그·계단형 성질에 대해 궁금한 점

2. 직관 — 단어 네 개면 끝난다

이 전처리는 네 단계입니다. 단어 네 개만 구별하면 전부 이해한 것입니다.

2-1. 하나의 예시로 끝까지 갑니다

로트 하나에서 이런 일이 있었다고 합시다. 작업자가 처음 8분 동안 여섯 번 손을 대고, 그 뒤 두 시간 조용하다가 한 번 더 손을 댔습니다.

묶음(event)의 규칙 — 앵커 방식

첫 변경이 생기면 그 시각을 앵커(닻) 로 삼습니다. 앵커에서 2분 안에 일어난 변경은 같은 묶음. 2분을 넘는 첫 변경이 새 앵커 가 됩니다.

중요한 점: 기준이 항상 앵커 지 "직전 변경" 이 아닙니다. 그래서 어떤 묶음도 폭이 2분을 넘지 못합니다.

2-2. 왜 "앵커" 인가 — 이게 이번 변경의 핵심입니다

예전 코드는 직전 변경 과 비교했습니다. 그러면 2분씩 계속 이어지는 한 묶음이 끝없이 커집니다. 위 예시에서 0분부터 8분까지 전부 하나의 묶음이 됩니다.

질문 메모 앵커 방식 vs 연쇄 방식이 헷갈리면 여기에

2-3. 격리 — 쓸 수 있는 묶음 고르기

묶음을 만들었다고 다 쓸 수 있는 건 아닙니다. Gap 을 바꾼 효과 를 보려면 그 앞뒤로 아무 일도 없어야 합니다. 조정 직후에 또 조정하면 Wet 이 움직였을 때 둘 중 어느 것 때문인지 알 수가 없으니까요.

그래서 묶음마다 앞 10분, 뒤 10분 이 조용한지 봅니다. 재는 방법이 조금 까다롭습니다.

간격을 재는 방법 — "끝" 에서 잰다

앞간격 = 이 묶음의 첫 변경 − 직전 묶음의 마지막 변경
뒤간격 = 다음 묶음의 첫 변경 − 이 묶음의 마지막 변경

묶음이 폭을 가지므로, 시작점끼리 재면 실제 조용한 시간을 그 폭만큼 길게 잡습니다. 그래서 끝에서 잽니다.

위 예시에 적용하면 이렇게 됩니다.

묶음첫 변경마지막앞간격뒤간격판정
L1#101.5없음3 − 1.5 = 1.5 ✗ 뒤 1.5<10
L1#234.53 − 1.5 = 1.56 − 4.5 = 1.5 ✗ 앞뒤 1.5/1.5
L1#3686 − 4.5 = 1.5120 − 8 = 112 ✗ 앞 1.5<10
L1#4120120120 − 8 = 112없음 ✓ 사용 가능
여기서 저절로 생기는 좋은 성질

쪼개진 조각들은 서로가 서로를 탈락시킵니다. 1.5분 간격으로 붙어 있으니 앞뒤 10분이 나올 리가 없죠.

그래서 "쉼 없이 이어서 만진 구간은 실험으로 못 쓴다" 는 판단을 위한 별도의 규칙이 필요 없습니다. 격리 규칙 하나가 알아서 걸러냅니다. 규칙이 하나뿐이면 나중에 "왜 이게 빠졌지?" 를 한 군데서만 찾으면 됩니다.

제외 ① — Wet 이 변한 것은 조작이 아니다

Wet 은 결과 입니다. Wet 변화를 "조작" 으로 세면 원인과 결과가 뒤집힙니다.

제외 ② — 로트의 첫 값(시작값)은 조작이 아니다

로트가 시작되면 모든 항목의 값이 처음 한 번 기록됩니다. 이건 원래 그랬던 것 이지 누가 방금 바꾼 게 아닙니다. 코드는 이걸 prev_value(직전 값)가 비어 있는지로 구별합니다.

이걸 안 빼면 모든 로트가 29개짜리 가짜 조작을 하나씩 갖게 됩니다. 로트가 29개면 가짜가 29개죠.

"바뀌었다" 는 어떻게 판단하나

pivot.py 의 compress_runs 가 항목별로 직전 기록과 값이 다른 시점만 남깁니다. 숫자가 완전히 같으면 변경이 아닙니다 (오차 허용 범위 같은 건 없습니다 — Gap 은 설정값이라 소수점이 흔들리지 않습니다).

Q3. event 와 run_id 는 각각 뭘 뜻하나?

둘 다 변경들을 묶은 것 인데, 묶는 방법이 다릅니다. 같은 데이터를 두 가지 방식으로 묶어 나란히 두는 것이 핵심입니다.

event (묶음)run (연쇄)
id 모양L1#3L1@1
묶는 기준앵커 에서 2분 이내직전 변경 에서 2분 이내
폭 제한최대 2분 (보장됨)없음 — 무한히 커질 수 있음
뜻“한 번의 제어 조작”“작업자가 쉬지 않고 만진 한 세션”
쓰임실제 분석 단위. 격리 판정도 이 단위배제에 안 씀. 설명과 비교에만 씀
정체현재 규칙옛 규칙 그 자체
중요한 관계 — event 는 항상 run 안에 들어간다

한 묶음(event) 안의 변경들은 전부 앵커에서 2분 이내에 있으므로, 서로 이웃한 것끼리도 2분 이내 입니다. 그러면 연쇄 규칙(직전과 2분 이내)이 그 묶음 안쪽 을 쪼갤 방법이 없습니다.

그래서 event 하나가 두 run 에 걸치는 일은 수학적으로 불가능합니다. 코드가 run_id 를 "first"(첫 값)로 집계하는 것이 안전한 이유입니다.

run_id 는 왜 남겨두나 — 두 가지 용도

  1. 로그에서 "이 조각들이 원래 한 덩어리였다" 를 보여주려고. 원장에 L1#1 · L1#2 · L1#3 이 나란히 있고 셋 다 run 칸이 L1@1 이면, "아, 작업자가 8분 동안 이어서 만진 걸 셋으로 쪼갠 거구나" 가 한눈에 보입니다.
  2. 옛 규칙과 비교하려고 (§3 대조표). run 이 곧 옛 규칙의 묶음이라, run 으로 접기만 하면 옛 규칙 결과가 추가 계산 없이 나옵니다.
# trace.py — legacy_events(): 옛 규칙 결과를 공짜로 만드는 곳
out = (
    iso.groupby([S.LOT, S.RUN], as_index=False)   # run 으로 접으면 = 옛 묶음
       .agg(...)
)
out[S.EVENT] = out[S.RUN]
# last_at 열을 **넣지 않는다** — isolation() 이 그 열이 없으면
# 자동으로 "시작 기준" 으로 돌아간다. 옛 규칙의 나머지 절반이 공짜로 재현된다.
여기가 설계상 예쁜 부분입니다

옛 규칙은 세 가지가 합쳐진 것입니다 — ① 연쇄 병합 ② 시작 기준으로 간격 재기 ③ 옛 창(앞30/뒤60).

run 으로 접으면 ①이 재현되고, last_at 열을 빼면 ②가 저절로 재현되고, 옛 창 숫자를 넘기면 ③입니다. 원본 데이터를 다시 훑지 않고 옛 결과가 나옵니다.

4. 코드 따라가기

파일 세 개면 전부입니다. 순서대로 봅니다.

4-1. _anchor_groups — 묶음 번호를 매기는 12줄

전체 전처리에서 가장 중요한 함수인데, 놀랍게도 12줄입니다.

def _anchor_groups(times, merge_minutes):
    w = pd.Timedelta(minutes=merge_minutes)      # 2분
    out = np.empty(len(times), dtype=int)
    g, anchor = 0, None
    for i, t in enumerate(times):           # 시각들은 이미 정렬돼 있다
        if anchor is None or t - anchor > w:  # ★ 앵커와 비교 (직전 값이 아니다)
            g += 1
            anchor = t                           # 이 시각이 새 앵커가 된다
        out[i] = g
    return out

바로 아래에 옛 규칙도 나란히 있습니다. 차이가 한 줄 인 것을 눈으로 확인할 수 있습니다.

def _run_groups(times, merge_minutes):
    gap = times.diff()                          # ★ 직전 값과의 차이
    return (gap.isna() | (gap > pd.Timedelta(minutes=merge_minutes))).cumsum().to_numpy()
여기서 확인할 것

t - anchor 인가 times.diff() 인가. 이 한 군데가 이번 변경의 전부입니다. 앵커 쪽은 anchor 변수가 묶음이 바뀔 때만 갱신되고, 연쇄 쪽은 매 행마다 갱신되는 셈입니다.

4-2. build_events — 두 방식을 동시에 계산한다

for _, g in ctrl.groupby(S.LOT, sort=False):   # 로트마다 따로 (로트를 넘나들지 않는다)
    g = g.sort_values(S.AT)
    g["_g"] = _anchor_groups(g[S.AT], merge_minutes)   # 새 규칙
    g["_r"] = _run_groups(g[S.AT], merge_minutes)      # 옛 규칙 (비교용)

ctrl[S.EVENT] = ctrl[S.LOT] + "#" + ctrl["_g"]...   # "L1#3"
ctrl[S.RUN]   = ctrl[S.LOT] + "@" + ctrl["_r"]...   # "L1@1"
ctrl[S.DELTA] = ctrl[S.VALUE] - ctrl[S.PREV_VALUE]     # 얼마나 바꿨나
ctrl[S.ZONE]  = ctrl[S.ITEM].map(_zone_of)             # 몇 번 zone 인가 (스칼라는 NaN)

그 다음 묶음 단위로 접습니다. 여기서 나오는 열들이 뒤에서 계속 쓰입니다.

열 이름뜻어떻게 나오나
event_id묶음 번호L1#3
worked_at첫 변경 시각묶음 안 시각의 최소
last_at마지막 변경 시각묶음 안 시각의 최대
span_min묶음의 폭(분)last_at − worked_at — 항상 2 이하
run_id연쇄 번호L1@1
n_items만진 항목 수서로 다른 항목의 개수

4-3. isolation — 쓸 수 있는지 판정

end = out[S.LAST_AT] if S.LAST_AT in out.columns else out[S.AT]   # ★ 아래 설명
prev_end = end.groupby(out[S.LOT]).shift(1)      # 직전 묶음의 '끝'
next_at  = out.groupby(S.LOT)[S.AT].shift(-1)    # 다음 묶음의 '시작'

if bounds is not None:                        # 이웃이 없으면 로트 경계가 벽
    prev_end = prev_end.fillna(로트 시작시각)
    next_at  = next_at.fillna(로트 종료시각)

out["gap_before"] = (out[S.AT] - prev_end) / 1분
out["gap_after"]  = (next_at - end) / 1분
out["isolated"] = (gap_before >= pre) & (gap_after >= post)
첫 줄의 if 가 우연이 아닙니다

last_at 열이 있으면 끝 기준, 없으면 시작 기준으로 잽니다. 얼핏 "옛 데이터 호환" 처럼 보이지만 아닙니다.

§3 대조표가 옛 규칙을 재현할 때 일부러 last_at 을 뺀 표 를 넘깁니다. 그러면 이 함수가 알아서 옛날처럼 계산합니다. 이 줄이 옛 규칙 재현의 통로입니다.

로트 경계도 벽으로 친다

이웃한 조정이 없어도 로트가 시작된 직후 나 끝나기 직전 이면 못 씁니다.

  • 로트 시작 3분 뒤 조정 → 그 앞에 기준선을 잴 구간이 없습니다. 뭐와 비교하죠?
  • 로트 끝 3분 전 조정 → 반응이 끝나기 전에 로트가 끝납니다. 최종값을 못 읽습니다.

반대로 이웃도 없고 경계 정보도 없으면 제약이 없는 것으로 봅니다 — 없는 이웃을 이유로 버리지는 않습니다.

4-4. 탈락 사유를 문장으로 남긴다

def _iso_reason(gb, ga, pre, post):
    short_before = pd.notna(gb) and gb < pre
    short_after  = pd.notna(ga) and ga < post
    if short_before and short_after: return f"앞뒤 {gb:.1f}/{ga:.1f}<{pre}/{post}"
    if short_before: return f"앞 {gb:.1f}<{pre}"
    if short_after:  return f"뒤 {ga:.1f}<{post}"
    return None          # 통과한 것은 사유가 없다
왜 "탈락" 만 적지 않았나

✗ 뒤 1.5<10 이라고 적으면 얼마나 모자랐는지 가 그 줄에서 바로 읽힙니다. 1.5분이 모자란 것과 9.8분이 모자란 것은 완전히 다른 상황이죠 — 후자는 창을 조금만 줄여도 살아납니다.

"탈락" 만 적으면 창을 몇으로 바꿔야 할지 알 수 없어서, 결국 사람이 다시 물어보러 와야 합니다.

4-5. 왜 trace.py 를 따로 만들었나

events.py 는 규칙 입니다 — 파이프라인이 돌 때마다 실행됩니다.
trace.py 는 사람이 볼 표 입니다 — 사람이 확인할 때만 필요합니다.

섞어 두면 규칙을 읽으러 온 사람이 표 만드는 코드까지 같이 읽어야 합니다. 규칙은 이 시스템에서 가장 자주 의심받는 부분이라, 짧고 깨끗하게 유지할 값어치가 있습니다.

6. 퀴즈

다섯 문제입니다. 답을 클릭하면 바로 채점됩니다.

Q1. 어떤 로트에서 제어값 변경이 0분, 1.8분, 3.5분, 5.0분에 있었습니다. 병합창이 2분일 때 묶음(event) 은 몇 개가 될까요?

Q3. 어떤 묶음의 첫 변경이 10:00, 마지막 변경이 10:02 입니다. 다음 묶음의 첫 변경은 10:15 입니다. 이 묶음의 뒤간격 은?
Q4. run_id 는 배제(어떤 이벤트를 버릴지)에 쓰이지 않습니다. 그런데도 계산해서 남겨두는 이유로 틀린 것은?
Q5. 작업자가 8분 동안 쉬지 않고 여섯 번 조정했습니다. 앵커 병합은 이걸 세 조각으로 나눕니다. 이 세 조각은 결국 전부 격리 판정에서 탈락하는데, 왜 그런가요?
질문 메모 틀린 문제나, 답을 봐도 납득이 안 되는 부분

마치며 — 한 문단 요약

설비 로그는 모든 항목을 매 분 다시 적습니다. 값이 달라진 시점만 남기면 그것이 곧 사람이 설비를 만진 순간입니다. 제어 항목 29개(zone별 Gap 25 + 스칼라 4) 중 무엇이든 바뀌면 변경으로 세되, 로트의 시작값 과 Wet(결과) 은 뺍니다. 변경들을 첫 변경으로부터 2분 안으로만 묶어 event 를 만들고 — 그래서 어떤 묶음도 폭이 2분을 넘지 않고 — 같은 변경들을 옛 방식(직전 변경 기준)으로 묶은 것이 run 입니다. run 은 아무것도 버리지 않고, "이 조각들이 원래 한 덩어리였다" 를 보여주고 옛 결과와 비교하는 데만 씁니다. 마지막으로 묶음의 끝에서 앞뒤 10분이 조용한지 보고, 조용하면 그 조작을 실험 데이터로 씁니다.

아직 정해지지 않은 것

10분 이라는 창의 폭은 측정된 값이 아니라 가정 입니다. "Gap 을 바꾸면 Wet 이 10분 안에 반응을 마친다" 는 주장인데, 실데이터에서 그 시간을 아직 재지 못했습니다. --preprocess 의 §4 가 매 실행 그 가정을 스스로 검사하지만 완전하지는 않습니다 (자세한 것은 PR #10 의 "열린 채 남은 세 건").

그래서 이 네 값은 근거가 아니라 되돌릴 준비가 된 선택 입니다. 실측 지연이 나오면 그때 근거가 생깁니다.
