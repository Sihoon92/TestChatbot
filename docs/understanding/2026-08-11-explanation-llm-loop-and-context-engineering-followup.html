0. 준비운동 — LLM 은 말밖에 못 하는 친구다

이 다섯 질문의 답은 전부 한 가지 사실에서 나온다. 그러니 이것부터 확실히 하자.

기억이 없다는 게 특히 중요하다. 그래서 우리는 편지를 주고받듯 일한다. 말을 걸 때마다 지금까지 오간 대화를 처음부터 전부 다시 적어 보낸다.

알아둘 말 세 개

토큰 — 글자를 세는 단위. 대충 한글 한 글자가 1개쯤, 영어는 3~4글자가 1개쯤이다. 요금은 토큰 수로 매겨진다.
입력 토큰 — 우리가 보낸 글자. 대화 기록 + 도구 설명서 전부.
출력 토큰 — LLM 이 말한 글자. 보통 입력보다 비싸다.

질문 메모 준비운동에서 헷갈리는 점이 있으면 적어두세요.

1. Q1 — 도구를 부르는 것도 ‘말’인가?

tool_call 로 submit_layout 을 출력하면 이건 파이썬 함수로 실행될 텐데, LLM 출력 토큰으로 쓰이는 구조인가?

그렇다. 전부 출력 토큰이다. 그리고 이게 이 시스템에서 가장 비싼 출력이다.

창문 비유

친구는 손이 없다. 그래서 창문을 열고 싶으면 이렇게 한다.

submit_layout 은 왜 특히 비싼가

“창문 열어줘”는 짧다. 그런데 submit_layout 은 부탁 자체가 아주 길다. 표의 구조를 전부 말로 불러줘야 하기 때문이다.

한 줄 정리

LLM 이 도구를 “실행”하는 게 아니다. 도구를 부르는 문장을 지어내는 것이고, 지어낸 문장은 전부 출력 토큰으로 계산된다. 그래서 부탁이 길수록 비싸다.

질문 메모 Q1 에서 더 궁금한 점을 적어두세요.

2. Q2 — 출력 토큰 10,000개, 대체 어디서 나왔나

회사 내부에서 LLM 출력 토큰을 10K 이상 썼다는데, 이게 어디서 이렇게 많이 나온 건가?

추측하지 말고 세어보자. backend/logs/llm_calls.log 에 지난 수집 실행이 통째로 남아 있어서, LLM 이 말한 글자를 전부 모아 토큰으로 셌다.

왜 이렇게 차이가 날까? 다른 도구는 부탁이 짧고 답이 길다. 반대로 submit_layout 은 부탁이 길고 답이 짧다. 그리고 요금이 붙는 건 부탁(출력) 쪽이다.

도구LLM 이 말하는 것 (출력)도구가 돌려주는 것 (입력)
read_range{'sheet':'기준정보','address':'B2:K8'}
평균 30 토큰		표 전체 (수백~수천 글자)
submit_layout레이아웃 전체
평균 526 토큰 (최대 2,535자)		“레이아웃을 접수했다.” (한 줄)

그런데 왜 30번이나 불렀을까 — 세 가지가 곱해진다

시트 하나에 한 번이면 될 것 같은데, 로그에는 submit_layout 이 30번 찍혀 있다. 세 가지 이유가 곱셈으로 쌓인다.

줄이는 방법은 셋뿐이다

① 캐시를 맞히기 — 양식이 그대로면 LLM 을 아예 안 부른다. 가장 효과가 크다(100% 절약).
② 퇴짜를 줄이기 — 프롬프트를 고쳐 한 번에 맞게 내도록. 지금 상한은 2회다.
③ 스키마를 작게 — 필드가 많을수록 말할 게 많아진다. 다만 필요한 정보는 줄일 수 없다.

질문 메모 토큰 계산이나 절약 방법에 대해 궁금한 점을 적어두세요.

3. Q3 — Pydantic 을 쓰면 왜 형식에 맞게 나오나

Pydantic 으로 스키마를 정하면 LLM 출력이 어떻게 거기 맞게 나오나? 원리가 뭔가? 그냥 “JSON 으로 줘” 하고 받은 걸 구조에 끼워 맞추는 건가?

끼워 맞추는 게 아니다. 세 겹으로 되어 있다 — 양식을 보여주고, 벗어나지 못하게 막고, 마지막에 채점한다.

1겹: 파이썬 클래스를 ‘빈칸 시험지’로 바꾼다

Pydantic 모델은 사실 양식이다. 자기소개서 같은 것이다.

2겹: 시험지를 함께 보내고, 벗어나지 못하게 막는다

편지에 시험지를 동봉한다. 그리고 두 가지가 작동한다.

① 모델이 그렇게 배웠다 요즘 모델은 “도구를 부를 땐 이런 형식으로 말해”를 훈련 단계에서 익혔다. 그래서 대체로 알아서 맞춘다 — 하지만 대체로일 뿐이다.
② 프로그램이 글자 단위로 막기도 한다 모델이 다음 글자를 고를 때, 시험지에서 벗어나는 글자를 아예 고를 수 없게 막는 기능이 있다. 숫자 칸이면 숫자 아닌 글자를 후보에서 지워버리는 식이다.
여기가 “그냥 JSON 달라고 하기”와 갈리는 지점

“JSON 으로 답해줘”는 부탁이다. 모델이 설명문을 덧붙이거나 코드블록으로 감싸면 파싱이 깨진다.
도구 호출은 약속된 통로다. 답이 문장 속에 섞여 오지 않고, 이름 + 인자라는 정해진 자리에 담겨서 온다. 우리 코드는 정규식으로 뜯을 필요 없이 그 자리를 바로 읽는다.

3겹: 그래도 틀릴 수 있으니 채점한다

막아도 완벽하진 않다. 그래서 마지막에 Pydantic 이 채점한다. 실제로 틀린 답을 넣어 실행해 봤다.

그리고 이 오류 문장은 버려지지 않는다. 그대로 편지에 담겨 친구에게 되돌아간다. 친구는 그걸 읽고 고쳐서 다시 낸다.

Q3 한 줄 정리

부탁(시험지 보여주기) + 강제(벗어나지 못하게 막기) + 채점(Pydantic 검증) — 세 겹이다. “JSON 받아서 끼워 맞추기”는 첫 겹만 있는 방식이고, 그래서 잘 깨진다.

질문 메모 스키마·검증 원리에서 더 궁금한 점을 적어두세요.

4. Q4 — 시트 하나에 왜 LLM 을 여러 번 부르나

시트마다 submit_layout 이 하나씩 생기는데, 그 하나를 만드는 데 LLM 이 여러 번 호출된다. 어떤 원리로 여러 번 불리는 건가?

규칙은 딱 하나다. LLM 은 한 번 말하면 그 차례가 끝난다. 답을 들으려면 새로 말을 걸어야 한다.

스무고개와 똑같다

친구는 눈이 없다. 그래서 한 번에 하나씩만 물어볼 수 있고, 물어본 뒤에는 답을 들어야 다음 질문을 정할 수 있다.

외우면 편한 공식

LLM 호출 횟수 = 도구 호출 횟수 + 1

마지막 +1 은 “도구를 더 안 부르고 끝내겠다”고 말하는 차례다.

그림으로 보는 루프

퇴짜를 맞으면 한 바퀴가 더 는다

submit_layout 을 냈다고 바로 끝나는 게 아니다. 우리 코드가 진짜 엑셀 격자와 대조해서 빠진 열이 있으면 돌려보낸다.

왜 격자와 대조하나 — 프롬프트로는 안 되나

프롬프트에 “표의 오른쪽 끝까지 가라”고 세 번 적어놨는데도 13개를 빠뜨렸다. 격자는 표가 어디서 끝나는지 알고 있고, 모델은 추측한다. 아는 쪽이 확인해야 한다.

다만 퇴짜는 2번까지만이다. 무한정 돌리면 못 맞추는 모델을 만났을 때 40바퀴를 다 쓰고 레이아웃을 하나도 못 얻는다. 몇 열 빠진 레이아웃이 그것보다는 낫다.

질문 메모 루프가 도는 방식에서 궁금한 점을 적어두세요.

5. Q5 — sheet_mapping 서랍은 왜 있나

에이전트가 돌고 나서 sheet_mapping 에 저장한다는데, 배경을 잘 모르겠다. 왜 저장하고, 언제, 어떻게 쓰이나?

한 문장으로: 비싸게 얻은 지도를 서랍에 넣어두고, 다음엔 꺼내 쓰는 것이다.

이야기로 보는 배경

“지도가 아직 맞는지” 어떻게 아나 — 표지판 3개

건물을 고쳤을 수도 있다. 옛 지도를 그대로 믿으면 엉뚱한 칸을 읽는다. 그래서 탐험대는 지도를 그릴 때 표지판 3개를 함께 적어온다. 이게 앵커다.

표지판은 왜 ‘머리글’이어야 하나

표지판으로 데이터 칸을 골랐다면, 행이 하나 추가될 때마다 값이 달라져서 매번 “지도가 틀렸다”가 된다. 머리글(제목 줄)은 행이 늘어도 그대로 있다. 그래서 프롬프트가 “데이터 값이 아니라 헤더 텍스트를 골라라”라고 못 박아 두었다.

질문답
왜 옛 지도를 안 버리나? “그때는 이 양식을 이렇게 읽었다”가 나중에 숫자를 의심할 때 유일한 증거이기 때문이다. 대신 최신부터 맞춰봐서 옛 규칙이 먼저 걸리는 일을 막는다.

6. 퀴즈 5문항

답을 누르면 바로 채점과 해설이 나온다.

Q1. LLM 이 submit_layout({...}) 이라고 말했다. 이 글자들은 무엇으로 계산되나?

LLM 은 도구를 실행하지 않는다. 도구를 부르는 문장을 지어낼 뿐이고, 지어낸 글자는 전부 출력 토큰이다. 실제 실행(파이썬)은 공짜이고, 그 결과가 다음 편지에 실려 갈 때 비로소 입력 토큰이 된다. 즉 도구 한 번에 토큰이 두 번 든다 — 부탁할 때와 결과를 알려줄 때.

Q2. 수집 1회에서 출력 토큰 17,491개를 썼다. 가장 많이 쓴 곳은?

①②가 헷갈리기 쉬운데, 그 도구들은 부탁이 짧고 답이 길다. read_range 를 부르는 말은 {'sheet':'기준정보','address':'B2:K8'} 뿐이라 평균 30 토큰이다. 돌아오는 표가 아무리 길어도 그건 입력 쪽이다. 반대로 submit_layout 은 레이아웃 전체를 말해야 해서 평균 526 토큰이고, 30번 불려 15,793 토큰을 썼다. ④는 실제로 “완료” 두 글자라 20번 합쳐 114 토큰뿐이다.

Q3. Pydantic 스키마를 쓰면 형식에 맞는 출력이 나오는 원리는?

세 겹이다. ①은 “JSON 으로 답해줘”만 하는 방식인데, 모델이 설명문이나 코드블록을 덧붙이면 깨진다. 도구 호출은 약속된 통로라 답이 이름 + 인자 자리에 담겨 오고, 마지막에 Pydantic 이 채점한다. 실제로 data_start_row 에 “세번째줄”을 넣어보면 Input should be a valid integer 라는 오류가 나는데, 이 문장이 그대로 모델에게 되돌아가 스스로 고치게 만든다.

Q4. 어떤 시트에서 LLM 이 5번 호출됐다. 도구는 몇 번 불렸을까? (퇴짜는 없었다고 하자)

LLM 호출 = 도구 호출 + 1 이다. 도구를 부를 때마다 결과를 들으려고 다시 말을 걸어야 하고, 마지막에는 도구를 안 부르고 “완료”라고만 말한다 — 그 순간 루프가 끝난다. 실제 기준정보 시트는 LLM 4번 / 도구 3번이었다. 퇴짜를 맞으면 여기에 2번이 더 붙는다(다시 내기 + 마무리).

Q5. 양식이 똑같은 시트 7개인데 탐험대가 일곱 번 나갔다. 왜였나?

표지판은 맞춰볼 기회조차 없었다. 서랍을 “#RX28312 지도 있어?”라고 찾으니 항상 없다고 나왔기 때문이다. 지금은 종류(ees)로만 찾아서 지도를 전부 꺼낸 뒤 표지판으로 판정한다 — 원래 표지판이 하라고 만든 일이다. ①은 틀렸다: 표지판은 머리글에서 고르므로 시트가 달라도 같게 나온다. ②도 반대다 — 지도는 그 자리에서 바로 저장되므로 다음 시트가 즉시 꺼내 쓸 수 있다.
질문 메모 틀린 문제나 이해 안 되는 해설을 적어두세요.
