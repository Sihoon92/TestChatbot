코팅 실사 리포트 — 돌리는 법과 읽는 법

명령어 한 줄이 무엇을 만들고, 그 리포트의 각 숫자를 어떻게 읽어야 하며, insufficient 가 떴을 때 사업부에 무엇을 요구해야 하는가.

먼저 읽으면 좋은 글. 이 문서는 “돌리고 읽는” 실무편입니다. 왜 이런 걸 재는지는 지연·gain 기초편, 표 한 줄이 만들어지는 과정은 delta_samples 편에 있습니다.
이 글의 모든 출력은 실제로 실행해 얻은 것입니다. 지어낸 숫자는 없습니다.

읽다가 막히는 곳마다 질문 메모 상자가 있습니다. 적으면 이 브라우저에 자동 저장되고, 맨 아래 질문 저장 을 누르면 질문이 박힌 사본이 같은 파일 이름으로 내려받아집니다. 원본 자리에 덮어쓴 뒤 Claude 에게 “질문에 답해줘” 라고 하면 됩니다.

1. 이 리포트가 답하는 질문 — 배경

처음 보는 사람을 위해 (익숙하면 건너뛰세요)

코팅 공정은 움직이는 종이 위에 액체를 발라 말리는 일입니다. 폭 방향으로 25칸(zone)이 있고, 칸마다 다이 볼트가 하나씩 있어 그것을 돌리면 그 칸의 도포량이 바뀝니다. 결과는 라인 아래쪽 수분계가 1분마다 25칸을 재서 알려줍니다 — 이 값이 Wet 입니다.

목표는 “두께를 목표치에 맞추려면 어느 볼트를 얼마나 돌려야 하는가”를 자동으로 계산하는 것입니다. 그러려면 먼저 볼트 ↔ 두께의 관계를 데이터에서 배워야 합니다. 그런데 여기서 사람들이 흔히 건너뛰는 질문이 하나 있습니다.

이 리포트의 존재 이유

“모델이 얼마나 정확한가”보다 “이 데이터로 학습이 가능하기는 한가”가 먼저다.

사업부에서 받은 로그로 무작정 모델을 돌리면 숫자는 반드시 나옵니다. 그 숫자가 의미가 있는지는 별개 문제입니다. 이 리포트는 모델을 만들기 전에 데이터를 실사(due diligence)해서, 가능하면 통과시키고 불가능하면 무엇이 얼마나 부족한지를 요구 가능한 형태로 적어 줍니다.

이 글에 필요한 만큼의 배경

원본은 “세로로 긴 로그”입니다 — 한 행이 (lot, 시각, 제품, 항목ID, 값) 하나입니다. 항목ID 중 일부는 입력(볼트 25개 + 스칼라 제어값 4개)이고 나머지가 출력(Wet 25칸)입니다. 값은 계단형이라, 사람이 볼트를 돌린 순간부터 새 값이 계속 찍힙니다.

파이프라인은 이 로그에서 조정 이벤트를 뽑아내고(“누가 언제 무엇을 얼마나 돌렸나”), 각 이벤트에 대해 Wet 이 어떻게 반응했는지를 봅니다. 리포트는 그 과정에서 나온 사실들을 markdown 과 HTML 두 벌로 씁니다.

질문 메모 이 부분에서 궁금한 점을 적어보세요. 저장하면 이 파일에 그대로 남습니다.

2. 실행 — 명령어 세 개

전부 backend/ 에서 실행합니다. 실질적으로 외울 명령은 하나이고, 나머지 둘은 준비 단계입니다.

cd backend
python -m app.coating.report

2-4. 준비 단계 — 기종이 여럿일 때

왜 합쳐도 되나

라인 속도가 설비 고정값(전 제품 공통)이라 순수 지연 L 은 기종이 달라도 같습니다. 그래서 지연을 재는 표본은 합칠수록 좋습니다. 다만 product 열은 보존됩니다 — gain 은 다르기 때문입니다. 커널이 기종별 gain 을 같다고 강제하므로 영향행렬은 제품별로 갈라 봐야 하고, 호기가 다른 파일이 섞였는지도 이 열로 확인합니다.

3. 직관 — 두 개의 관문과 세 개의 판정

리포트 맨 윗줄은 언제나 판정입니다. 나머지는 그 판정의 근거입니다. 판정은 관문 두 개를 순서대로 통과하느냐로 갈립니다.

왜 랭크가 진짜 제약인가

이벤트 수는 “몇 번 밀어봤나”이고, 유효 랭크는 “서로 다른 방향으로 몇 가지나 밀어봤나”입니다. 늘 같은 방향으로만 밀었다면 그 방향의 반응만 알 수 있고, 다른 방향은 데이터에 정보가 없습니다. 아무리 좋은 모델도 없는 정보를 만들 수는 없습니다.

# 코팅 초기조건 데이터 실사 리포트

- **판정: trainable** — 1·2차 관문을 통과했다.

맨 윗줄만 읽고 끝낼 수 있어야 합니다. 세 가지 중 하나입니다.

trainable 두 관문 통과

모델을 만들어도 되는 데이터입니다. 다만 정확할 것이라는 보장은 아닙니다 — “배울 수 있다”까지입니다.

insufficient 1차 관문 탈락

깨끗한 이벤트가 0건이거나 20건 미만. 더 많은/다른 기간의 데이터가 필요합니다.

rank_deficient 2차 관문 탈락

이벤트는 있는데 방향이 단조롭습니다. 데이터를 더 받아도 안 풀립니다 — 실험 설계(DOE)가 필요합니다.

규모 — 먼저 “말이 되는 크기인가”

## 규모
- lot 수: 8
- 기간: 2026-02-02 06:00:00 ~ 2026-02-05 21:19:00
- 원본 행 수: 267840

여기서 볼 것은 딱 하나, 내가 요청한 데이터가 맞게 왔는가입니다. 기간이 예상보다 짧거나 lot 수가 1이면 그 아래 숫자를 읽을 필요도 없습니다.

식별성 — 2차 관문의 근거

## 식별성
- Δgap 유효 랭크: 24 / 25
- 상위 특이값: [20.846, 14.142, 14.142, 14.142, 12.806, 12.806, 11.314, 11.314, 11.314, 10.0]

유효 랭크는 3 이상이면 통과입니다. 위 예는 24 로, 작업자가 여러 zone 을 골고루 만졌다는 뜻입니다.

특이값은 방향별 “세기”를 큰 것부터 늘어놓은 것입니다. 읽는 법은 절대 크기가 아니라 감쇠 속도입니다. 

[20.8, 14.1, 14.1, 14.1, 12.8, ...]   완만함 — 여러 방향이 고르게 있다  ✔
[31.2,  2.1,  0.4,  0.0, ...]        급락 — 사실상 한 방향뿐이다      ✘
주의

effective_rank 는 SVD 의 수치적 임계(sv > sv.max()·max(shape)·eps)로 셉니다. 아주 작지만 0 은 아닌 방향도 랭크로 세어집니다. 그래서 랭크가 통과했더라도 특이값 목록이 급락하면 실질적 다양성은 부족합니다. 두 숫자를 같이 보세요.

5. 동특성 섹션 — L·τ·T_s 는 어떻게 나왔나

리포트에서 가장 정보량이 많은 부분입니다. 실제 출력 전문입니다.

## 동특성 (조정 → 반영까지)
- 노이즈 바닥: σ = 0.0212 (분당 ΔWet, 조정 없는 1,080분에서)
- 깨끗한 이벤트 32건 → (이벤트×zone) 표본 35개
- **순수 지연 L = 9분** — 조정 후 이 시간이 지나야 Wet 이 움직인다
  - 환산 거리 315 m (라인 속도 35 m/min, 설비 고정·전 제품 공통)
    — 다이~측정기 실제 거리와 자릿수가 다르면 이 L 은 노이즈를 문 것이다.
- 시정수 τ = 3분 (최종 변화의 63% 도달)
- 정착 T_s = 21분 — 다음 조정까지 최소 이만큼 띄워야 두 조정의 효과가 섞이지 않는다
- 최종 변화량 +2.7439 (부호 정렬, |Δgap| 1회분 기준)

줄마다 무엇을 뜻하나

σ = 0.0212 노이즈 바닥 · 분당 ΔWet 표준편차

모든 판정의 자다. 조정 근처 ±60분을 전부 뺀 구간에서만 잽니다 — 반응이 섞이면 σ 가 부풀고, 그러면 진짜 반응이 노이즈 아래로 숨습니다.

표본 35개 (이벤트 × 조정한 zone)

이벤트 32건인데 35개인 이유는 한 번에 두 zone 을 만진 이벤트가 3건 있어서입니다. 통계의 단위는 이벤트가 아니라 이 값입니다.

L = 9분 순수 지연 (dead time)

조정 후 Wet 이 움직이기 시작하기까지의 시간. 도포 지점의 종이가 측정기까지 이송되는 물리 시간입니다.

315 m 환산 거리 = L × 라인 속도

L 이 맞는지 확인할 외부 기준은 이것 하나뿐입니다. 다이~수분계가 315m 떨어져 있을 리 없다면 그 L 은 노이즈를 문 것입니다.

τ = 3분 시정수 (63.2% 도달)

움직이기 시작한 뒤 얼마나 빨리 가느냐. L 기준의 상대값이라 L 이 1분 틀리면 τ 도 반대로 1분 틀립니다.

T_s = 21분 정착 시간

현장에 바로 쓰이는 숫자입니다 — 다음 조정까지 최소 21분은 띄우라는 운전 규칙이 여기서 나옵니다.

이 합성 데이터에는 순수지연 8분·τ 4분을 심었습니다. 리포트는 L=9, τ=3 을 냈습니다. 틀린 게 아닙니다 — lag 8 시점의 반응 크기는 정확히 0 이고(그 순간부터 오르기 시작), 실제로 0 과 구별되는 첫 lag 은 9 입니다. τ 는 L 기준 상대값이라 L 이 1 커진 만큼 1 작아졌습니다. 두 값은 항상 짝으로 읽어야 합니다.

못 낼 때 나오는 문장들

동특성은 자기만의 판정을 냅니다. 못 낼 때 빈칸을 두지 않고 이유별로 다른 말을 합니다.

리포트 문장뜻과 다음 행동
노이즈를 잴 조용한 구간이 없다 σ 를 못 재서 판정 자체가 불가. 조정이 너무 잦다는 뜻입니다 — 아래 경고 참고.
지연 추정 불가 — 깨끗한 조정 이벤트가 없다 제어값이 바뀐 구간의 데이터가 필요합니다(no_events).
반응이 관측되지 않았다 — 최소 반응 ±0.0xxx no_response. 반응이 없는 게 아니라 그 크기 이하는 지금 표본으로 못 본다는 말입니다. 조정 폭을 키워야 합니다.
1분 단위로 가르려면 약 N건 필요하다 (지금 M건, K건 부족) underpowered. 반응은 보이는데 표본이 모자랍니다. 이벤트 수를 늘려야 합니다.
⚠ 관측 창이 끝날 때까지 아직 오르고 있다 τ 와 최종 변화량은 하한입니다. COATING_RESPONSE_POST_MINUTES 를 늘려 다시 돌립니다.
실행 중 확인한 함정

조정이 잦으면 동특성 섹션이 통째로 꺼집니다. σ 는 모든 이벤트의 ±COATING_RESPONSE_POST_MINUTES(기본 60분)를 제외한 구간에서만 잽니다. 그래서 조정 간격이 2시간보다 촘촘하면 조용한 분이 하나도 남지 않고 노이즈를 잴 조용한 구간이 없다 로 끝납니다.

이 글을 쓰며 25분 간격으로 조정하는 데이터를 만들어 돌렸더니 정확히 그렇게 나왔고, 간격을 140분으로 넓히자 σ = 0.0212 (조용한 1,080분)로 잡혔습니다. 바쁜 실조업 데이터일수록 이 벽에 부딪히기 쉽다는 뜻이라, 동특성이 안 나오면 먼저 02_events.csv 의 조정 간격부터 보세요.

질문 메모 L·τ·T_s·σ 중 헷갈리는 것을 적어보세요.

6. 막혔을 때 — 무엇을 요구할 것인가

번들 샘플로 돌리면 이렇게 나옵니다. 막힌 리포트가 오히려 정보가 많습니다. 

- **판정: insufficient** — 조정 이벤트가 0건이다. 제어값이 한 번도 바뀌지 않은
  구간만 있으면 입력→출력 관계를 배울 수 없다. 튜닝 과정이 포함된 구간의 데이터가 필요하다.

## 규모
- lot 수: 1
- 기간: 2026-01-31 18:55:00 ~ 2026-01-31 19:04:00     ← 10분짜리다
- 원본 행 수: 31

## 식별성
- Δgap 유효 랭크: 0 / 25
- 상위 특이값: []

중요한 것은 막힌 이유마다 요구할 것이 다르다는 점입니다.

숫자로 요구하는 법

“데이터를 더 주세요”는 요구가 아닙니다. 리포트의 lot 당 제어값 변경 횟수 로 역산합니다. 예컨대 깨끗한 이벤트가 12건이고 lot 당 평균 4건이면, 하한 20건까지 8건 부족 → lot 2개 분량입니다. 동특성 쪽이 막혔다면 required_events·shortfall_events 가 이미 그 계산을 해서 문장으로 적어 줍니다.

질문 메모 우리 데이터가 어느 갈래인지 헷갈리면 증상을 적어보세요.

7. 숫자를 못 믿을 때 — --dump

리포트는 결론만 말합니다. “왜 그런 결론이 나왔나”를 보려면 중간 산출물을 열어야 합니다. 

python -m app.coating.report --dump

그러면 <out>/dump/YYYYMMDD-HHMMSS/ 아래에 표 6개와 매니페스트가 남습니다. 번호는 파이프라인 순서라, 폴더를 열었을 때 무엇이 무엇 다음인지가 파일 이름만으로 보입니다.

덤프의 성격

검사용이지 캐시가 아닙니다. 쓰기만 하고 아무도 다시 읽지 않습니다 — 그래서 무효화 로직도 없고, 덤프를 켠 실행과 끈 실행의 결론이 달라질 여지가 없습니다. 형식이 parquet 이 아니라 CSV(+BOM)인 것도 목적 하나 때문입니다: 사내 PC 의 엑셀에서 바로 열려야 하고, BOM 이 없으면 한글 사유(“오염”·“정착”)가 깨집니다.

덤프로 실제로 무엇을 잡을 수 있나 — 예시

이 글을 쓰며 돌린 trainable 실행의 04_events_settled.csv 를 열어 보면 이런 게 보입니다. 

settled_at − worked_at 의 분포: {5.0분: 32건}
→ 32개 이벤트 전부 정확히 5분. (settle_window_minutes = 5)

정착까지 걸린 시간이 모든 이벤트에서 똑같이 설정값과 같다면, 그건 정착을 측정한 게 아니라 탐색이 가능한 가장 이른 자리를 집었다는 신호입니다. 실제로 이 데이터의 순수지연은 9분이라 5분 시점은 아직 반응이 시작되기도 전입니다.

알려진 한계

이것은 delta_samples 편 8장에 적어 둔 문제가 실제 덤프에 나타난 모습입니다. 순수지연이 정착 창(5분)보다 길면 settled_at 이 지연 안쪽에 박힙니다. L·τ·T_s 는 이 값을 쓰지 않으므로 동특성 섹션은 영향을 받지 않지만, 영향행렬 학습에 쓰이는 ΔWet 은 0 쪽으로 무너집니다. 아직 고치지 않았습니다.

확인 방법: 04_events_settled.csv 에서 settled_at − worked_at 이 전부 COATING_SETTLE_WINDOW_MINUTES 와 같은지 보면 됩니다.

8. 코드 지도 — 어느 함수가 어느 줄을 만드나

리포트의 한 줄이 이상할 때 어디를 열어야 하는지의 지도입니다. 실행의 뼈대는 report.profile_readings() 하나이고, 나머지는 거기서 부르는 순수 함수들입니다. 

report.main()                     CLI 인자 파싱, 입력 없으면 문장으로 실패
 └ report.run()                   기본값 결정은 여기 한 곳 (.env 를 보는 유일한 층)
    └ parse.load_readings()       파일을 읽는 유일한 곳
    └ report.profile_readings()   ★ 판정의 본체. 파일을 만지지 않는다
       ├ pivot.dedupe_minute()        (lot,분,항목) 중복 정리
       ├ pivot.compress_runs()        바뀐 시점만 남김        → 01_changes_control
       ├ features.wet_wide()          Wet 25칸 wide, 0 → NaN
       ├ features.valid_zones()       → "유효 폭" 섹션
       ├ events.build_events()        변경을 이벤트로 묶음     → 02_events, 03_event_deltas
       ├ events.annotate_settling()   정착·오염 표시          → 04_events_settled
       ├ features.delta_samples()     (Δgap 25, ΔWet 25) 표
       ├ profile.rank_diagnostics()   → "식별성" 섹션
       ├ report._dynamics_facts()     → "동특성" 섹션          → 05_aligned, 06_response_curve
       │  ├ panel.build_panel()          1분 등간격 격자
       │  ├ response.noise_floor()       σ 와 조용한 분 수
       │  ├ response.align_events()      lag 축 정렬 + 부호 정렬
       │  ├ response.response_curve()    lag별 mean·sem·n
       │  ├ response.dynamics()          L·τ·T_s·final
       │  ├ response.verdict()           identifiable / 부족분
       │  └ response.implied_distance_m() 환산 거리
       └ report._verdict()            → 맨 윗줄 판정
    └ report.render_markdown() / render_html()
    └ dump.write_tables()          --dump 일 때만
읽을 때의 요령

“이 숫자가 왜 이렇지”는 대부분 순수 함수 한 개로 좁혀집니다. 파일을 읽는 곳은 parse 하나, 설정을 읽는 곳은 run() 과 profile_readings() 의 첫 줄뿐입니다. 나머지는 DataFrame 만 받고 DataFrame 만 돌려주므로, 덤프의 표를 그대로 넣어 파이썬에서 재현할 수 있습니다.

10. 치트시트

명령

cd backend
python -m app.coating.report                          # .env 가 가리키는 원본으로
python -m app.coating.report --input raw/파일.csv      # 다른 원본 한 번만

python -m app.coating.merge --input a.parquet b.parquet --out m.parquet

맨 윗줄만 읽고 판단

  • trainable → 모델 단계로 간다.
  • insufficient → 이벤트가 없거나 20건 미만. 기간·튜닝 구간을 숫자로 요청한다.
  • rank_deficient → 데이터를 더 받아도 안 된다. DOE 를 제안한다.

그다음 세 줄

  • 오염 비율 — 높으면 조정 간격이 문제. 사유는 04_events_settled.csv 의 drop_reason.
  • 상위 특이값 — 급락하면 랭크가 통과했어도 실질 다양성 부족.
  • 환산 거리 — 설비 실제 거리와 자릿수가 다르면 그 L 은 믿지 않는다.
